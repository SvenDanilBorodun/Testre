## What this is

**EduBotics** — a vertically integrated educational stack for teaching Physical AI on **ROBOTIS OpenMANIPULATOR-X** arms to **German-speaking students**. Student lifecycle: install `.exe` → setup wizard → record demos (ROS 2 teleop) → train policy (Modal cloud GPU) → inference (local or classroom Jetson) → optional **Roboter Studio** (Blockly authoring + AprilTag perception + manual arm control).

Students run Windows 11 PCs (no GPUs). Training runs on Modal (NVIDIA L4; A100 for VLA). The product ships as a single `.exe` that installs a bundled WSL2 Ubuntu 22.04 distro named `EduBotics` containing Docker Engine + three containers — **no Docker Desktop**. Images pull from **GHCR (primary) with Docker Hub fallback**. A teacher/admin web dashboard is a separate Railway deploy. Installs are online-only.

Single git repo, no submodules. ROBOTIS upstream (`open_manipulator/`, `physical_ai_tools/`) is absorbed as plain directories.

## Six non-negotiable rules

These exist because we paid for the lesson. Don't undo without explicit user agreement.

### 1. German UI / English code

- **German** for everything a student/teacher/admin reads: tkinter labels, React UI, `detail` fields on API errors, user-visible log strings, toasts. Use literal `ä ö ü ß` (legacy files use `Schueler`; new code uses `Schüler`).
- **English** for everything the maintainer reads: code, comments, docstrings, internal logs, JSON keys, function names, commit messages.
- CI guard `german-strings-lint`: transliterations in `[FEHLER]`/`[WARNUNG]`/`[STOPP]` lines + an AST pass over cloud-API `detail=`/`error_message=` AND pi_agent `message=` (the pi_agent JSON `{"ok","message"}` surface is student-facing). `# english-ok` is the escape hatch.

### 2. Hardware safety lives in xacro + entrypoint, not software overlays

Software inference safety envelopes (NaN/Inf guard, joint clamp, velocity cap, stale-camera halt) were removed deliberately in the 2026-05 stripdown to fix recording↔inference asymmetry. Inference runs upstream `predict()` raw. Remaining protection is hardware-enforced or warning-only:

- **Xacro Dynamixel limits** (`omx_f.ros2_control.xacro`, `omx_l.ros2_control.xacro`): restrictive position limits exist ONLY on dxl12/dxl13 — dxl11 (Op Mode 4) and dxl14/15 are full-register-range, and the leader xacro has NO position limits (it is torque-free). The real safety floor is the gripper current limits (follower dxl16 `Current Limit 350` + `Goal Current 350` + `Shutdown 21`, Op Mode 5; leader trigger 300 mA).
- **ros2_control YAML**: 100 Hz; JointTrajectoryController in-flight `trajectory` tolerance 2.0 rad (effectively off — the safety floor is the Dynamixel current limit), `goal` 0.10 rad arm / 0.50 rad gripper, `goal_time` 5.0 s. Bumped from upstream's tight values because those aborted the 3 s quintic boot-sync mid-flight → compose restart-storm.
- **Torque-disable on shutdown** in `entrypoint_omx.sh::disable_torque()` — `trap … SIGTERM SIGINT EXIT`, so `set -e` aborts are covered. The leader path uses the namespaced `/leader/omx_l/set_dxl_torque`.
- **Phase-3 post-sync verification** in `entrypoint_omx.sh` (phases: 1 leader, 2 follower, 3 quintic sync + verify, 4 cameras) — 0.30 rad tolerance, arm joints only, soft-fail `[WARN]` (a hard exit looped compose restarts). Requires ≥50 % of commanded delta traversed. Two hard-exit paths remain: camera-disambiguation (exit 3) and `wait_for_device()`'s 60 s serial timeout (exit 1).
- Recording-side QUALITY guards (stale camera, camera-Hz deficit at 0.9×fps) are warning-only. But a topic-availability timeout, msg-conversion error, or add_frame failure hard-stops the recording timer, and the streaming frame-drop guard DISCARDS the in-flight episode and re-records it (no retry cap).
- **The leader ARM JOINTS 1-5 are torque-free/limp by design** — no gravity compensation is spawned (`Torque Enable 0`, Goal/Present Current interfaces commented out in `omx_l.ros2_control.xacro`; broadcasters only). The leader GRIPPER TRIGGER is NOT limp: `trigger_position_controller` + a 50 Hz `ros2 topic pub` of −0.7 rad simulate spring resistance under the 300 mA cap. Two comments still claim gravity compensation exists and are stale (`docker/open_manipulator/Dockerfile` leader block; `collision_monitor.py` header re `/collision_flag` consumers) — the xacro + launch files are the truth.

**ONE sanctioned exception: the teleop force/collision e-stop** — scoped to teleop/recording ONLY. Gated OFF during inference (inside the detector via `mode_is_inference`), and OFF during workflow and manual mode (`collision_monitor.py`, one combined `if on_workflow or on_manual` gate; the manual half is a sanctioned scope change from v2.11 — follower-only Roboter Studio has no leader and hand-guiding presses the arm at ~0 velocity, indistinguishable from a collision). It never modifies samples — a trip DISCARDS the in-progress episode, it does not filter or clamp.

If you need to reintroduce any OTHER software safety guard that modifies the pipeline, **stop and ask the user**.

### 3. The shipped image must reflect the repo

**physical-ai-server: COPY-WHOLESALE, no overlays.** The image's `physical_ai_server` package is a verbatim copy of `physical_ai_tools/physical_ai_server/` (staged as `pkg_src/` by `build-images.sh` — excluding `test/`, the three base Dockerfiles, `CHANGELOG.rst`, bytecode — then `rm`'d + `COPY`'d + re-`colcon`'d). "Image == repo HEAD" holds by construction: edits, new files AND deletions propagate. The old overlay model silently dropped edits. The Dockerfile asserts the stripped `safety_envelope.py` and the dead `training/trainers` + `evaluation` trees never re-enter (`build-images.sh` re-checks staged `pkg_src/` independently), and four build-time smoke gates must pass: policy imports + `CODEBASE_VERSION == 'v3.0'`, node import, `control_msgs` gpio import, functional cv_bridge rgb8 decode.

**open-manipulator: STILL the overlay model.** `apply_overlay()` in `docker/open_manipulator/Dockerfile` does sha256 pre/post verification over the **7-file** chain (both `ros2_control.xacro`s, both `*_ai.launch.py`s, both controller-manager YAMLs, `camera_usb_cam.launch.py`); build aborts on a missing upstream target. Kept because open_manipulator contains C++ `ros2_control` packages where a full re-`colcon` is heavy. When adding an overlay you **must** add it to the chain with a unique path filter — without that the source edit never reaches the image. Standalone scripts (`identify_arm.py`, `camera_ingest_node.py`, `calibrate_collision_currents.py`, `edu6_arm_node.py`, `feetech_bus.py`, `edu6_geometry.py`) are plain `COPY`s, not overlays.

**Both are guarded by `image-source-parity`** (`.github/scripts/image_source_parity.sh`, run per-arch in `docker-publish.yml::smoke-test`): physical-ai-server asserts byte-identity (`diff -r`); open-manipulator asserts every overlay by sha256. The parity script mirrors `build-images.sh`'s staging exclusions — change one, change both.

LeRobot is **not** overlaid — pip-installed from PyPI at `0.5.1` (Rule §5). `patches/fix_server_inference.py` is retained ONLY so CI `overlay-guard` can test the patch harness.

The server **amd64 BASE image is pulled, never built** — `build-images.sh` resolves `robotis/physical-ai-server:amd64-0.8.2` via `docker manifest inspect`. `Dockerfile.amd64` is forward-compat scaffolding (keep its pins in lockstep anyway).

**The other TWO server bases are ours, and NO workflow builds them.** Two hand-run triggers: `BUILD_BASE_ARM64=1 PLATFORM=arm64` → `Dockerfile.arm64` (Jetson), `BUILD_BASE_OPI=1 PLATFORM=opi` → `Dockerfile.arm64cpu` (Orange Pi CPU base). Every CI build merely *resolves* the tag pinned in `build-images.sh`. So **editing `Dockerfile.arm64cpu` / `.arm64` ships nothing on its own, silently** — the release goes green on the previously-published base. Rule §5 routes people into these files to bump LeRobot pins, which is what makes this load-bearing. Two fences: `ci.yml::base-version-guard` fails any non-comment edit to a base Dockerfile whose `PAS_BASE_IMAGE` tag didn't move in the same commit; `docker/bump-upstream-digests.sh` reports all three self-built pins and exits non-zero on a tag never pushed. The rebuild is a Rule §6 manual step.

### 4. Service-role key bypasses RLS — authorization is your job

Every Supabase query in `cloud_training_api/app/` runs as **service-role** via `services/supabase_client.py::get_supabase()` (lazy singleton, fails fast if secrets empty). RLS policies exist for defense-in-depth (anon-key/Realtime read paths) but are dormant under service-role.

Every endpoint touching another user's data **must** call an ownership assert. The teacher/workgroup/workflow helpers raise a German 404 — never 403 — to avoid existence leakage. The Jetson pair deliberately differs: `_assert_classroom_member` raises 403 (membership gating, not existence) and `_assert_jetson_owner` raises 404-or-**410 „Lock verloren"**; `_assert_workgroup_in_classroom` can also 400.

- `_assert_classroom_owned` / `_assert_student_owned` / `_assert_entry_owned` / `_assert_workgroup_in_classroom` — `routes/teacher.py`
- `_assert_workgroup_owned` — `routes/workgroups.py`
- `_assert_workflow_owned` (write) / `_assert_workflow_visible` (read ladder: owner OR group sibling OR classroom template) — `routes/workflows.py`
- `_assert_classroom_member` / `_assert_jetson_owner` — `routes/jetson.py`

**One missed assertion = silent IDOR.** RLS will not catch it. Writes additionally re-scope the query (`.eq("owner_user_id", …)`). Dataset registration is enforced atomically in Postgres instead: `register_dataset_safe` RPC (migration 026, `FOR UPDATE` on the caller's users row, HF-author anchor, P0034 → 403). The workflow read-visibility ladder is implemented FOUR times in `routes/workflows.py` (`_assert_workflow_visible`, inline in `list_workflows` + `get_workflow`, ad-hoc in `clone_workflow`) plus near-twin resolvers in `services/workgroups.py` — semantics changes must touch every copy.

The Modal worker uses the **anon key** + per-row `worker_token` (UUID). Its only DB write surface is the `update_training_progress(p_token, …)` RPC, guarded by the terminal-state `WHERE status NOT IN ('succeeded','failed','canceled','cancel_requested')` clause (migrations 010 + 032) — a late worker write is a P0001 no-op, and that P0001 is also the worker's in-band cancel signal. RPC GRANTs are asymmetric by design: `update_training_progress` is anon+authenticated (the worker), `register_dataset_safe` is service-role-ONLY. `update_training_progress` is deliberately absent from the boot schema probe (its defaulted 8-arg signature is overload-ambiguous) — drift there is invisible to `/health`.

### 5. Don't introduce drift between the LeRobot pinning sites

The LeRobot pin `0.5.1` must agree across:

- `modal_training/modal_app.py` constant `LEROBOT_VERSION`
- `physical_ai_server/Dockerfile.amd64` (`pip install "lerobot[pi,smolvla,peft]==0.5.1"` — the extra is `pi`, not `pi0`)
- `physical_ai_server/Dockerfile.arm64` (same line under the Jetson AI Lab pip index)
- `physical_ai_server/Dockerfile.arm64cpu` (Orange Pi 5 Pro CPU base, stock `ros:jazzy-ros-base`, plain PyPI; same line, but torch is PINNED EXPLICITLY — `torch==2.7.0` + `torchvision==0.22.0` — **before** lerobot, because this base inherits no torch and `lerobot 0.5.1` allows `torch<2.11`, so an unpinned resolve pulls 2.10.x and breaks the one-torch-2.7.x surface)
- the thin overlay `docker/physical_ai_server/Dockerfile` carries the same install and is what CI actually builds on

Bumping LeRobot is a **one-PR multi-site change**. `meta/info.json` `codebase_version: "v3.0"` and the Modal preflight `EXPECTED_CODEBASE_VERSION="v3.0"` are **derived** consts that move together with the pin.

**Hard dependency caps — never widen silently:**

- `numpy==1.26.4` force-reinstalled AFTER lerobot in the server images — ros-jazzy-cv-bridge's boost `.so` is compiled against NumPy 1.x; numpy 2.x SEGFAULTs the rgb8 decode path (uncatchable, kills the node). A build-time functional cv_bridge decode gate proves it.
- `scipy>=1.14.0,<1.18` in all four server Dockerfiles — scipy 1.18.0 dropped numpy-1.x support (`np.long`). Never widen back to `<2.0.0` while numpy is floored at 1.26.4.

**One PyTorch surface (torch 2.7.x), three CUDA channels — by design.** Modal worker: `nvidia/cuda:12.6.1-devel` + `torch==2.7.0` cu126. Student amd64: base ships torch 2.7.0+cu128, then the build-arg-gated `SLIM_CUDA=1` step (amd64 only, set by `build-images.sh`) swaps to **torch 2.7.0+cpu** and drops CUDA (~16 GB → **5.56 GB** after `flatten_image`'s `docker export | import`; the same flatten slims the `-opi` server). **Dropping CUDA is not just `/usr/local/cuda*`:** the `nvidia/cuda:*-devel` base also lands `/opt/nvidia/nsight-compute` (1192 MB) and `/usr/lib/x86_64-linux-gnu/libnccl.so*` + `libnccl_static.a` (774 MB) OUTSIDE that prefix, so the original glob could not reach them and they shipped in every student download through v2.14.0. Both are provably dead once torch is `+cpu` — no `libtorch_cuda.so`, no `site-packages/nvidia/`, `torch.distributed.is_nccl_available()` False, and **zero `DT_NEEDED` on either soname anywhere** in `/opt/ros`, `/usr/lib` or `/usr/local/lib`; the only FUNCTIONAL `libnccl` reference is `torch/__init__.py`'s `_load_global_deps()` OSError fallback, which globs `<sys.path entry>/nvidia/<folder>/lib` and never `/usr/lib`. (The base's `NV_LIBNCCL_*` env vars do survive in captured colcon `*.sh.env` files, and `/usr/lib/x86_64-linux-gnu` **is** in `/etc/ld.so.conf.d` because it is the default system lib dir — both inert; "nothing declares or dlopens it" is the claim, not "the string appears nowhere".) The same `SLIM_CUDA=1` branch now removes them: 7.53 GB → 5.56 GB, 2.626 → 1.592 GB compressed (−39 % on the actual download). They must STAY in that branch: opi has neither path (measured 0 MB), and Jetson is exempt for the reason given next. Jetson arm64 keeps GPU torch 2.7.0+cu128 (SLIM_CUDA defaults 0, never flattened — NCCL is a legitimate dependency there). CPU-only students are safe: `inference_manager.load_policy()` returns a German „needs GPU" error; recording never loads a policy; training is cloud-only.

### 6. CI/CD deploys

Seven workflows in `.github/workflows/` are the canonical path:

- `ci.yml` — 25 validator jobs on every push/PR to `main`.
- `supabase-migrate.yml` — **W1**. `supabase db push --linked --include-all` (password extracted with `urllib.parse`, never sed) against project `fnnbysrjkfugsqzwcksd`. Concurrency group is PROJECT-scoped so a tag release and a direct `main` push serialize instead of racing the DB. A `workflow_dispatch` `rollback` job applies `rollback/<name>.sql` via psql.
- `railway-deploy-cloud-api.yml` — **W2**. Read-only schema probe → `railway up` → `/health` gate asserting `body.commit == github.sha` (never a bare 200 — blue-green keeps the old pod serving 200).
- `railway-deploy-teacher-web.yml` — **W3**. Placeholder-build validate → `railway up` via `scripts/railway-deploy.sh` → `/version.json` gate asserting buildId contains the SHA.
- `docker-publish.yml` — **W4**. Builds + dual-pushes **8 images** (3 amd64 + 2 `-jetson` arm64 + 3 `-opi` arm64) to **GHCR primary (`ghcr.io/svendanilborodun/*`) + Docker Hub fallback (`nettername/*`)**. Fires on `main` pushes (`:latest`), `workflow_call`, `workflow_dispatch`. **Its standalone tag-push trigger was REMOVED** — on a tag, only `release.yml` W4 builds. Build order: `build-images.sh` pushes to Docker Hub first; the `retag` job then creates GHCR tags FROM Hub via `imagetools create` — GHCR is the consumption primary, not the build primary.
- `release-installer.yml` — **W5**. Windows `.exe` build; `workflow_call`-only + `workflow_dispatch` (no tag race).
- `release.yml` — top-level dispatcher on `vX.Y.Z` tags. **Golden order W1→W6**: supabase → cloud-api → teacher-web → docker → installer → **W6 `publish-gui-version`** (an inline job: sets Railway `GUI_RELEASE_REPO`/`GUI_DOWNLOAD_URL`/`GUI_INSTALLER_SHA256` then `GUI_VERSION` last, AFTER the `.exe` is attached — race-safe auto-update advertising; tag-push only).

**opi is DECOUPLED from the core release.** Its build + smoke-test matrix legs are `continue-on-error: matrix.platform == 'opi'`; the build leg uploads an `opi-build-success` marker artifact (containing the run's sha) as its LAST step, and the retag job retags opi ONLY when that marker exists AND matches `github.sha` — never off an existence probe of the mutable `:latest` (a failed/partial opi build must not promote the PRIOR release's opi images under new semver tags). Dual-push-integrity warns rather than fails for opi repos, and opi GHCR retags are best-effort, so no opi-only transient blocks the amd64/Jetson publish.

**`version-preflight` runs FIRST on tag pushes** and hard-fails the release when the tag ≠ the repo `VERSION` file. W6 advertises the TAG while the tarball/installer bake the FILE — a mismatch puts every Pi AND every Windows GUI into an infinite forced-update loop whose skip button never appears, because every update "succeeds" without advancing the anchor. W1 `needs` it; W2 additionally checks its result explicitly.

**The Pi tarball.** A W5-adjacent `pi-agent-tarball` job attaches `edubotics-pi-agent.tar.gz` (built from `robotis_ai_setup/pi_agent/`, top-level `pi_agent/`) with three baked files, all gated: the repo-root `VERSION` as `pi_agent/VERSION`, a generated `pi_agent/docker/versions.env` pinning `IMAGE_TAG=<VERSION>`, and the TRACKED `docker-compose.opi.yml` twin. The tarball must contain each; both version files must equal the repo `VERSION`; the packaged compose must `cmp` equal to `robotis_ai_setup/docker/docker-compose.opi.yml`. The post-`tar` cleanup deletes only the GENERATED `versions.env` — `rm -rf …/pi_agent/docker` would take the tracked twin with it.

W6 also publishes `PI_AGENT_SHA256` before the `GUI_VERSION` flip — the hash of that exact tarball, emptied BOTH on hash failure AND when any of the three `-opi:<VERSION>` images is anonymously pullable on NEITHER GHCR nor Docker Hub (the same GHCR→Hub order the Pi's own pull path uses, so availability matches the apply criterion). An empty hash ⇒ the Pi advertises NO self-update, so it can never pin a release whose `-opi` images never published. `pi-agent-tarball` is an ORDERING-only `needs` of W6, but W6 gates ONLY on `installer` success — a Pi-tarball hiccup never withholds the Windows `.exe` advertisement. **The reverse direction is undocumented and is an owner call**: a failed installer build skips BOTH Pi-facing jobs after the `-opi` images have already published (see `docs/KNOWN-ISSUES.md`).

**The Modal app (`edubotics-training`) deploys MANUALLY** — the image builds in Modal's infrastructure and the CI feedback loop is too slow to debug remotely:

```bash
cd robotis_ai_setup/modal_training
modal deploy modal_app.py
modal run -m modal_app::smoke_test    # optional
```

Run it BEFORE pushing a tag if the release touches Modal.

**The three self-built Docker BASES also deploy MANUALLY** — the second sanctioned carve-out, most easily missed because it looks like ordinary source. If a release touches `Dockerfile.arm64cpu` or `Dockerfile.arm64`, rebuild + push the base and bump its tag in `build-images.sh` BEFORE the tag, or **the release silently ships on the old base**. Commands under "Build images"; `base-version-guard` fences the tag bump at review time but cannot check that you pushed the image — `bump-upstream-digests.sh` is what catches that.

For the remaining surfaces, manual `railway up`, `psql -f`, and a full `build-images.sh` run are EMERGENCY-only. The `BUILD_BASE_*` invocations are a *workstation push by design* — "never push from a workstation" governs the student-facing thin images (`open-manipulator*`, `physical-ai-server*`, `physical-ai-manager*`), which CI owns. CI refuses to build from a dirty tree, so `*-dirty` tags can never reappear.

**Applying migrations:** `supabase db push` works; Claude's MCP `apply_migration` also works, but MCP re-stamps the version prefix into the ledger — **rename the on-disk file to the MCP-stamped value afterwards** or the next `db push` sees ghost-unapplied migrations (the doubled-prefix filename on migration 026 is this scar).

## Critical architectural choices (don't undo silently)

- **No Docker Desktop.** Docker Engine runs inside the bundled WSL2 distro `EduBotics`. The GUI invokes Docker via `wsl -d EduBotics -- docker …` (`docker_manager.py::_docker_cmd`) — never bare `docker`. USB reaches the distro via `usbipd attach --wsl EduBotics --busid X` (5.x positional form; the 4.x `--distribution` form is rejected), always resolved to an **absolute path** via `usbipd_resolver.find_usbipd()` (post-install PATH race: the Inno-launched GUI inherits explorer's pre-MSI PATH). Docker pinned `5:27.5.1-1~ubuntu.22.04~jammy` + containerd `1.7.27-1` via `apt-mark hold`, `containerd-snapshotter: false` — Docker 29.x snapshotter corrupts multi-layer pulls on WSL2 custom rootfs. `start-dockerd.sh` (the distro's `[boot]` command — NOT systemd, unreliable on custom-imported rootfs; `wsl.conf` also sets `appendWindowsPath=false`, so the script exports its own PATH) modprobes serial/UVC modules + starts udev + watchdogs dockerd on every boot; its modprobe list must stay in sync with `device_manager.diagnose_usb_environment`, and `device_manager.self_heal_wsl_serial` is the GUI-side counterpart at scan time. Installer Step 0 (`migrate_from_docker_desktop.ps1`) removes a pre-existing Docker Desktop (uninstall + unregister `docker-desktop*` distros + strip its autostart Run key; one-shot `.migrated` flag). usbipd-win is a pinned 5.3.0 MSI, SHA256-verified at install — a `RELEASE_PIN_NEEDED` sentinel in the `.iss` hard-fails `install_prerequisites.ps1` if a release forgets to update the pin.

- **The GUI is the SOLE owner of the container lifecycle.** The stack comes up ONLY on „Umgebung starten" — never on GUI launch or distro boot. Two enforcement points: (1) every student-stack service in `docker-compose.yml` is `restart: "no"` (`unless-stopped` resurrected the stack the instant dockerd started, holding the Dynamixel serial bus before any arm scan); (2) `gui_app.py::_run_prerequisite_checks_body` calls `docker_manager.ensure_environment_stopped()` **immediately after the dockerd-ready gate and BEFORE the rootfs-mismatch gate** — that gate `return`s, and a rootfs mismatch MEANS the distro is old and was never re-imported, i.e. exactly the population whose persisted container configs still carry `restart: unless-stopped`. Any new early return placed after a distro boot must sit BELOW the teardown. `_run_prerequisite_checks` is a re-entrancy guard (`_prereq_in_progress`, `try/finally`) wrapping that body, because four call sites re-run it on worker threads and two concurrent runs meant two 15-30 min pulls racing two prunes. `_scan_arms` calls it first too — `identify_arm.py` opens the same `/dev/serial` ports a live 100 Hz controller holds, so a running stack makes BOTH arms fail to identify. The GUI also runs `start_keepalive()` for the session (WSL2's ~60 s vmIdleTimeout would kill dockerd + the manager container mid-session; `atexit` reaps it).

  Two sanctioned exceptions. The **Jetson** compose uses `restart: unless-stopped` — the agent owns that lifecycle differently; don't conflate the two. The **Orange Pi (`-opi`) compose** runs `physical_ai_manager` as `restart: unless-stopped` and the pi-agent brings it up at boot, because the manager *is* the setup wizard on a Pi — a freshly booted Pi must serve the UI with the robot tier down. Only the manager tier is exempted; `open_manipulator` + `physical_ai_server` stay `restart: "no"`, and the pi-agent's `ensure_environment_stopped` stops ONLY the robot tier (never the manager, never `compose down` — stop + `rm -f` for every tier including factory reset, so `ros_net` and the manager survive).

- **Compose is boot-order- and security-opinionated** (`docker/docker-compose.yml`). Startup is health-gated: `physical_ai_server` waits on `open_manipulator: service_healthy`, `physical_ai_manager` on the server — don't remove the healthchecks. Only `open_manipulator` is `privileged` + `/dev:/dev`; the server container deliberately is NOT (attack-surface trim). The student compose now publishes **NO robot port at all** — `:9090`/`:8080` were removed in the 2026-08-06 rosbridge move, and only the manager's `127.0.0.1:80:80` remains. Removing them is what makes the nginx Origin allowlist non-bypassable; with the ports still open the proxy would be theatre (which is exactly what the Orange Pi's LAN-bound publishes made of its own gate until they were loopback-pinned). Anything published stays loopback-bound (`127.0.0.1:`) because rosbridge is unauthenticated — anyone reaching it can drive the arm. Both robot containers get `SYS_NICE` + rtprio/memlock ulimits (the 100 Hz loop); `mem_limit` 2g/6g + `pids_limit` are what actually OOM-kill a leaky node. The `open_manipulator` healthcheck INLINE-duplicates the entrypoint's WSL2 `uname -r | grep -i microsoft` camera-source detection — change one, change both. `CAMERA_NAME_1` defaults `gripper` but `CAMERA_NAME_2` defaults EMPTY: that asymmetry is how a 1-camera Roboter-Studio kit is told apart from a 2-camera rig.

- **Students see the React UI through an embedded WebView2 window, and GUI startup is update-gated.** „Web-Oberfläche öffnen" spawns a CHILD process (`EduBotics.exe --webview` → `gui/app/webview_window.py`, pywebview 6.x on `edgechromium` — pywebview demands the main thread tkinter already owns; system-browser fallback on import failure or a fast ~2 s exit). The URL carries a cache-busting `_v=<IMAGE_TAG>` param (WebView2's persistent cache would serve a stale app shell after an image update), and the GUI — not React — appends `?cloud=1` in cloud-only mode. Separately, `_check_prerequisites` hits the Cloud-API `/version` FIRST: a newer release opens a non-closable modal that downloads the installer (Content-Length + SHA-256 verified, HEAD-precheck against 404'd assets); „Überspringen" appears only after a failed attempt.

- **Elevated repairs share `_run_privileged`.** With an admin token already held (UAC off / „Never notify") the command runs DIRECTLY with no UAC and an INFINITE wait — a timeout kill would only reach powershell.exe while the wsl.exe grandchild survives detached, and killing `wsl --import` mid-copy risks the corrupt-VHDX state. A standard token routes through `_elevate_and_wait` (ctypes `ShellExecuteExW` with `use_last_error=True` + `SEE_MASK_FLAG_NO_UI`, German SE_ERR classification — PS `Start-Process -Verb RunAs -Wait` has unreliable wait semantics). `exit_code is None` means „never launched" (distinct from a numeric child failure); launch failures and ≥2 UAC cancels open a manual-command fallback dialog whose command MUST stay `$`-free (an interactive PowerShell interpolates `$` in double quotes before the child parses them). The post-reboot finalize (`_prompt_finalize_install`) runs AUTOMATICALLY — no consent dialog, re-entrancy-guarded via `_finalize_in_progress` (cleared in a `finally` after ALL post-processing). A `preflight_system.ps1` self-diagnostic runs once per launch on a daemon thread — FIVE non-fatal checks (temp-path/dotted-username write probe, UAC feasibility — where `isAdmin` is read, WSL2, dockerd, and the account-scope check that reads the finalize marker), always `exit 0`; the `Users:Modify` ACL grant on the diagnostics leaf is part of the sink setup, not a numbered check, informational only — output forced to UTF-8 via a `[Console]::OutputEncoding` wrapper and decoded `errors="replace"` (PS 5.1 writes redirected stdout in the OEM codepage; a cp1252 decode garbled umlauts and a stray 0x81 killed the whole capture).

- **The GUI-managed `.env` (`%LOCALAPPDATA%\EduBotics\.env`) is the compose interface.** Compose resolves `${REGISTRY}`/`${IMAGE_TAG}`/camera keys ONLY from the `--env-file` the GUI passes (Windows env vars do not cross the `wsl.exe` boundary). `config_generator.MANAGED_KEYS` (9: `FOLLOWER_PORT, LEADER_PORT, ROS_DOMAIN_ID, REGISTRY, REGISTRY_FALLBACK, IMAGE_TAG, EDUBOTICS_CAMERA_NAMES, EDUBOTICS_FOLLOWER_ONLY, EDUBOTICS_ROBOT_TYPE` + the `_MANAGED_PREFIXES` `CAMERA_DEVICE_`/`CAMERA_NAME_`) are re-emitted on every regenerate — a stale hand-pinned value is SUPERSEDED; everything else is preserved verbatim via `_read_unmanaged_lines`, with ONE exception: an `HF_TOKEN` + `HF_TOKEN_MACHINE` pair whose stamp proves it came from another PC is DROPPED (see the HuggingFace-token bullet). **Keep `MANAGED_KEYS` in lockstep with the emitted lines** — orphaning one leaks stale values (the `manifest unknown` scar). Per-rig overrides go through env vars (`EDUBOTICS_IMAGE_TAG`, `EDUBOTICS_REGISTRY`), never hand-edits of managed lines. Writes are atomic (temp + `os.replace` + fsync). The Pi has its own `MANAGED_KEYS` (13 keys vs the GUI's 9); the divergences read as deliberate but **nothing asserts them** — see `docs/KNOWN-ISSUES.md`.

- **The IMAGE and the COMPOSE are version-COUPLED since the 2026-08-06 rosbridge move, so `EDUBOTICS_IMAGE_TAG` is no longer a ONE-variable rollback on Windows.** `docker-compose.yml` ships with the **installer** (`{app}\docker\`, `constants.COMPOSE_FILE`), while `EDUBOTICS_IMAGE_TAG` pins only the IMAGES — so the two can be from different releases, and now that matters. `docker-compose.yml` no longer publishes `:9090`/`:8080`; the SPA reaches both transports same-origin through `nginx.conf`'s `location = /rosbridge` and `= /video/stream`; and BOTH of those live in the manager IMAGE. Pin the tag to a pre-fix release and you get **new compose (no publishes) + old nginx (no `/rosbridge` — verified zero occurrences at v2.14.1) + old SPA (`ws://<host>:9090`)**, i.e. a robot the browser cannot reach at all. **The rollback is therefore two-step: install the older `.exe` AND pin the tag** (or pin nothing — the baked `versions.env` already matches the installer). The reverse direction is safe: an OLD compose with a NEW image merely publishes two ports nothing uses. The **Orange Pi is unaffected for availability** — the SPA reaches both transports through the manager's `:80` proxy and the agent self-repairs the compose to the release it is running — but pinning an old `-opi` tag silently drops the Origin gate AND restores the LAN-bound `:9090`/`:8080` publishes (loopback-pinned since 2026-08-08), which is a security rollback and not a neutral one.

- **Registry resolution: env override → `docker/versions.env` → default**, shared by `REGISTRY` (`ghcr.io/svendanilborodun`), `REGISTRY_FALLBACK` (`nettername`), `IMAGE_TAG` (`latest`) in `gui/app/constants.py`. The runtime fallback pulls the digest-identical Hub twin and `docker tag`s it to the GHCR name so compose's single `${REGISTRY}` ref resolves; the fallback ref is computed by **prefix swap**, never `split('/')`. The auto-pull digest pre-check uses **set membership** of the remote candidate set (manifest-list + child digests) because a buildx push makes the local RepoDigest the LIST digest. One-variable rollback to Hub: `EDUBOTICS_REGISTRY=nettername` (that one IS still one variable — the registry does not change what the image contains). `prune_superseded_tags()` is a NO-OP while `EDUBOTICS_IMAGE_TAG` is set (both GUI and pi_agent twins, `.strip()`-guarded) — an explicit per-rig pin IS the documented rollback, and pruning would delete the tag the operator needs to return to; the caller additionally gates on `any_updated and not any_failed`. **But `EDUBOTICS_IMAGE_TAG` alone no longer rolls a Windows rig back across the 2026-08-06 rosbridge move — see the image/compose coupling bullet above.**

- **Both fleets pin `IMAGE_TAG` via a BAKED `versions.env`; the Pi's is baked by `release.yml`, not CI.** Windows gets `docker/versions.env` from `release-installer.yml`'s payload; the Orange Pi gets `pi_agent/docker/versions.env` from `release.yml::pi-agent-tarball`, landing at `/opt/edubotics/pi_agent/docker/versions.env` — the FIRST path `pi_agent/constants.py::_read_versions_env`'s upward walk probes, so no agent code knows about it. **The Pi's `versions.env` has TWO writers** — the release tarball AND `pi_agent/setup.sh` at PROVISION time (a Pi provisioned from a repo checkout never sees the tarball, so it previously had NO pin and silently tracked `:latest` = main HEAD). **With no `versions.env` at all the Pi falls back to `APP_VERSION` — its own release — NOT `latest`** (`constants.py::_default_image_tag()`; only an ACTUALLY-READ VERSION counts, via `_VERSION_IS_AUTHORITATIVE`, so the baked literal never becomes a confidently-wrong pin and a blank VERSION can't yield the unpullable ref `…-opi:`). The GUI still falls back to `latest`. The systemd unit's `EnvironmentFile` carries `IMAGE_TAG`, which is NOT the `EDUBOTICS_IMAGE_TAG` name `_resolve_setting` reads, so the env override never rescued it either. Intended consequence of the pin: a release whose `-opi` images never published fails LOUDLY on the Pi (`:X.Y.Z` resolves nowhere) instead of quietly running main HEAD — `pi_agent/docker_manager.py` names the missing version in German there, because a bare docker `manifest unknown` reads like a network fault.

- **The Pi agent REPAIRS its own systemd units, udev rules AND its opi compose, and every mutating endpoint takes a BOUNDED lock.** `agent.py::_check_system_files_version` byte-compares the installed `SYSTEMD_UNIT_NAMES` against the copies in `pi_agent/systemd/` and, on drift, installs the shipped bytes atomically (temp → fsync → chmod 0644 → `os.replace`, one `.edubotics-bak`, then an fsync of the DESTINATION DIRECTORY — the durability half; a rename is atomic for readers but that is ordering, not durability) + `systemctl daemon-reload` — never `restart`, never `enable`, never a unit not already installed.

  **Repair is per-FILE, via `_install_each`.** The legs used to be `all(install(n) for n in drifted)`, which short-circuits (a failure on the FIRST of two units left the second UNATTEMPTED) and collapsed to one bool (a unit that HAD been swapped was still named in the banner). Every drifted file is now attempted; the success sentence names `repaired` and the banner names `failed`. A MIXED outcome stays possible (there is no transaction across several `os.replace` calls) and is reported as mixed. The reload is gated on "something actually changed", not "everything succeeded". The System-tab `system_files_stale` banner fires ONLY on drift the agent could NOT repair, with at most ONE line naming exactly the unrepaired files. The `[WARNUNG]` says the Pi keeps running on the previous files, points at the reason logged ABOVE it (both of `_install_system_file`'s False returns log a German reason first) and names the next-boot retry as the primary remedy, with `setup.sh` demoted to the fallback. Rationale: units reach a Pi only via `setup.sh`, which needs a source checkout no classroom has, so any release touching a unit would otherwise pin a permanent amber banner on 100 % of the fleet.

  **`docker-compose.opi.yml` is in that repairable set** (`SHIPPED_COMPOSE_RELPATH`, `_compose_drifted`/`_renew_compose`). It used to be unreachable — it lived only in `robotis_ai_setup/docker/` while the tarball packages `-C robotis_ai_setup pi_agent` and the self-update rsyncs `pi_agent/` alone, so a release changing a forwarded env / healthcheck / image ref reached the field HALF-applied and SILENTLY. A **byte-identical TWIN** now ships at `robotis_ai_setup/pi_agent/docker/docker-compose.opi.yml`, fenced three ways: `ci.yml::pi-compose-twin-guard` (`cmp -s` against the source of truth, which stays `robotis_ai_setup/docker/docker-compose.opi.yml` — edit THAT one and copy), `ci.yml::compose-validate` (`docker compose config` on BOTH), and a `release.yml::pi-agent-tarball` gate. **The twin's path is DERIVED, never restated**: both gates read `SHIPPED_COMPOSE_RELPATH` out of `pi_agent/constants.py` via `.github/scripts/pi_shipped_compose_relpath.py` (the release gate from the TARBALL's own copy). Keep the constant a string literal or an `os.path.join()` of string literals; the script parses it statically. `_shipped_compose_path()` resolves PACKAGE-relative off `__file__` — repointing it at the `robotis_ai_setup/docker/` copy leaves the suite green in a checkout and silently kills the feature in the field.

  **The compose repair is VALIDATE-THEN-SWAP** (`docker compose -f <tmp> config -q`), a gate the systemd path deliberately lacks: a bad unit is inert, but an unparseable compose stops `docker compose` doing anything, so the always-on manager — the wizard, the only repair surface — would never come up. A refused swap leaves the working file byte-intact and raises the banner. **Isolating that gate from the student's `.env` takes TWO things**: omitting `--env-file` AND `env=docker_manager._scrubbed_env()`. Compose interpolates from the process environment too, and the unit is `EnvironmentFile=-/etc/edubotics/.env`, so the whole managed `.env` is already in the agent's `os.environ`. Scrubbing gives the gate the same PROCESS ENVIRONMENT `_compose_up` runs under — and nothing more: `_compose_up` also passes `--env-file`, which the gate deliberately does not. Do not "align" the two; that difference IS the fix. `boot()` runs the repair BEFORE `docker_manager.start_manager`, so the manager tier adopts the new compose in THAT boot while the robot tier waits for „Umgebung starten".

  **`UDEV_RULE_NAMES` joined that set too** (`UDEV_RULES_DIR`, `_drifted_udev_rules`/`_renew_udev_rules`): the rules always rode the tarball and the rsync, but nothing COMPARED them, so a release adding a VID/PID line would put an agent that scans for an arm onto a fleet whose `/dev` node it cannot open. The renewal runs **`udevadm control --reload-rules`, NEVER `udevadm trigger`** — the analogue of „daemon-reload, never restart": a reload makes the rule set known, a trigger REPLAYS add/change events on already-enumerated devices, i.e. on tty nodes a mid-lesson serial session is holding. A failed reload is non-fatal. `setup.sh` may and does trigger — nothing is live at provisioning time; that asymmetry is deliberate.

  **The repair only ever REPLACES, never CREATES — a live constraint on the next release that adds a system file.** `_drifted_in` (and `_compose_drifted`) skip any name whose SHIPPED or INSTALLED side cannot be read, because absent proves nothing — so a NEWLY ADDED unit or udev rule reaches nobody: only `setup.sh` creates them and that needs a source checkout no classroom has, while the release-artifact gate happily confirms the new file is in the tarball. Adding a name to `SYSTEMD_UNIT_NAMES`/`UDEV_RULE_NAMES` is delivery to the NEXT provision only. Treat any new system file as undeliverable to the fielded fleet until create-vs-replace is settled — that question is OPEN and has no owner (see `docs/KNOWN-ISSUES.md`).

  `.s6-keep` stays OUT of the repairable set and cannot join it (0 bytes, empty blob, one commit in its history — a byte compare has nothing to find). It is still REQUIRED on disk (the compose bind-mounts it and Docker auto-creates a missing mount target as a DIRECTORY, refusing every server start), so `setup.sh` CREATES it when there is no source `docker/` dir instead of `die`ing — that `die` sat at step 6 of 10 under `set -euo pipefail`, one statement after the compose install logged success, so a tarball-only provision aborted before `.env` seeding, the image pull and the unit install, leaving the Pi with no agent at all.

  **Every MUTATING pi-agent endpoint acquires `_lifecycle_lock` with a bounded `acquire(timeout=_LIFECYCLE_LOCK_WAIT_S)` and answers a German 503 on failure — never a blocking `with`**: „Umgebung starten" holds that lock across a resilient image pull and nginx's `proxy_read_timeout` is 3600 s, so a blocking „Stoppen" froze the entire wizard for up to ~50 min behind the start it was meant to interrupt. `_LIFECYCLE_LOCK_WAIT_S` is DERIVED from `_PREVIEW_HANDOFF_TIMEOUT_S` (+1 s) since `stream_camera_preview` legitimately holds the lock across its handoff. Background workers (`_run_update_job`) keep the blocking form. Lock order stays one-directional. `start_robot_tier` pulls with `attempts=1` (it runs on the request thread); the update path keeps the patient budget. `UPDATE_CHECK_TTL_S=600` is paired with `_UPDATE_CHECK_FORCE_MIN_INTERVAL_S=30` and an Origin check on `force`, because `?force=1` bypassed the TTL entirely and a no-cors GET sends no Origin — a looping page turned the Pi into an amplifier against the cloud `/version`.

- **The Pi wizard is PROFILE-AWARE end to end, and every new key is additive so an un-updated Pi is byte-unchanged.** `GET /status` gained exactly three keys — `robot_type` (the VALIDATED on-disk id), `robot_profiles` (`[{id, display_de, scan_requires_leader, camera_roles}]`) and `hardware_ready` — and `POST /robot-type` is the ONLY route added. `hardware_ready` is the profile-aware start gate (`_hardware_ready`: follower present, plus a leader only when `scan_requires_leader`, plus every arm it uses being of the profile's own ARM FAMILY). **`arms_identified.both` stays exactly as it was** because it answers a DIFFERENT question — are two arms present — and a follower-only rig is fully ready with it `false`, which is precisely why `omx_follower` and `edu6_studio` were both unstartable on a Pi. Enforced on BOTH sides (`SystemPage.js` `canStart`, and again in `handle_environment_start`; the React gate is UX, not the fence).

  **Graceful degrade is load-bearing and takes both halves**: an agent predating this work sends none of the keys, so `robot_profiles` → `[]` (selector hidden, never crashed — a non-string `display_de` would throw „Objects are not valid as a React child" and white-screen the Pi's ONLY repair surface, hence rows are FILTERED not trusted), `scan_requires_leader` is read as `!== false` (only an EXPLICIT false hides the Leader tile), and an absent `hardware_ready` falls back to `armsBoth`. The selector is frozen exactly where the GUI greys its combobox: while the robot tier RUNS and in cloud-only mode.

  **The scan card DELIBERATELY diverges from Windows and must not be re-synced**: heading, button and pill go SINGULAR on a leader-less profile („Arm scannen" / „Arm erkannt") and the Leader tile is HIDDEN rather than disabled, with the survivor renamed „Roboterarm" — the Pi card sits beside labels the Windows card lacks, so a permanently empty „Leader —" made a Roboter-Studio kit look half-broken. The GUI stays plural everywhere (`gui_app.py::btn_scan_leader`, „Arme scannen").

  **Three scan outcomes, three status codes, and the split is not the obvious one**: a WRONG-FAMILY arm yields **404**, not 409 — the by-id filter is family-scoped so the wrong-family arm never reaches the prober, both slots come back `None`, and the generic „Kein Arm gefunden" is REPLACED by the German cross-family sentence naming the mismatch; genuinely nothing found keeps that generic 404; and **409 means right family, wrong arm within it**, where the message NAMES the arm that answered rather than sending a student hunting a cable.

  **Camera roles are PROFILE-SCOPED on the Pi, enforced twice, and are the one place the two platforms genuinely disagree.** `camera_roles` is an ALLOWLIST, not a hint: `edu6_studio` declares `('scene',)` and the server's `config/edu6_studio_config.yaml` backs that with exactly one camera topic, so a camera named `gripper` publishes a topic nothing subscribes to — **and nothing downstream notices**, because the opi compose healthcheck greps `/${CAMERA_NAME_1:-gripper}/image_raw/compressed`, i.e. the very topic the student just NAMED. It goes green, the start reports success, and the failure surfaces later as an empty Roboter Studio. Both OMX profiles carry both roles (in opposite ORDER — the order is for the Windows `camera_roles[0]` default, the Pi tests membership), so the whole behavioural delta is one cell: `edu6_studio` + `gripper`, refused. Enforced in BOTH halves deliberately: the row on `/status.robot_profiles[]` carries `camera_roles` and `SystemPage.js` filters its `<option>` set from it, AND `handle_cameras_roles` re-checks it server-side with a German 400 — a stale cached bundle still offers the wrong role, and a hand-crafted POST bypasses the SPA. Two degrade rules: an agent sending no `camera_roles` yields BOTH roles rather than an empty `<select>`, and the `<option>` ORDER comes from the SPA's own list, never the wire. The `<select value=>` is deliberately NOT narrowed — a stale role leaves a value with no matching `<option>` and HTML's own selectedness algorithm picks „— Rolle —"; `handleSaveRoles` is the real fence.

  `handle_cameras_roles` requires an EXPLICIT role on every camera with NO lone-camera auto-assign, while `gui_app.py::_on_cameras_changed` still auto-assigns a single camera the profile's `camera_roles[0]`. Same field, opposite policy — a doctrine difference, not a live/inert one. **No lockstep test ties the two platforms' camera-role behaviour together in either direction** — a known, accepted, unguarded twin divergence.

  The two `fast_rehydrate_arms` twins (`gui/app/device_manager.py`, `pi_agent/identify_arm.py`) are signature-locked by `robotis_ai_setup/tests/test_arm_scan_twin_lockstep.py` after the Pi twin briefly ordered `arm_family` third and `require_leader` fourth — a third POSITIONAL argument then meant opposite things per platform, invisible to both platforms' own suites. The bodies are deliberately NOT asserted: only the call CONTRACT has to agree. That test carries an explicit zero-file floor (>100 `.py` files parsed AND ≥2 call sites found) because its caller check would otherwise be vacuously green after a directory move.

- **Crossing ARM FAMILIES invalidates a scan — on BOTH platforms.** `_hardware_ready` judged PRESENCE only, so the Modus dropdown alone could arm „Umgebung starten" for a bringup against the wrong servo bus (an OMX-scanned Pi switched to `edu6_studio` answered `hardware_ready: True`, wrote a ROBOTIS OpenRB-150 as the `FOLLOWER_PORT` of a Feetech rig, and let the start through into a ~300 s `service_healthy` block ending in a generic German failure whose real reason lives in the CONTAINER's stdout). **NOTHING new is persisted**: the scan only ever stores a by-id path that matched that family's `_ARM_MARKERS`, so the recorded PORT *is* the family tag, and `rehydrate_hardware` reads it back out of the `.env`. The reading is the twin pure predicate `serial_path_family_conflict` (`gui/app/device_manager.py` + `pi_agent/identify_arm.py`), fenced by `robotis_ai_setup/tests/test_arm_family_conflict_twin_lockstep.py`.

  **It refuses only on PROOF, and all three fail-open branches are load-bearing**: a path matching the family we need is fine whatever else it also matches; a path matching NO family means `_EDU6_BYID_MARKERS` (an admitted six-way guess) is incomplete, not that the arm is wrong; and a FAMILY with no markers is unjudgeable rather than universally conflicting, because the fail-CLOSED reading turns one forgotten checklist line into a permanently unstartable profile. That last fail-open is paired with a CI assertion that every registry family HAS markers on both platforms — **add a family to `ROBOT_PROFILES` and you must add it to both `_ARM_MARKERS` copies.** `arms_identified` is deliberately untouched. The **Pi's eager `.env` write** (`_persist_env_if_ready`, which Windows lacks) SKIPS on a conflict rather than emitting a wrong-family port, leaving the LAST COHERENT scan in place; CLEARING the ports was rejected because it would destroy a valid OMX scan the moment a student merely looked at the other dropdown entry.

- **HuggingFace token is set ONCE in the GUI (Schritt D), lives in the host `.env`, and is BOUND to the PC it was entered on.** `config_generator.write_hf_token` is the GUI's sole writer (both Schritt D and the „Umgebung starten" persist path; `upsert_env_var` is the underlying primitive but a GUI call site using it directly stores an UNSTAMPED token — an AST guard in `test_gui_install_lifecycle.py` refuses that). The token is deliberately NOT a managed key, so it survives every regenerate AND Factory Reset / volume wipes (Factory Reset removes the three docker volumes and never touches the `.env`). Compose forwards `HF_TOKEN=${HF_TOKEN:-}` on `physical_ai_server` (keep it in that `environment:` list). There is NO token UI in React — re-adding one is a regression. The GUI redacts it (and any TOKEN/SECRET/PASSWORD/KEY key) when echoing the `.env` to the Protokoll; the server has a `_BearerTokenScrubber` logging filter for the same reason.

  **`%LOCALAPPDATA%\EduBotics\` TRAVELS, so the token is fingerprinted.** The same directory that motivated the `ROS_DOMAIN_ID` derivation is carried to another PC by a roaming profile, an FSLogix container, AppData redirection, or a golden image captured after a first launch — and it holds `HF_TOKEN`, which compose forwards, so a copied profile uploaded one student's recordings under another's account. `write_hf_token` stores `HF_TOKEN_MACHINE` = `sha256(_read_machine_id())` beside it — **the SAME machine-identity notion `ROS_DOMAIN_ID` uses, never a second one**; a hash, because the `.env` is the artefact support collects. `HF_TOKEN_MACHINE` is UNMANAGED too, which is the mechanism: the pair travels together, so the copy carries the ORIGIN's stamp. `MANAGED_KEYS` is therefore unchanged, and nothing forwards the stamp into a container.

  Enforced in TWO halves that do different jobs. `bind_hf_token_to_this_machine` (called from `gui_app.py::__init__` BEFORE `_build_ui`, so Schritt D's status label reports the token as absent and re-prompts) DELETES a foreign token from disk and reports it in the Protokoll — ignoring it is not enough, because an unmanaged token stays in the file for compose to forward. `_read_unmanaged_lines` additionally never CARRIES the pair forward, which makes "a foreign token cannot reach `HF_TOKEN=${HF_TOKEN:-}`" true by construction for every generator caller, including `gui_app.py::_rs_set_leader_mode`, which regenerates at RUNTIME on the `:8769` control-server thread and never passes through startup. On the FOREIGN path the token is written first and the stamp second — reversed, a crash between the two writes leaves an unstamped foreign token that the adopt branch would claim.

  `hf_token_is_foreign` is the ONE predicate both halves ask, and it refuses on PROOF only. **An ABSENT stamp is LEGACY, not foreign** — every install in the field has a token and no stamp, so reading absence as a mismatch would re-prompt Schritt D on 100 % of the fleet. **This is the OPPOSITE call from the deleted `ROS_DOMAIN_ID` cache**, whose legacy handling was simply to re-derive, and the asymmetry is the reason: re-deriving a domain id costs nothing, while re-prompting costs every student a trip to huggingface.co. Do not harmonise them. An unresolvable fingerprint (registry probe fails; every non-Windows host, i.e. the whole deps-free suite) also keeps the token. **One-variable opt-out: `EDUBOTICS_HF_TOKEN_ANY_MACHINE=1`** — for a school deliberately baking ONE service account's token into a golden image, which the fingerprint would otherwise make re-prompt on all 30 clones. It gives up the protection ENTIRELY (a profile copied from a student's PC is accepted just as readily) and must stay set on the clones. The Pi needs none of this: `/etc/edubotics/.env` is machine-local and cannot roam.

Judging an already-torqued arm was a false alarm that BROKE JOGGING. The judged set is EVERY joint, not a "full-circle" subset — such a subset misses joint2 `hi` and joint3 `lo`, whose windows touch a register end. Compared against the EEPROM-CLAMPED goal. BLANKET, never a derived subset. `rad_to_tick` stays a plain register-range map (a future non-command caller must not inherit a command-only clamp); an AST test pins both caller sets. **`_seed_goal_from_present_locked` is deliberately EXEMPT** — it writes `Goal = Present` from a MEASURED tick to hold a limp arm still, so clamping it would COMMAND a real move at the instant torque arrives. ## Roboter Studio (layer 9) — consolidated reference

### Calibration (3 steps + optional check; wizard in `CalibrationWizard.jsx`)

- **Per-rig ChArUco intrinsics are MANDATORY — 20 frames** (`INTRINSIC_FRAMES_REQUIRED=20`), solved with `CALIB_RATIONAL_MODEL` (8-term — the ~102° wide lens overwhelms the 5-term default). Factory-default seeding is DELETED (never re-add): a guessed focal length scales every projected XY and the touch-off only fixes height. Any YAML with `source == factory_default` is skipped by both the manager and the runtime loader.
- **Scene extrinsic („single shot" to the student, a BURST in code)**: board against the 3D-printed L-jig → `EDUBOTICS_EXTRINSIC_BURST_FRAMES` (8) reads ~60 ms apart, ≥4 must pass per-frame gates → MAD outlier rejection → SO(3) chordal-mean. Per-frame solve: ChArUco `matchImagePoints` → **`cv2.SOLVEPNP_SQPNP` + `solvePnPRefineLM`** (ITERATIVE only as exception fallback; NOT `IPPE_SQUARE`) → compose with the jig-known `T_board_to_base` (yaw from `EDUBOTICS_BOARD_YAW_DEG`); hard reprojection/corner gates + an orientation sanity gate (`_check_extrinsic_orientation`: optical axis must hit the workspace region, camera must look DOWN) — which CANNOT catch a 90°/180°/mirror error; that's the ground-truth check's job.
- **Touch-off („Tisch vermessen")**: torque-off, student taps ≥3 spread points → FK → least-squares plane (`z_table` + tilt); gates reject near-collinear/high-residual captures (`TABLE_TOUCH_MIN_MINOR_M=0.015`, residual ≤0.008, camera cross-check 0.12 m).
- **DUAL Z-KEY CONVENTION (don't conflate)**: `board_table_z` = camera-side table SURFACE height written by the extrinsic solve (the projection plane); `z_table` = MEASURED end-effector grasp height written ONLY by the touch-off (the descend target). **There is NO `z_table=0.0` fallback anywhere** — missing touch-off → grasp/`mark_destination` refuse in German („Tisch vermessen"). Never reintroduce it.
- **Optional ground-truth XY/yaw check („Genauigkeit prüfen")**: known-placed vs detected points → closed-form 2D similarity fit (`fit_xy_correction`, Umeyama) + circular-mean yaw bias, persisted as `xy_correction`/`yaw_bias_rad` inside the extrinsic YAML and applied live in perception. A mirror fit (`det(R)<0`) is REFUSED and persists nothing.
- `EDUBOTICS_FORCE_RECALIBRATION` (default ON) reports calibration as ABSENT until a touch-off completes in the current boot; a rig can opt out with `=0`.

## Recording, data, inference (physical_ai_server)

- **EVERY client-supplied path from the rosbridge is confined by `data_processing/dataset_paths.py`, and "dataset path" is NOT the boundary.** The Daten tab has no auth gate and the whole surface is untrusted. `confine()` judges where a path LANDS, never how it is spelled — `resolve()` (not a `'..'` scan), symlinks FOLLOWED, both sides resolved, ancestry over path COMPONENTS (so `<root>-evil` is outside `<root>`), non-str refused rather than coerced. Three primitives: `safe_child` (ONE component, e.g. an HF user id), `safe_under` (multi-component under one root), `confine_any` (under ANY of several roots; an empty root list REFUSES rather than allowing all). Four root sets, and they are NOT interchangeable — `dataset_root()` (edit/delete/read), `browsable_roots()` = datasets + models (the file browser and HF upload), `policy_roots()` = `model_root()` + `hf_hub_cache_root()` (inference; the hub cache is where `get_saved_policies` actually finds policies, so the browsable pair would refuse every real policy), and `MODEL_ROOT_RELATIVE` as the single source of truth three sites read (`training_manager.get_weight_save_root_path`, `download_huggingface_repo`, React `paths.js`) after they drifted into three disagreeing paths.
  - **The framing is the recurring bug, not the code.** A sweep scoped to "dataset paths" walked past `get_training_info_callback` (a MODEL path), then past `ControlHfServer.local_dir`, `GetDatasetInfo.dataset_path` and `TaskInfo.policy_path`. `local_dir` was the worst: `upload_huggingface_repo` opens with an `shutil.rmtree` of `<local_dir>/.cache`, so `/root` deleted every dataset AND the HF token while the student saw an unrelated German sync error (measured in the shipped image). **Confine by ARRIVAL FROM THE WIRE, never by what the parameter is called.**

- **Sign-out is ONE primitive: the `utils/signOut::signOutStudent` THUNK, and everything LOCAL completes before the one REMOTE call.** Order: `features/jetson/sessionReset::resetJetsonOnLogout` (needs the still-valid JWT, and both it and the claimed `jetsonId` come from `getState()` — no caller threads them in) → `dispatch(signedOut())` → storage scrub → awaited `supabase.auth.signOut()` → the scrub AGAIN → reload. **The single `await` is a WINDOW**, not a boundary: every timer, socket callback and pending promise in the document keeps running across it. With the broadcast on the far side, `auth.isAuthenticated` was still true while storage was already scrubbed, so ONE `/task/status` tick (~2 s cadence, against a revoke of hundreds of ms) re-adopted the previous student's id into Redux AND — via `setTaskInfo`'s re-persist — back into the key just deleted, and the reload re-hydrated it. Hence broadcast-first AND the second scrub. **The revoke's RETURN VALUE is read, not discarded**: `@supabase/auth-js::_signOut` returns `{ error }` and skips `_removeSession()` for any admin-signOut status other than 404/401/403 — the promise RESOLVES, nothing throws, and `sb-<ref>-auth-token` SURVIVES (a captive portal answering 502 is the classroom case; `scope: 'local'` is no escape hatch, `admin.signOut()` runs before the scope check). A reported failure — or a throw — falls back to `sessionScope::clearSupabaseSessionKeys`. **The in-memory half is ONE BROADCAST, `session/signedOut` (`features/session/sessionActions`), that every slice answers for ITSELF in its own `extraReducers`** — `auth`, `tasks`, `training`, `editDataset`, `workshop`, `teacher`, `admin`. An enumeration inside `signOut.js` is a list of "which slices hold student data" maintained by the file owning none of them, and a slice added later is invisible to it: `workshop` already was, keeping `unsavedBlocklyJson`/`selectedWorkflowId`/`restrictedBlocks` (`setActiveTutorial({id:null})` does NOT clear the toolbox restriction). It is not optional: `clearStudentScopedStorage` deletes `edubotics_userId`, but `tasks.taskInfo.userId` is what `useRosServiceCaller` sends as `user_id` on START_RECORD, and `setTaskInfo` re-persists a truthy userId on the next keystroke. **The TWO HYDRATING slices — `taskSlice` and `trainingSlice` — must reset to a snapshot-free DEFAULTS constant** (`defaultTaskInfo`, `defaultTrainingState`+`defaultTrainingInfo`) and never to their `initialState`: those two `initialState`s ARE module-load `localStorage` snapshots and would hand the id straight back, so each is spelled as a visible hydration line over its defaults. The rule stops there — `admin`, `editDataset` and `teacher` read no storage, so `() => initialState` is CORRECT for them and must not be "fixed". `training`'s handler is a KEEP-LIST with a reason per survivor (`topicReceived`/`lastUpdate` are rig facts, `cloudJobsRefreshCounter` is a monotonic nonce read by `pages/TrainingPage.js`), because enumerating what to RESET said nothing about what it silently retained. `workshop` is the one selective handler: calibration is the RIG's and stays. `sessionScope.test.js`'s reasoned exemption list has exactly THREE entries — `ros` and `ui` are DELIBERATE non-answers (rig facts; `ui.hfUserList` is the rig token's account list and is what keeps the never-signed-in recording path working), and `jetson` is on it for a different reason: it IS handled, but imperatively and as step 1, because its release beacon needs the JWT the revoke invalidates, so a reactive handler would run too late. That test derives the slice set from `store.js`'s own import map, so a slice holding NETWORK-sourced student state with no handler fails even though the storage scan can never see it. `reload: false` is passed by exactly the three paths that have just shown a German toast the student must read (`StudentApp`'s and `WebApp`'s wrong-role bounces + `useMeProfile`'s 401), counted per file by that same test; everywhere else the reload is the completeness backstop. `signOut.test.js` proves the whole property against the REAL root reducer with one DISTINCT sentinel per `STUDENT_SCOPED_KEYS` entry — a slice added later is covered for free — and `sessionScope.test.js` asserts `supabase.auth.signOut()` appears in exactly ONE non-test file (whole-file match, not line-by-line) and pins the step SEQUENCE rather than pairwise order.
- **„Abmelden" is REFUSED while an activity is in flight, and the gate needs a LIVE rosbridge for every branch.** `utils/signOut::logoutBlockReason` is the pure decision (`'task' | 'workflow' | 'calibration' | null`) and `LOGOUT_BLOCK_TITLES_DE` the German wording — three distinct texts, because one shared string would tell a student to stop the wrong thing. `StudentApp` wires it to `taskStatus.running`, `workshopSlice::selectWorkflowRunning` and `selectCalibrationHasUnsolvedCaptures`; **Roboter Studio activity is `state.workshop`, never `tasks.taskStatus`, so the gate has to ask both.** Every input is written ONLY by a rosbridge message and NOTHING clears them on a drop (`resetTaskStatus` exists and is dispatched nowhere; the watchdog writes only `heartbeatStatus`), so a socket death while the last tick said RECORDING latched the control shut for the life of the document — telling the student in German to stop a recording they can no longer reach, on the shared PC they are handing over. Gating on `heartbeatStatus === 'connected'` was chosen over clearing `running` on the disconnect edge: `running` is also read by `beforeunload`, by the InfoPanel/InferencePanel editability gates and by RecordPanel, and the server-side recorder keeps recording whether or not the browser can see it. Two traps the calibration branch avoids: `framesCaptured` LATCHES (nothing resets it on leaving a step or the page), so it is ANDed with `!calibrated` and with being on the Roboter-Studio page; and `recalibrating` is deliberately not a trigger, since nothing clears it but finishing all three steps. `calibState` is NOT read — `setCalibState` has no dispatcher in `src/`, so it never leaves `'idle'`.
- **The robot must not name a student who is not signed in.** The ROS node keeps `task_info.user_id` for the life of a task, so ONE `/task/status` tick used to restore the previous student's HF id into Redux AND (via `setTaskInfo`'s re-persist) into localStorage after a sign-out, with no user action — nothing unsubscribes on sign-out and nothing can. `useRosTopicSubscription` therefore gates the ADOPT of that ONE field on `store.getState().auth.isAuthenticated`; the rig identity (`robot_type`/`robot_profile`/`capabilities_json`) keeps flowing on the same tick. Gated on a session rather than a "just signed out" latch because the default sign-out RELOADS, which clears any latch while the robot still holds the id. Accepted cost: a student who never signs in (recording needs no cloud login) no longer inherits the id of a task started elsewhere. The „Abmelden" control itself is disabled while `taskStatus.running` (a sign-out would wipe the form while the SERVER-side recorder keeps going) and stays on screen once a handover has been started, so a declined `beforeunload` prompt cannot strand a student half-signed-out with no way to retry.
- **Lazy chunks keep heavy deps out of the entry bundle** the white-screen greps watch: `UrdfTwin` (three 0.184 + urdf-loader 0.12.7, exact pins), `CodeView`/`pythonCodeGen` (dynamic `import('blockly/python')`), all `@blockly/*` plugins.
- **Self-update**: bundle bakes `REACT_APP_BUILD_ID`; `useVersionCheck` polls `/version.json` (no-store) and reloads on a new buildId (60 s sessionStorage loop-guard; `dev` skips).
- `useMeProfile` is the single `/me` owner (401/403→signOut, 404→German, 5xx→backoff, HF auto-link from the ROS whoami Benutzer-ID); thrown API errors carry `.status` + `.detail`.
- **`supabaseClient.js` re-pushes the JWT to Realtime** (`realtime.setAuth`) at boot and on every auth event — supabase-js does NOT do it on `INITIAL_SESSION`, and without it every RLS-filtered `postgres_changes` subscription silently delivers nothing after a reload while still reporting SUBSCRIBED. `useSupabaseTrainings` additionally layers a 30 s reconciliation poll + a 6 s active-job poll that run REGARDLESS of channel status.

## Windows GUI + installer (robotis_ai_setup)

- Everything the GUI writes lives in `%LOCALAPPDATA%\EduBotics\` (`.env`, `.last_image_pull.json`, `phone-cert/` — plus a now-orphaned `.ros_domain_id` on upgraded installs, which nothing reads any more) **except the diagnostics sink, which is the machine-wide leaf `%ProgramData%\EduBotics\logs\`** — resolved by the single helper `gui/app/constants.py::diagnostics_dir()` and shared by `device_manager._diagnostics_log_path()`, `gui_app._edubotics_diag_dir()` and all SIX installer `.ps1`. It holds `install_diagnostics.log` **plus** the elevated transcripts so support gets ONE artifact: the installer is `PrivilegesRequired=admin`, so on a managed PC the elevating admin's `%LOCALAPPDATA%` is not the student's. **The LEAF is load-bearing**: the six `.ps1` grant `Users:Modify, ObjectInherit, NoPropagateInherit` on it, and `NoPropagateInherit` is not `InheritOnly` — the ACE lands on the container itself, so granting it on the PARENT let a standard user pre-create `…\EduBotics\wsl` and own `ext4.vhdx`. `import_edubotics_wsl.ps1` additionally refuses a pre-existing `-InstallRoot` that is a reparse point (junction → elevated arbitrary write). The resolver falls back to `%LOCALAPPDATA%\EduBotics` then `~` on **unwritability** (a real create-probe — `os.access` is not ACL-aware on Windows). `%ProgramData%\EduBotics\.migrated` deliberately does NOT follow the sink into `logs\`.
- Ports: web 80, camera-ingest 5557, Roboter-Studio control 8769 (127.0.0.1), phone HTTPS 8444. web_video 8080 + rosbridge 9090 are **container-internal on Windows** (the student compose publishes neither; the SPA reaches both same-origin through `nginx.conf`) and **loopback-only on the Pi** (debug via `ssh -L`).
- **Multi-line WSL scripts go through `wsl_bridge.run()`** (stdin bytes, CRLF-normalized) — `wsl.exe … bash -c "<script>"` mangles `$(...)` output containing `(`/tabs (the silent camera-discovery break). **`wsl --list --quiet` output is BOM-less UTF-16LE** — every consumer strips NULs before matching (PS scripts, `docker_manager.is_distro_registered`, `wsl_bridge`, and the `.iss` Pascal `IsDistroRegistered` — that Pascal fn was once the lone exception and silently skipped the image pull).
- **usbipd**: `Not shared` devices need an elevated `bind` first (AutoBind policies only cover future replugs) — `configure_usbipd.ps1`/`bind_devices.ps1` try three `policy add` syntaxes across usbipd 5.x patch drift. Arms are OpenRB-150 boards: VID `2F5D`, PIDs `0103`/`2202` (FTDI is only a legacy udev fallback). `fast_rehydrate_arms(require_leader=True)` trusts saved leader/follower ports (arms have distinct stable serials — identical-serial is camera-only) and returns `(None, None)` on ANY mismatch — the GUI then only PROMPTS the student to rescan. On an `omx_follower` rig `_try_rehydrate_arms` reads the profile from the `.env` and passes `require_leader=False`: a missing `LEADER_PORT` is legal, follower mismatch still fails; `_scan_arms` succeeds leader-less without routing into the diagnose/repair flow; readiness gates go through `_hardware_ready(profile)`, which is also arm-family-aware.
- **Installer PS 5.1 traps** (CI-guarded): installer `.ps1` use `$ErrorActionPreference='Continue'` + `$LASTEXITCODE` (`configure_wsl.ps1` is the one sanctioned EAP=Stop file — it makes zero native calls). Under EAP=Stop a native `wsl`/`docker`/`usbipd`/`nvidia-smi` command writing stderr becomes a TERMINATING `NativeCommandError` even on success; `ci.yml::powershell-native-stderr` enforces exactly that pairing, not a blanket EAP rule. Shipped `.ps1` need a UTF-8 BOM; `.gitattributes` pins `*.ps1` to CRLF + UTF-8.
- **Rootfs upgrade gate protects student Docker volumes**: `wsl_rootfs/ROOTFS_VERSION` is baked into the rootfs as `/etc/edubotics-rootfs-version`; both `.iss::ShouldImportDistro` (German consent MsgBox) and `import_edubotics_wsl.ps1` skip the destructive `wsl --unregister` + re-import when versions match. Both sides fail **OPEN** on an unreadable stamp: `_rootfs_rebuild_required()` (GUI) and `RootfsReimportNeeded()` (`.iss`) block only on a POSITIVE mismatch. A fail-CLOSED `.iss` made a ≤2.6.0 upgrade show a German „images do NOT fit" modal and skip the pull while the GUI pulled them onto the old rootfs minutes later. Relatedly, **`.reboot_required` is never routed on by EXISTENCE** — it means „the deferred work is not finished", which is true of every non-zero finalize exit, so both `finalize_install.ps1::Test-RebootStillPending` and `verify_system.ps1`'s `$rebootPending` discriminate on flag-mtime vs `Win32_OperatingSystem.LastBootUpTime` and prefer the FAILED direction on a read error. finalize also takes CUSTODY of the flag across its `install_prerequisites.ps1` child (snapshot + conditional restore). **Bump `ROOTFS_VERSION` whenever anything under `wsl_rootfs/` changes EXCEPT `*.md`** (`ci.yml::rootfs-version-guard`; a bump forces a DESTRUCTIVE fleet-wide re-import). Uninstall's distro wipe is consent-gated with default **Nein**; `[InstallDelete]` wipes `{app}\gui|scripts|wsl_rootfs` on every upgrade. `import_edubotics_wsl.ps1` also hard-fails on a bad/missing rootfs-tarball SHA256 sidecar and on <20 GB free disk BEFORE `wsl --import`.
- `pull_images.ps1` retries GHCR 3× before Hub and prunes superseded tags by enumeration (dangling-only `prune` misses them — the VHDX otherwise grows a full image per release). `finalize_install.ps1` is the elevated post-reboot/GUI-invoked one-button repair — idempotent and STATE-GATED: each phase trusts verified state (`Test-DistroRegistered` → `Wait-DockerReady` → `Test-ImagesPresent`), never child `$LASTEXITCODE` (the ONE meaningful child code is import's 12), and every failure exits via `Fail-WithNextAction`. Its exit code is THE contract with the GUI — `0` done / `10` reboot still required / `12` rootfs rebuild needs consent / `1` failed, mirrored as `gui_app.py::FINALIZE_EXIT_*`; `exit 0` with the distro still absent gets its own honest German handling, and that handling is TWO branches, not one — see the finalize-marker contract below. `wsl_docker_ready.ps1::Wait-DockerReady` (dot-sourced; caller MUST keep EAP=Continue) is the SOLE implementation of dockerd readiness, used by finalize, `pull_images.ps1`, `preflight_system.ps1` AND `import_edubotics_wsl.ps1`. Every dot-source is `Test-Path`-guarded (Controlled Folder Access can silently truncate `{app}\scripts`). `install_prerequisites.ps1` deliberately does NOT gate on Windows edition (WSL2 works on Home; build ≥ 22000 only). The rootfs must keep `tzdata` installed — compose bind-mounts `/etc/timezone`+`/etc/localtime` read-only into every container, and Docker auto-creates a missing mount target as a DIRECTORY. The `.iss` launches the GUI via `explorer.exe` (+ `ChangesEnvironment=yes`) so it inherits the post-install PATH; `CurStepChanged(ssInstall)` runs `docker compose down` before new files land.
- **The finalize MARKER is a three-component, two-language contract, and its ENCODING is load-bearing.** `%ProgramData%\EduBotics\logs\edubotics_finalize.marker` is a NARROWER channel than the exit code: the exit code still decides WHAT happened and the marker never picks a branch of that chain. It disambiguates exactly ONE cell — exit 0 (so finalize's own `Test-DistroRegistered` passed) while the un-elevated GUI still cannot see the distro. WSL2 registers distros PER WINDOWS USER (`HKCU\...\Lxss`) and the installer is `PrivilegesRequired=admin`, so on a managed school PC a DIFFERENT admin's `wsl --import` lands the registration in that admin's hive and no reboot can help — which is what the generic message advises. Three components must agree: `finalize_install.ps1` writes all THREE marker shapes with `-Encoding UTF8` — that pairing is what is universal — and carries `user=<name>` on TWO of them, `started <iso> pid=<n> user=<name>` and the terminal `SUCCESS <iso> user=… distro=…`; the `FAILED <iso>\n<problem>\n<next step>` shape has no `user=` field at all, so a reader must tolerate its absence; `gui_app.py::_prompt_finalize_install::_marker_user` reads it back as **`utf-8-sig`** and treats any U+FFFD in the parsed name as UNPARSEABLE rather than as a different account; `preflight_system.ps1` check 5 parses the same field for its own verdict. `%USERNAME%` may contain spaces, so the value runs to end-of-line except in the SUCCESS shape, where a reader must cut at `" distro="`. Names compare CASEFOLDED — a different account routes to the per-account German remedy, the same account or an unreadable marker falls through to the generic one BYTE-FOR-BYTE. BOTH the encoding and the cut cost a wrong accusation, and NEITHER is catchable by the U+FFFD rule. PS 5.1's `Set-Content` default is the system ANSI codepage, so a German „Müller" was written cp1252 and decoded as „M\uFFFDller"; read the other way round (UTF-8 bytes decoded as ANSI), or left uncut, it comes back as „MÃ¼ller" / „Müller distro=EduBotics" — VALID characters that simply never casefold-match `%USERNAME%`, so the per-account branch fires on the SAME account. **The two parsers are twins with only a PARTIAL lockstep**: `test_gui_install_lifecycle.py::PreflightAccountScopeTest` compares the marker PATH, the U+FFFD rule, the PS read's declared encoding and the `" distro="` delimiter across the two languages; the casefold-vs-`-ine` comparison and the `user=` key itself are still uncompared — see `docs/KNOWN-ISSUES.md`.
- Camera preview renders base64-PNG via `cv2.imencode` into `tk.PhotoImage` (Tk 8.6's binary `-data` path is not NUL-safe); previews stop before the capture bridge claims devices, before rescans, and on close. `win_camera.camera_privacy_blocked()` surfaces the Windows camera-consent registry cause.

## Cloud stack (cloud_training_api + modal_training + supabase + jetson_agent)

- **Rate limiter** (in-process, `--workers 1`): rules sorted longest-prefix-first; `/jetson/`, `/trainings/`, `/workflows` are **per-user keyed** (`jwt:<sha256(token)[:16]>` — hashed unverified token, so a forger can't starve a victim); everything else per-IP (leftmost X-Forwarded-For, safe behind Railway's proxy only). ### Build images

**Default path for the THIN images: GitHub Actions.** Push to `main` with changes under the docker paths and `docker-publish.yml` builds both arches (`:latest`). Local builds of those are dev-only (never push from a workstation):

```bash
cd robotis_ai_setup/docker
SUPABASE_URL=... SUPABASE_ANON_KEY=... CLOUD_API_URL=... ./build-images.sh   # amd64
PLATFORM=arm64 ./build-images.sh                                             # Jetson repos, skips manager
PLATFORM=opi   ./build-images.sh                                             # Orange Pi repos, incl. manager
```

**The three self-built BASES are the exception: a workstation push is their ONLY path** (Rule §6) — "never push from a workstation" governs the thin images CI owns, and has never applied to the bases:

```bash
BUILD_BASE_OPI=1   PLATFORM=opi   ./build-images.sh   # Dockerfile.arm64cpu → physical-ai-server-opi-base
BUILD_BASE_ARM64=1 PLATFORM=arm64 ./build-images.sh   # Dockerfile.arm64 → both Jetson bases
```

All three secrets are required even for a base-only build: every flavor builds the manager FIRST, and `${VAR:?}` aborts long before the base build runs.

An **image rebuild is required** whenever you touch: anything under `docker/open_manipulator/` or `docker/physical_ai_server/`, the overlay files, the entrypoint, the `physical_ai_server` package source (COPY-wholesale), or `physical_ai_interfaces` msg/srv — CI does those on a push. Touching a **base Dockerfile** additionally requires the manual base rebuild + a `PAS_BASE_IMAGE` tag bump in the same commit. Hot-deploys into a running container are ephemeral (revert on `--force-recreate`).

### Deploy

**Always via GitHub Actions** (Rule §6). Full release: bump the version (below), then

```bash
git tag vX.Y.Z && git push --tags     # fires release.yml → golden order W1→W6
```

Per-surface pushes to `main` fire the path-filtered workflow alone. **Before every tag: prove the installer builds** — `release-installer.yml` via workflow_dispatch with `version_tag` set to the PREVIOUS release (so the baked `versions.env` points at images that exist); it's the only `.iss` Pascal compile check in CI. For releases touching the upgrade path (installer scripts, `wsl_rootfs/`), install the artifact TWICE on a dev rig (first shows the German consent + re-imports; second logs „Import übersprungen" and preserves volumes).

**Bumping product VERSION = 4 in-tree sites in one commit**: `VERSION` (source of truth), `installer/robotis_ai_setup.iss` `AppVersion`, `gui/app/constants.py` fallback literal, and `pi_agent/constants.py` fallback literal. Both `constants.py` readers resolve the `VERSION` FILE at runtime — the literals are the last-resort fallback when no VERSION file is reachable. A stale pi_agent literal is the more dangerous of the two: it is what `APP_VERSION` degrades to if the packaged file goes missing, and `update_checker` compares it against the Cloud-API `/version` — a version that reads LOW re-offers the same update forever. `release.yml::version-preflight` hard-fails a tag whose name ≠ the VERSION file AND asserts all three fallback literals equal it. (The literal check is a source grep, so keep each literal a plain `return "X.Y.Z"`.) W6 then auto-flips the Railway GUI-version vars after the `.exe` is attached — no manual Railway step.

Manual emergency paths (document in a PR): `supabase db push` / `psql -f rollback/NNN_*.sql`; `modal deploy modal_app.py`; `railway up --service scintillating-empathy --environment production --path-as-root . --ci` from `cloud_training_api/`; `build-images.sh` from a clean Linux host.

## CI guardrails — `ci.yml`, 25 validator jobs on every push/PR to `main`

- **python-tests** — compileall + unittest discover over FOUR trees (`tests/`, `cloud_training_api/app/tests/`, `jetson_agent/tests/`, **`pi_agent/tests/`**) + the physical_ai_server pytest suite. Five suites in one job; the pi_agent step is ~35 s of it and is the one most easily forgotten when this list is edited. The compileall step carries a ZERO-FILE FLOOR per root (exists + ≥1 `.py`): `compileall` prints „Can't list <dir>" and exits 0, so a renamed root used to make that step vacuously green.
- **shell-lint** — shellcheck `-S error` on the 8 shipped shell scripts.
- **compose-validate** — `docker compose config` on the student+gpu, Jetson AND Orange-Pi composes (fake `.env`s) **plus the shipped `pi_agent/docker/` twin**; asserts `.s6-keep` exists and that BOTH the student and opi composes bind it and target `127.0.0.1` in the manager healthcheck (busybox-wget IPv6 regression).
- **pi-compose-twin-guard** — `cmp -s` the source-of-truth opi compose against the tarball twin. A drifted twin is worse than the bug it replaced: the agent would report in German that it renewed the compose, having written the wrong file, and its own `config -q` gate proves VALID, never CURRENT.
- **overlay-guard** — runs `fix_server_inference.py` against a synthetic upstream: asserts non-zero exit on no-op AND that the patch actually applies (catches an upstream rename sliding the regex off target).
- **modal-import-validate** — imports `modal_app.py` (NOT `training_handler.py` — container-only deps) + smoke-imports the cloud-API routes that touch the Modal SDK.
- **teacher-web-build-validate** / **manager-build-validate** / **manager-opi-build-validate** — build the three React Dockerfiles with placeholders; assert each placeholder reached the bundle (white-screen catcher); the opi variant also asserts `version.json` buildId and the `/pi-mode.json` nginx marker location.
- **tutorials-validate** — tutorial JSON + `allowed_blocks` vs the server dispatch tables + `HAT_BLOCK_TYPES` + Blockly built-ins.
- **interfaces-validate** — every `.srv` has exactly one `---`; CMakeLists ↔ on-disk cross-check.
- **nginx-validate** — `envsubst $PORT` then `nginx -t` on all THREE configs.
- **base-version-guard** — a non-comment edit to `Dockerfile.arm64cpu` / `.arm64` must move the matching `PAS_BASE_IMAGE` tag in `build-images.sh` (nothing in CI builds those bases — an un-bumped tag ships the old one, green; comment-only edits exempt).
- **env-forwarding-guard** — every `EDUBOTICS_*` read by entrypoint/start-dockerd/ingest-node/overlay `.py` must appear in a compose `environment:` list **somewhere**. Read that literally: "forwarded" is a UNION over all four shipped composes, so the guard is structurally blind to a key present on ONE target only, and to a key on the WRONG SERVICE of the right file.
- **compose-env-parity** — the per-TARGET, per-SERVICE half the union guard cannot provide: `.github/scripts/compose_env_parity.py` (stdlib-only) compares `docker-compose.yml` against `docker-compose.opi.yml` service by service. Gates KEY PRESENCE only; value diffs are `::notice` (a `PINNED-LITERAL` notice flags the sub-class where a knob the Pi `.env` cannot reach is how a documented rollback goes missing). An `INTENTIONAL` allowlist carries a written reason per divergence (today exactly one) and a STALE entry is a hard error. The parser reads ONE shape — a block sequence of `- KEY=value` under `environment:` — and REFUSES every other way a compose could carry env rather than comparing an incomplete picture. Two structural fences: `REQUIRED_ENV_SERVICES` (those services parsing to zero env entries is a failure, not an empty comparison) and service-set equality. **KNOWN RESIDUAL:** a name forwarded ONLY by the Jetson or gpu compose satisfies both guards (absent from student and opi alike, so they agree). Nothing is in that state today. The Jetson compose is deliberately out of scope.
- **powershell-encoding** — every shipped `.ps1` carries a UTF-8 BOM (German Windows decodes BOM-less as CP1252).
- **powershell-native-stderr** — no `.ps1` pairs file-level EAP=Stop with a stderr-capturing native call.
- **powershell-install-guards** — runs the four `ps_*` install-hardening guards directly so their `::error file=…,line=…` annotations land on the diff; `tests/test_ps_guard_scripts.py` pins their BEHAVIOUR against synthetic fixtures. All four refuse a zero-file scan — a directory rename used to turn every guard green having read nothing. They share `.github/scripts/_ps_lex.py`.
- **german-strings-lint** — no ae/oe/ue transliterations in `[FEHLER]`/`[WARNUNG]`/`[STOPP]` lines + AST pass over cloud-API `detail=`/`error_message=` AND pi_agent `message=`.
- **rootfs-version-guard** — any `wsl_rootfs/` change EXCEPT `*.md` must bump `ROOTFS_VERSION`.
- **enum-parity** — wire-int cross-check (`.srv`/`.msg` ↔ `taskCommand.js`/`taskPhases.js` ↔ getattr fallbacks ↔ hardcoded test ints).
- **secret-scan** — gitleaks (pinned binary, sha256-verified) over full history; benign fingerprints in `.gitleaksignore`.

### Deploy-workflow hardening invariants

- Health gates verify IDENTITY, never bare 200 (commit sha / buildId).
- **docker-publish**: native per-arch runners (amd64 `ubuntu-latest`, arm64 `ubuntu-24.04-arm`, NO QEMU; `fail-fast: false`); `jlumbroso/free-disk-space` amd64-only; `--no-cache --pull`; dirty-tree refusal; buildkit routes docker.io through `mirror.gcr.io`; smoke-test pulls the **GHCR** images, asserts arch, bundle env, amd64 **< 7 GB of UNCOMPRESSED layer bytes** (calibrated against a MEASURED 5.56 GB, ~1.26× headroom), and runs `image_source_parity.sh`. That ceiling is measured with **`docker image history --human=false`, deliberately NOT `docker image inspect .Size`** — `.Size` means different things per image store (uncompressed layer diffs on classic overlay2, **COMPRESSED** under the containerd snapshotter, where the same image reads 2.626 GB instead of 7.53 GB), and under the compressed reading the gate is INERT rather than merely loose: a CUDA-back image compresses to ~5.6 GB and would pass any uncompressed-calibrated ceiling. `history` is uncompressed on both stores, so the gate no longer depends on the runner. The opi ceiling stays 11 GB on `.Size` and is deliberately NOT synced — the opi image was never CI-measured (locally 4.58 GB uncompressed, ~2.4× slack, so it survives either reading); tightening it without also moving it to `history` would make it silently store-dependent. Tag set: `:latest` (main), `:<sha>`, `:<short-sha>`, and on tags `:X.Y.Z` + `:X.Y` (both ALWAYS re-pointed on both registries). GHCR retags fatal, Hub best-effort (a Hub 429 warns, never fails the release).
- **Concurrency semantics differ per workflow**: `ci.yml` cancels in-flight PR runs (never main); `docker-publish.yml` never cancels (non-atomic pushes) and runs TWO lanes — a per-tag release lane vs one shared `main` lane, keyed on `github.ref` (**NOT** `github.event_name`, which inside a reusable workflow reports the CALLER's event and would collapse both lanes); a single static group let a third queued `main` push evict a release's PENDING W4 mid-release. `release.yml` cancels on a newer tag; `supabase-migrate.yml` serializes on a project-scoped group. Job timeouts encode real budgets: docker build 60 min, retag 45 min, installer 90 min.
- **Caller-permissions-superset rule**: `release.yml` grants per-job permissions and each caller job must superset its callee's declared permissions or GH `startup_failure`s the run. Change both in one PR.
- Every checkout: `persist-credentials: false`. All third-party actions SHA-pinned. Template injection defused via env indirection. Inno Setup pinned 6.7.0. `softprops/action-gh-release` needs the explicit `token:` under `workflow_call`.
- **Secrets consumed by CI** (10 + auto `GITHUB_TOKEN` + repo var `SUPABASE_BRANCHING_ENABLED`): `DOCKERHUB_USERNAME/TOKEN`, `RAILWAY_TOKEN`, `SUPABASE_ACCESS_TOKEN/DB_URL/PROJECT_REF/URL/SERVICE_ROLE_KEY/ANON_KEY`, `REACT_APP_CLOUD_API_URL`. `MODAL_TOKEN_ID/SECRET` are NOT used by any workflow — they exist for the operator's manual `modal deploy` only.
- Supabase PR-branch flow is gated behind BOTH the dashboard Branching feature (Pro+) and repo variable `SUPABASE_BRANCHING_ENABLED=true`; unset → both jobs skip green.

## When to ask the user

Act autonomously on: reading files, editing code with low blast radius, running local tests/lints, building images locally, spawning sub-agents for research.

**Ask first** for:

- `git push` (and never force-push to `main`)
- `wsl --unregister EduBotics` (destroys VHDX → volumes `ai_workspace`, `huggingface_cache`, `edubotics_calib` gone)
- `docker compose down -v` or `docker volume rm` of `huggingface_cache` / `edubotics_calib`
- Force-push, `git reset --hard`, `git clean -fd`, `--no-verify`
- Modal `cancel` on a running training (charges credit)
- `supabase.auth.admin.delete_user` calls
- Rotating production secrets, editing CI/CD config
- Changing safety-critical paths (torque-disable, sync-verification tolerance, ownership assertions, Dynamixel current limits, the manual-mode arbiter/lock order, collision gating, the edu6 torque-on guards, `LINK_RADIUS_M + ZONE_MARGIN_M`)
- Renaming files other layers reference (overlay targets, ROS topics, env var names, RPC signatures)
- Touching `start_training_safe` / `get_remaining_credits` / `adjust_workgroup_credits` semantics (workgroup credit pool is load-bearing; regressions are silent over-spend or refused trainings)
- Reintroducing software-side inference safety guards (Rule §2)

## Spec-before-code for multi-layer features

Any feature touching **more than one of the 10 layers** gets a one-page dated spec+plan in `docs/plans/` BEFORE the first commit, with an explicit **"Non-goals (this round)"** section carrying trigger conditions. `docs/plans/` is **gitignored and throwaway** — delete the page once the feature lands. Durable invariants graduate into THIS file; dated narratives go to `docs/CLAUDE-CHANGELOG.md`; living status goes to `docs/KNOWN-ISSUES.md`; the plan never claims to be authoritative.

## When in doubt

The single source of truth is **the code**. This file describes invariants at the time it was written. Verify against `git log` and the current file when stakes are high. If this file disagrees with the code, fix this file in the same change — the whole point is that it stays in sync.

When you find an obstacle, **find the root cause** instead of bypassing it (never `--no-verify`, never `@pytest.skip`, never short-circuit an `apply_overlay` sha256 assertion that's telling you upstream renamed something).
