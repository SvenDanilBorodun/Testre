## What this is

**EduBotics** — a vertically integrated educational stack for teaching Physical AI on **ROBOTIS OpenMANIPULATOR-X** arms to **German-speaking students**. Student lifecycle: install `.exe` → setup wizard → record demos (ROS 2 teleop) → train policy (Modal cloud GPU) → inference (local or classroom Jetson) → optional **Roboter Studio** (Blockly authoring + AprilTag-marker perception + manual arm control).

Students run Windows 11 PCs (no GPUs). Training runs on Modal (NVIDIA L4; A100 for VLA policies). The product ships as a single `.exe` that installs a bundled WSL2 Ubuntu 22.04 distro named `EduBotics` containing Docker Engine + three containers — **no Docker Desktop**. Images are pulled from **GHCR (primary) with Docker Hub fallback**. A teacher/admin web dashboard is a separate Railway deploy. Installs are online-only (the offline bundle path was removed in v2.8.2).

Single git repo, no submodules. ROBOTIS upstream (`open_manipulator/`, `physical_ai_tools/`) is absorbed as plain directories.

## Six non-negotiable rules

These exist because we paid for the lesson. Don't undo without explicit user agreement.

### 1. German UI / English code

- **German** for everything a student/teacher/admin reads: tkinter labels, React UI, `detail` fields on API errors, log strings users see, toast messages. Use literal `ä ö ü ß` (some legacy files use `Schueler`; new code uses `Schüler`).
- **English** for everything the maintainer reads: code, comments, docstrings, internal log lines, JSON keys, function names, commit messages.
- CI guards: `german-strings-lint` (transliterations in `[FEHLER]`/`[WARNUNG]`/`[STOPP]` lines + an AST pass over cloud-API `detail=`/`error_message=`; `# english-ok` is the escape hatch).

### 2. Hardware safety lives in xacro + entrypoint, not software overlays

Software-side inference safety envelopes (NaN/Inf guard, joint clamp, velocity cap, stale-camera halt) were removed deliberately in the 2026-05 stripdown to fix recording↔inference asymmetry. Inference runs upstream `predict()` raw. The remaining protection is hardware-enforced or warning-only:

- **Xacro Dynamixel limits** (`omx_f.ros2_control.xacro`, `omx_l.ros2_control.xacro`): restrictive position limits exist ONLY on dxl12/dxl13 — dxl11 (Op Mode 4) and dxl14/15 are full-register-range, and the leader xacro has NO position limits at all (it is torque-free). The real safety floor is the gripper current limits (follower dxl16 `Current Limit 350` + `Goal Current 350` + `Shutdown 21`, Op Mode 5; leader trigger 300 mA).
- **ros2_control YAML**: 100 Hz; JointTrajectoryController in-flight `trajectory` tolerance 2.0 rad (effectively off — the safety floor is the Dynamixel current limit, not the controller tolerance), `goal` 0.10 rad arm / 0.50 rad gripper, `goal_time` 5.0 s. These were bumped from upstream's tight values on 2026-05-18 because the upstream values aborted the 3 s quintic boot-sync mid-flight → compose restart-storm (see the inline comment in `overlays/omx_f_hardware_controller_manager.yaml`).
- **Torque-disable on shutdown** in `docker/open_manipulator/entrypoint_omx.sh::disable_torque()` — registered as `trap … SIGTERM SIGINT EXIT`, so `set -e` aborts (which exit via `exit`, not a signal) are covered too. The leader path uses the namespaced `/leader/omx_l/set_dxl_torque`.
- **Phase-3 post-sync verification** in `entrypoint_omx.sh` (the script's own phases: 1 leader, 2 follower, 3 quintic sync + verify, 4 cameras) — 0.30 rad tolerance, arm joints only, soft-fail `[WARN]` (a hard exit looped compose restarts). Requires ≥50 % of commanded delta traversed to distinguish a dropout from finishing lag. Two hard-exit paths remain: the camera-disambiguation guard (exit 3) and `wait_for_device()`'s 60 s serial-port timeout (exit 1).
- Recording-side QUALITY guards (stale camera, camera-Hz deficit — warn threshold 0.9×fps) are warning-only; but a topic-availability timeout, a msg-conversion error, or an add_frame failure (the `record()` call is exception-guarded — an uncaught raise would kill the whole node) hard-stops the recording timer, and the streaming frame-drop guard DISCARDS the in-flight episode and re-records it (no retry cap) — the session completes, that attempt doesn't.
- **The leader ARM JOINTS 1-5 are torque-free/limp by design** — no gravity compensation is spawned (`Torque Enable 0`, Goal/Present Current interfaces commented out in `omx_l.ros2_control.xacro`; broadcasters only for those joints). The leader GRIPPER TRIGGER is NOT limp: `trigger_position_controller` (`position_controllers/JointGroupPositionController`) + a 50 Hz `ros2 topic pub` of −0.7 rad simulate spring resistance under the 300 mA current cap. The `docker/open_manipulator/Dockerfile:51` "enable gravity compensation" comment is stale, and so is `collision_monitor.py:50`'s claim that the gravity-compensation controller consumes `/collision_flag` (it is never spawned) — the xacro + launch files are the truth.

**ONE sanctioned exception (user-approved): the teleop force/collision e-stop** — scoped to teleop/recording ONLY. It is gated OFF during inference (inside the detector via `mode_is_inference`), and gated OFF during workflow and manual mode (in `collision_monitor.py` — one combined `if on_workflow or on_manual` gate; the manual-mode half is the one sanctioned Rule-§2 scope change from v2.11: follower-only Roboter Studio has no leader and hand-guiding presses the arm at ~0 velocity, indistinguishable from a collision). It never modifies samples — a trip DISCARDS the in-progress episode, it does not filter or clamp. Full mechanics under "Critical architectural choices".

If you genuinely need to reintroduce any OTHER software safety guard that modifies the pipeline, **stop and ask the user**.

### 3. The shipped image must reflect the repo — physical-ai-server is COPY-wholesale; open-manipulator still overlays

**physical-ai-server: COPY-WHOLESALE, no overlays.** The image's `physical_ai_server` package is a verbatim copy of `physical_ai_tools/physical_ai_server/` (staged as `pkg_src/` by `build-images.sh` — excluding `test/`, the three base Dockerfiles (`Dockerfile.amd64`/`.arm64`/`.arm64cpu`), `CHANGELOG.rst`, bytecode — then `rm`'d + `COPY`'d + re-`colcon`'d). "Image == repo HEAD" is true by construction: edits, new files AND deletions all propagate. The old overlay model silently dropped edits (the v2.5.0 `training_manager.py` regression → node crash). The Dockerfile asserts the stripped `safety_envelope.py` AND the dead `training/trainers` + `evaluation` trees never re-enter (`build-images.sh` re-checks the staged `pkg_src/` independently before the build), and four build-time smoke gates must pass: policy imports + `CODEBASE_VERSION == 'v3.0'`, node import, `control_msgs` gpio import, and a functional cv_bridge rgb8 decode.

**open-manipulator: STILL the overlay model.** `apply_overlay()` in `docker/open_manipulator/Dockerfile` does sha256 pre/post verification over the **7-file** chain (`omx_f.ros2_control.xacro`, `omx_l.ros2_control.xacro`, `omx_f_follower_ai.launch.py`, `omx_l_leader_ai.launch.py`, both controller-manager YAMLs, `camera_usb_cam.launch.py`); build aborts on a missing upstream target. Kept (not converted) because open_manipulator contains C++ `ros2_control` packages where a full re-`colcon` is heavy/risky. When adding an open_manipulator overlay you **must** add it to the chain with a unique path filter — without that the source edit never reaches the image. Standalone scripts (`identify_arm.py`, `camera_ingest_node.py`, `calibrate_collision_currents.py`) are plain `COPY`s, not overlays.

**Both are guarded by `image-source-parity`** (`.github/scripts/image_source_parity.sh`, run per-arch in `docker-publish.yml::smoke-test`): physical-ai-server asserts byte-identity (`diff -r`); open-manipulator asserts every overlay present by sha256. The parity script mirrors `build-images.sh`'s staging exclusions — change one, change both (the exclusion list also drops `Dockerfile.arm64cpu`; the `-opi` flavor rides the same flavor-neutral gate).

LeRobot itself is **not** overlaid — pip-installed from PyPI at `0.5.1` (Rule §5). `patches/fix_server_inference.py` is retained ONLY so CI `overlay-guard` can test the patch harness — it does nothing for the current build.

The server **amd64 BASE image is pulled, never built** — `build-images.sh` resolves `robotis/physical-ai-server:amd64-0.8.2` via `docker manifest inspect`; only the arm64 base has a build trigger (`BUILD_BASE_ARM64=1` → `Dockerfile.arm64`). `Dockerfile.amd64` is forward-compat scaffolding (keep its pins in lockstep anyway, Rule §5).

### 4. Service-role key bypasses RLS — authorization is your job

Every Supabase query in `cloud_training_api/app/` runs as **service-role** via `app/services/supabase_client.py::get_supabase()` (lazy singleton, fails fast at startup if secrets empty). RLS policies exist for defense-in-depth (anon-key/Realtime read paths) but are dormant under service-role.

Every endpoint that touches another user's data **must** call one of the ownership asserts (the teacher/workgroup/workflow helpers raise a German 404 — never 403 — to avoid existence leakage; the Jetson pair deliberately differs: `_assert_classroom_member` raises 403 (membership gating, not resource existence) and `_assert_jetson_owner` raises 404-or-**410 „Lock verloren"** to signal a lost claim; `_assert_workgroup_in_classroom` can also 400):
- `_assert_classroom_owned` / `_assert_student_owned` / `_assert_entry_owned` / `_assert_workgroup_in_classroom` (in `routes/teacher.py`)
- `_assert_workgroup_owned` (in `routes/workgroups.py`)
- `_assert_workflow_owned` (write) / `_assert_workflow_visible` (read ladder: owner OR group sibling OR classroom template) (in `routes/workflows.py`)
- `_assert_classroom_member` / `_assert_jetson_owner` (in `routes/jetson.py`)

**One missed assertion = silent IDOR.** RLS will not catch it. Writes additionally re-scope the query (`.eq("owner_user_id", …)`) as belt-and-suspenders. Dataset registration is enforced atomically in Postgres instead: `register_dataset_safe` RPC (migration 026, `FOR UPDATE` on the caller's users row, HF-author anchor, P0034 → 403). The workflow read-visibility ladder is implemented FOUR times in `routes/workflows.py` (`_assert_workflow_visible`, inline in `list_workflows` + `get_workflow`, ad-hoc in `clone_workflow`) plus near-twin resolvers in `services/workgroups.py` — semantics changes must touch every copy.

The Modal worker uses the **anon key** + per-row `worker_token` (UUID). Its only DB write surface is the `update_training_progress(p_token, …)` RPC, guarded by the terminal-state `WHERE status NOT IN ('succeeded','failed','canceled','cancel_requested')` clause (migrations 010 + 032) — a late worker write is a P0001 no-op, and that P0001 is also the worker's in-band cancel signal (it kills the training subprocess, freeing the GPU). RPC GRANTs are asymmetric by design: `update_training_progress` is granted anon+authenticated (the worker), `register_dataset_safe` is service-role-ONLY. `update_training_progress` is deliberately absent from the boot schema probe (its defaulted 8-arg signature is overload-ambiguous) — drift there is invisible to `/health`.

### 5. Don't introduce drift between the LeRobot pinning sites

The LeRobot **version pin `0.5.1`** must agree across:
- `robotis_ai_setup/modal_training/modal_app.py` constant `LEROBOT_VERSION`
- `physical_ai_tools/physical_ai_server/Dockerfile.amd64` (`pip install "lerobot[pi,smolvla,peft]==0.5.1"` — the extra is `pi`, not `pi0`)
- `physical_ai_tools/physical_ai_server/Dockerfile.arm64` (same line under the Jetson AI Lab pip index)
- `physical_ai_tools/physical_ai_server/Dockerfile.arm64cpu` (Orange Pi 5 Pro CPU base — stock `ros:jazzy-ros-base`, plain PyPI; same `lerobot[pi,smolvla,peft]==0.5.1` line, but torch is PINNED EXPLICITLY (`torch==2.7.0` + `torchvision==0.22.0`) **before** lerobot because this base inherits no torch and `lerobot 0.5.1` allows `torch<2.11` — an unpinned resolve pulls 2.10.x and breaks the one-torch-2.7.x surface; replicates the `numpy==1.26.4` + `scipy>=1.14.0,<1.18` caps below)

(The thin overlay `docker/physical_ai_server/Dockerfile` carries the same install and is what CI actually builds on top of the pulled base — keep it in lockstep too.) Bumping LeRobot is a **one-PR multi-site change**. `meta/info.json` `codebase_version: "v3.0"` and the Modal preflight `EXPECTED_CODEBASE_VERSION="v3.0"` (`training_handler.py`) are **derived** consts that move together with the pin.

**Hard dependency caps — never widen silently:**
- `numpy==1.26.4` force-reinstalled AFTER lerobot in the server images — ros-jazzy-cv-bridge's boost `.so` is compiled against NumPy 1.x; numpy 2.x SEGFAULTs the rgb8 decode path (uncatchable, kills the node). A build-time functional cv_bridge decode gate proves it.
- `scipy>=1.14.0,<1.18` in all four server Dockerfiles (`Dockerfile.amd64`/`.arm64`/`.arm64cpu` + the thin overlay `docker/physical_ai_server/Dockerfile`) — scipy 1.18.0 dropped numpy-1.x support (`np.long`). Never widen back to `<2.0.0` while numpy is floored at 1.26.4.

**One PyTorch surface (torch 2.7.x), three CUDA channels — by design.** Modal worker: `nvidia/cuda:12.6.1-devel` + `torch==2.7.0` cu126 wheels. Student amd64 image: base ships torch 2.7.0+cu128, then the build-arg-gated `SLIM_CUDA=1` step (amd64 only, set by `build-images.sh`) swaps to **torch 2.7.0+cpu** and drops CUDA (~16 GB → ~5-6 GB after `flatten_image`'s `docker export | import` — the rm alone only writes whiteouts; the same `flatten_image` slims the Orange-Pi `-opi` server, which is CPU-torch from the start). Jetson arm64: keeps GPU torch 2.7.0+cu128 (SLIM_CUDA defaults 0, never flattened). CPU-only students are safe: `inference_manager.load_policy()` returns a German „needs GPU" error; recording never loads a policy; training is cloud-only.

## Critical architectural choices (don't undo silently)

- **No Docker Desktop.** Docker Engine runs inside the bundled WSL2 distro `EduBotics`. GUI invokes Docker via `wsl -d EduBotics -- docker …` (`_docker_cmd()` in `gui/app/docker_manager.py`) — never bare `docker`. USB reaches the distro via `usbipd attach --wsl EduBotics --busid X` (5.x positional form; the 4.x `--distribution` form is rejected), always resolved to an **absolute path** via `usbipd_resolver.find_usbipd()` (post-install PATH race: the Inno-launched GUI inherits explorer's pre-MSI PATH). Docker pinned `5:27.5.1-1~ubuntu.22.04~jammy` + containerd `1.7.27-1` via `apt-mark hold`, `containerd-snapshotter: false` — Docker 29.x snapshotter corrupts multi-layer pulls on WSL2 custom rootfs. `start-dockerd.sh` (the distro's `[boot]` command — NOT systemd, which is unreliable on custom-imported rootfs; `wsl.conf` also sets `appendWindowsPath=false`, so the script exports its own PATH) modprobes the serial/UVC kernel modules + starts udev + watchdogs dockerd on every boot; its modprobe list must stay in sync with `device_manager.diagnose_usb_environment`, and `device_manager.self_heal_wsl_serial` is the GUI-side counterpart at scan time. Installer Step 0 (`migrate_from_docker_desktop.ps1`) actively removes a pre-existing Docker Desktop (uninstall + unregister `docker-desktop*` distros + strip its autostart Run key; one-shot `.migrated` flag). usbipd-win itself is a pinned 5.3.0 MSI, SHA256-verified at install — a `RELEASE_PIN_NEEDED` sentinel in the `.iss` hard-fails `install_prerequisites.ps1` if a release forgets to update the pin.

- **The GUI is the SOLE owner of the container lifecycle.** The stack comes up ONLY on "Umgebung starten" — never on GUI launch or distro boot. Two enforcement points: (1) every student-stack service in `docker-compose.yml` is `restart: "no"` (`unless-stopped` resurrected the stack the instant dockerd started, holding the Dynamixel serial bus before any arm scan); (2) `gui_app.py::_run_prerequisite_checks` calls `docker_manager.ensure_environment_stopped()` at startup, and `_scan_arms` does the same first — `identify_arm.py` opens the same `/dev/serial` ports a live 100 Hz controller holds, so a running stack makes BOTH arms fail to identify. The GUI also runs `start_keepalive()` for the session (WSL2's ~60 s vmIdleTimeout would otherwise kill dockerd + the manager container mid-session; `atexit` reaps it). Note: the **Jetson** compose deliberately uses `restart: unless-stopped` — the agent owns that lifecycle differently; don't conflate the two. The **Orange Pi (`-opi`) compose is a second sanctioned exception**: `physical_ai_manager` runs `restart: unless-stopped` and the pi-agent brings it up at boot, because the manager *is* the setup wizard on a Pi — a freshly booted Pi must serve the UI with the robot tier down. Only the manager tier is exempted; `open_manipulator` + `physical_ai_server` stay `restart: "no"` and come up only on „Umgebung starten", and the pi-agent's `ensure_environment_stopped` stops ONLY the robot tier (never the manager, never `compose down` — stop + `rm -f` for every tier including factory reset, so `ros_net` and the manager survive).

- **Compose is boot-order- and security-opinionated** (`docker/docker-compose.yml`). Startup is health-gated: `physical_ai_server` waits on `open_manipulator: service_healthy`, `physical_ai_manager` on the server — don't remove the healthchecks. Only `open_manipulator` is `privileged` + `/dev:/dev`; the server container deliberately is NOT (attack-surface trim). - **Teleop collision e-stop — mixed-servo effort fractions, student-paced two-step recovery.** HW-validated 2026-06-04; runbook `docs/COLLISION_ESTOP_WINDOWS_VALIDATION.md`.
  - **Force signal is MODEL-AWARE — this bricked a release once.** The follower mixes servo models: dxl11-13 are XL430-W250 (`Present Load` only — declaring `Present Current` on them aborts hardware init → follower dead on every rig, and `EDUBOTICS_COLLISION_ENABLED=0` does NOT help because the xacro is baked in); dxl14-15 are XL330-M288 (`Present Current`, ~1 mA/LSB). `collision_detector.effort_fraction_from_values()` normalizes both to a 0..1 effort fraction (Load/1000, Current/1750) and maps unsigned-published int16 back to signed first (−5 arrives as 65531). Exposed via a read-only `gpio_command_controller` (claims NO command interface — Rule §2). The server image MUST apt-install `ros-jazzy-control-msgs` (ros-base lacks it; without it the guard fail-opens silently) and MUST NOT contain `controller_manager_msgs` (Fast-CDR 2.x ABI mismatch — creating a client crashes the node, exit 127).
  - **Detection** (`safety/collision_detector.py`, pure/unit-tested): effort ≥ per-joint threshold AND |velocity| ≤ 0.05 rad/s, debounced 150 ms; firmware Overload bit (0x20) = immediate trip. Thresholds `EDUBOTICS_COLLISION_EFFORT_J1..J5` default 0.30/0.65/0.40/0.30/0.30 (calibrated p95×1.5 on the reference rig). Gripper (dxl16) excluded.
  - **Gating**: OFF during inference (inside the detector), OFF during workflow + manual mode (in `collision_monitor.py` — the settle window re-arms on mode exit). A `COLLISION_SETTLE_WINDOW_S=0.5` re-arms on every re-torque (holding-current spike). **Leader-gate**: a trip is DROPPED when `not leader_appears_active()` — which keys SOLELY on `/leader/joint_states` freshness (2 s window), never on the in-process `EDUBOTICS_FOLLOWER_ONLY` (stale after the leader toggle recreates only the arm container). **`/leader/joint_states` delivery is SAFETY-LOAD-BEARING** (`test_press_trips_in_teleop_recording_mode` is the regression guard).
  - **Recovery is student-paced (two-step) — the arm NEVER auto-homes**: trip → `/collision_flag=true` (the upstream leader-side broadcaster skips publishing; 5 Hz watchdog re-asserts) → relax-in-place (delayed 0.15 s, re-sent ≤3×, commands the MEASURED pose) → in-progress episode discarded if recording → phase `COLLISION(7)` → modal Schritt 1 → `HOME_FOLLOWER(9)`: verified quintic glide (`COLLISION_HOMING(8)` while moving) → `COLLISION_HOMED(9)` → Schritt 2 → `RESUME_TELEOP(8)`: STRICTLY refused until homed, leader proximity ≤0.30 rad, quintic resync, flag clears only after resync. A mid-recording collision then resumes the SAME dataset (re-records the interrupted episode; earlier episodes intact). `FORCE_RESUME_TELEOP(10)` is the escape hatch; `EDUBOTICS_COLLISION_ENABLED=0` the one-variable rollback. ## Roboter Studio (layer 9) — consolidated reference

The Blockly programming surface for a follower-only kit: ONE OMX follower + ONE scene camera (no leader, no gripper cam). Everything below lives in `physical_ai_server/workflow/` + `components/Workshop/` unless noted.

### Mode & lifecycle
- **Follower-only via runtime container flip on `omx_full`, natively on `omx_follower` — not a separate stack.** On an `omx_full` rig the student starts a normal both-arms session; the React `LeaderToggle` → GUI localhost HTTP bridge (`gui/app/roboter_studio_control.py`, port **8769**, 127.0.0.1-bound, exact-host Origin-checked, busy-locked — its task-busy callback only knows whether another SWITCH is in flight; the GUI cannot see recording/inference state, so the React-side toggle disable is the ONLY mid-recording protection) → `docker_manager.restart_open_manipulator` regenerates the `.env` (`generate_env_file(robot_type=…, follower_only=True)` omits `LEADER_PORT`, emits managed `EDUBOTICS_FOLLOWER_ONLY=1`; BOTH the forward and the re-derived rollback call MUST carry `robot_type=self._rs_robot_type` or a failed switch silently rewrites the managed type) and recreates ONLY `open_manipulator` (`up -d --force-recreate --no-deps`, no pull, no `--wait`; `.env` rolled back on restart failure). On an `omx_follower` rig the stack is follower-only from env-start, the toggle self-hides (`caps.has_leader === false`) and the `:8769` bridge is never constructed (`_start_rs_control_server` lockout + a German belt refusal in `_rs_set_leader_mode`). Env-start regenerates from the selected profile (`omx_full` → both-arms, `omx_follower` → follower-only). The follower re-homes via a 3 s quintic to `[0, -π/2, π/2, 0, 0, 0.8]` — TWO pose families, NOT four identical sites: the ±π/2 boot/workflow HOME (`entrypoint_omx.sh::HOME`, `motion.HOME_JOINTS_RAD`) vs the deliberately more-folded ±π/4 collision/Jetson safe-home (`collision_monitor.SAFE_HOME_ARM`, `jetson_agent/agent.py::SAFE_HOME_JOINTS`). The ArmProfile mirrors both as unconsumed seam data (no-drift-tested); reconciling the divergence is an ask-first safety change.
- **The toggle's readiness gate holds the blocking overlay PAST the POST** (the POST returns when the container starts, not when the arm is back): scene-camera frames flowing again + `/joint_states` flowing again + the follower **moved-then-settled** (motion-witnessed latch; 12 s floor for the already-at-HOME case; 4 s min-settle; 90 s hard cap → manual „Trotzdem fortfahren"). The toggle self-hides off the Windows rig (no bridge) AND when the profile has no leader (`caps.has_leader === false`), and is disabled during RECORDING/INFERENCING/INFERENCE_LOADING.
- **`controller_manager_msgs` stays OUT of the server image** (ABI crash, see the collision bullet) — there is no switch_controller bridge; follower-only means the leader is simply never launched.

### Manual-mode arbiter (do not regress)
- **THE invariant: `on_manual == (_manual_persistent or _manual_transient_ops > 0)`, mutated ONLY under `_mode_lock` via `_recompute_on_manual_locked()`** (`physical_ai_server.py`; the only writers are the ctor + that helper). Jog/replay are TRANSIENT (refcounted claim/release); hand-guide/record are PERSISTENT (held until „Beenden"/cancel/cap-finish). Every mode entry (workflow/record/inference/the 4 manual services/capture) claims under `_mode_lock` around BOTH the `_assert_no_other_active` check AND the flag set.
- **Lock order is one-directional**: `_mode_lock` is held only around gate-check + flag-set and ALWAYS released before `_manual_lock`/`_dxl_torque_lock`/motion (`_manual_lock → _mode_lock` only, never the reverse → no deadlock). Never nest new locks into this.
- **A hard-exit generation (`_manual_exit_gen`, bumped by „Beenden") is snapshotted at claim and re-checked** after acquiring `_manual_lock` AND after the blocking re-torque, and folded into replay's `should_stop` — the arm can NEVER drive after the student pressed stop. A torque-ON-fail retains the session (fail-loud, never drives a possibly-limp arm). A 30 s idle watchdog (own callback group) re-torques + resets an abandoned session, re-checking activity freshness UNDER `_mode_lock` so it can't clobber a live claim; a frontend keepalive keeps an active hand-guide alive.
- Four services on the reentrant preempt group: `WorkshopJog` (joint/cartesian/drive_to — same velocity-floored quintic path as workflow moves, refuses out-of-range, never silently clamps), `WorkshopHandGuide` (torque-off hand-teaching; the universal manual exit), `WorkshopRecordControl` (start/stop/cancel; ~25 Hz sampling into Contract-B `points_json` — samples identical within 0.003 rad on every joint are dropped; `RECORD_MAX_S=120`), `WorkshopReplay`. Plus `WorkshopCapturePose` („Position merken" — FK end-effector pose, Z verbatim, works uncalibrated; stale-readback + `isfinite` guarded). Interfaces changes require an interfaces rebuild.
- **Callback-group rule**: anything blocking (HF whoami, torque switch, jog drive, replay) must NOT run on the node-default MutuallyExclusive group or it starves the 1 Hz heartbeat → React "Getrennt". HF services have their own reentrant group; keep the React service timeout (10 s) above the server's 8 s whoami wait. The node runs a `MultiThreadedExecutor(num_threads=6)` shared by ~35 services + subs + timers (raised from 3 — the 10 Hz-Aufnahme starvation bug); `main()` catches only `KeyboardInterrupt`, so an uncaught exception in ANY callback kills the node — that's why the gpio/collision callbacks are individually try/except-wrapped.

### Motion, IK, floors
- **Closed-form analytical IK only** (`workflow/ik_solver.py`) — pure NumPy FK + strict-vertical (top-down) 5-DOF IK, bent upper link θ0≈20.14°, elbow-up tried first; unreachable/out-of-limit/non-finite → `None` → German „Arbeitsbereich" error. NO numerical/PyKDL/TRAC-IK fallback. Reach annulus ≈ **0.04–0.28 m** (`_REACH_MIN/_MAX` = 0.0415/0.2825 — the WRIST-CENTRE 2R span; the practical projected table radius tops out ~0.26 m; the authoritative bound is `solve(...) is not None`, not a radius). Solver + perception are built ONCE per server lifetime — the caches prevent per-run allocations OOM-killing the 6 GB container (cgroup kill → rosbridge drop → robot re-select).
- **Velocity floor** (`trajectory_builder._velocity_safe_duration`): 4.8 rad/s × 0.6 safety = 2.88 rad/s peak, quintic peak factor 15/8 — it only ever EXTENDS a segment's duration. **Tempo** (run-bar 0.5/1/2 + per-move `GESCHWINDIGKEIT`, clamped `[0.5, 2.0]`, cloud rejects out-of-range) shrinks the requested duration BEFORE the floor re-extends it → a speed-up can never exceed the floor. A tempo-slowed segment is additionally capped at `_MAX_STRETCHED_DURATION_S=4.5 s`.
- **Workspace floor**: `WORKSPACE_FLOOR_MARGIN_M=0.01`; any target below the (tilted-plane-aware) table → `'Zielpunkt liegt unter der Tischebene.'` Enforced in both solve paths.
- **Motion details that surprise**: `home` CARRIES the current gripper state (pickup→home must not drop the object); `drop_at` releases at `EDUBOTICS_DROP_HEIGHT_M` (0.05) above the table — deliberately higher than the grasp clearance to clear container rims. The grasp-split blocks re-solve each step WITHOUT the composite grasp's cross-step `motion_lock` atomicity (known, accepted).

### Calibration (3 steps + optional check; wizard in `CalibrationWizard.jsx`)
- **Per-rig ChArUco intrinsics are MANDATORY — 20 frames** (`INTRINSIC_FRAMES_REQUIRED=20`), solved with `CALIB_RATIONAL_MODEL` (8-term — the ~102° wide lens overwhelms the 5-term default). Factory-default seeding is DELETED (never re-add): a guessed focal length scales every projected XY and the touch-off only fixes height. Any YAML with `source == factory_default` is skipped by both the manager and the runtime loader.
- **Scene extrinsic („single shot" to the student, a BURST in code)**: board against the 3D-printed L-jig → `EDUBOTICS_EXTRINSIC_BURST_FRAMES` (8) reads ~60 ms apart, ≥4 must pass per-frame gates → MAD outlier rejection → SO(3) chordal-mean. Per-frame solve: ChArUco `matchImagePoints` → **`cv2.SOLVEPNP_SQPNP` + `solvePnPRefineLM`** (ITERATIVE only as exception fallback; NOT `IPPE_SQUARE`) → compose with the jig-known `T_board_to_base` (yaw from `EDUBOTICS_BOARD_YAW_DEG`); hard reprojection/corner gates + an orientation sanity gate (`_check_extrinsic_orientation`: optical axis must hit the workspace region, camera must look DOWN) — which CANNOT catch a 90°/180°/mirror error; that's the ground-truth check's job.
- **Touch-off („Tisch vermessen")**: torque-off, student taps ≥3 spread points → FK → least-squares plane (`z_table` + tilt); gates reject near-collinear/high-residual captures (`TABLE_TOUCH_MIN_MINOR_M=0.015`, residual ≤0.008, camera cross-check 0.12 m).
- **DUAL Z-KEY CONVENTION (don't conflate)**: `board_table_z` = camera-side table SURFACE height written by the extrinsic solve (the projection plane); `z_table` = MEASURED end-effector grasp height written ONLY by the touch-off (the descend target). **There is NO `z_table=0.0` fallback anywhere** — missing touch-off → grasp/`mark_destination` refuse in German („Tisch vermessen"). Never reintroduce it.
- **Optional ground-truth XY/yaw check („Genauigkeit prüfen")**: known-placed vs detected points → closed-form 2D similarity fit (`fit_xy_correction`, Umeyama) + circular-mean yaw bias, persisted as `xy_correction`/`yaw_bias_rad` inside the extrinsic YAML and applied live in perception (`_apply_xy_correction`/`_apply_yaw_bias`). A mirror fit (`det(R)<0`) is REFUSED and persists nothing.
- `EDUBOTICS_FORCE_RECALIBRATION` (default ON) reports calibration as ABSENT until a touch-off completes in the current boot; a rig can opt out with `=0` in the host `.env`.

## Cloud stack (cloud_training_api + modal_training + supabase + jetson_agent)

- **Rate limiter** (in-process, `--workers 1`): rules sorted longest-prefix-first; `/jetson/`, `/trainings/`, `/workflows` are **per-user keyed** (`jwt:<sha256(token)[:16]>` — hashed unverified token, so a forger can't starve a victim); everything else per-IP (leftmost X-Forwarded-For, safe behind Railway's proxy only). - **Teacher-facing sub-surfaces — IDOR-gated like everything else**: `progress_entries` (Tagesnotizen; 3 mutually-exclusive scopes enforced by DB CHECK + partial unique indexes), mid-training checkpoint listing (`HfApi.list_repo_files`, 30 s TTL cache), per-student `inference_runs` (self-write keyed to the JWT, pruned to newest 50).

- **Worker (`training_handler.py`)**: dataset preflight — pinned to the SAME revision the trainer reads (`revision=EXPECTED_CODEBASE_VERSION`, i.e. the `v3.0` tag; a missing tag refuses in German) and asserting layout completeness at that revision (≥1 `data/*.parquet`, `meta/episodes/*.parquet`, per-camera `videos/<key>/*.mp4`, `total_episodes ≥ 1`) so a truncated upload fails cheaply — then spawns `lerobot_train`, progress via the scoped RPC, self-terminates on P0001 (cancel signal), checkpoint-watcher mirrors intermediate checkpoints to the private HF model repo, full stdout uploaded as `training_log.txt` on every terminal path (`trainings.log_url`, migration 028). The worker never writes `cancel_requested` — only the Cloud API does (direct UPDATE; the RPC's `p_status` check deliberately excludes it). `_pretrained_load_failed` greps worker stdout for THREE LeRobot-0.5.1-specific markers (`Could not load state dict` = pi0-family override; `Missing key(s)`/`Unexpected key(s) when loading model` = smolvla's strict=False base-class load) — fragile across upstream bumps, keep in sync with `_PRETRAINED_LOAD_FAILURE_MARKERS`.

### Deploy workflows + hardening invariants

- Health gates verify IDENTITY, never bare 200 (commit sha / buildId).
- **docker-publish**: native per-arch runners (amd64 `ubuntu-latest`, arm64 `ubuntu-24.04-arm`, NO QEMU; `fail-fast: false`); `jlumbroso/free-disk-space` amd64-only (the ~15.5 GB build needs it; arm64 fits); `--no-cache --pull`; dirty-tree refusal; buildkit routes docker.io through `mirror.gcr.io`; smoke-test pulls the **GHCR** images, asserts arch, bundle env, amd64 `.Size < 11 GB`, and runs `image_source_parity.sh`. Tag set: `:latest` (main), `:<sha>`, `:<short-sha>`, and on tags `:X.Y.Z` + `:X.Y` (both ALWAYS re-pointed on both registries — reconciles a failed-then-retried release). GHCR retags fatal, Hub best-effort (a Hub 429 warns, never fails the release).
- **Concurrency semantics differ per workflow**: `ci.yml` cancels in-flight PR runs (never main); `docker-publish.yml` never cancels (non-atomic pushes); `release.yml` cancels on a newer tag; `supabase-migrate.yml` serializes on a project-scoped group. Job timeouts encode real budgets: docker build 60 min, retag 45 min, installer 90 min.
- **Caller-permissions-superset rule**: `release.yml` grants per-job permissions and each caller job must superset its callee's declared permissions or GH `startup_failure`s the run (documented at the grant sites). Change both in one PR.
- Every checkout: `persist-credentials: false`. All third-party actions SHA-pinned. ## Spec-before-code for multi-layer features

Any feature touching **more than one of the 10 layers** gets a one-page dated spec+plan in `docs/plans/` BEFORE the first commit, with an explicit **"Non-goals (this round)"** section carrying trigger conditions. `docs/plans/` is **gitignored and throwaway** — delete the page once the feature lands. Durable invariants graduate into THIS file; dated narratives go to `docs/CLAUDE-CHANGELOG.md`; the plan never claims to be authoritative.

## When in doubt

The single source of truth is **the code**. This file describes invariants at the time it was written. Verify against `git log` and the current file when stakes are high. If this file disagrees with the code, fix this file in the same change — the whole point is that it stays in sync.

When you find an obstacle, **find the root cause** instead of bypassing it (never `--no-verify`, never `@pytest.skip`, never short-circuit an `apply_overlay` sha256 assertion that's telling you upstream renamed something).
