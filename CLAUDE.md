## What this is

**EduBotics** — a vertically integrated educational stack for teaching Physical AI on **ROBOTIS OpenMANIPULATOR-X** arms to **German-speaking students**. Student lifecycle: install `.exe` → setup wizard → record demos (ROS 2 teleop) → train policy (Modal cloud GPU) → inference (local or classroom Jetson) → optional **Roboter Studio** (Blockly authoring + AprilTag perception + manual arm control).

Students run Windows 11 PCs (no GPUs); training runs on Modal (NVIDIA L4; A100 for VLA). The product ships as a single `.exe` that installs a bundled WSL2 Ubuntu 22.04 distro named `EduBotics` containing Docker Engine + three containers — **no Docker Desktop**. Images pull from **GHCR (primary) with Docker Hub fallback**. The teacher/admin web dashboard is a separate Railway deploy. Installs are online-only.

Single git repo, no submodules. ROBOTIS upstream (`open_manipulator/`, `physical_ai_tools/`) is absorbed as plain directories.

## Six non-negotiable rules

These exist because we paid for the lesson. Don't undo without explicit user agreement.

### 1. German UI / English code

- **German** for everything a student/teacher/admin reads: tkinter labels, React UI, `detail` fields on API errors, user-visible log strings, toasts. Use literal `ä ö ü ß` (legacy files use `Schueler`; new code uses `Schüler`).
- **English** for everything the maintainer reads: code, comments, docstrings, internal logs, JSON keys, function names, commit messages.
- CI guard `german-strings-lint`: transliterations in `[FEHLER]`/`[WARNUNG]`/`[STOPP]` lines + an AST pass over cloud-API `detail=`/`error_message=` AND pi_agent `message=` (the pi_agent JSON `{"ok","message"}` surface is student-facing). `# english-ok` is the escape hatch. **The two violation classes are deliberately NOT symmetric**: TRANSLITERATION runs on EVERY scanned string and returns before the language test; ENGLISH only on strings that do not classify as German. Never nest the transliteration check inside the `is_german` branch — a string with no umlaut and no `GERMAN_WORDS` hit classifies as neither language and would then never be checked. `SCAN_SCOPES` is exactly `cloud_training_api/app` + `pi_agent`, and it is a Python `ast.parse` walker, so it structurally CANNOT see React — the literal-umlaut rule still binds there and is enforced by review.

### 2. Hardware safety lives in xacro + entrypoint, not software overlays

Software inference safety envelopes (NaN/Inf guard, joint clamp, velocity cap, stale-camera halt) were removed deliberately in the 2026-05 stripdown to fix recording↔inference asymmetry. Inference runs upstream `predict()` raw. Remaining protection is hardware-enforced or warning-only:

- **Xacro Dynamixel limits** (`omx_f.ros2_control.xacro`, `omx_l.ros2_control.xacro`): restrictive position limits exist ONLY on dxl12/dxl13 — dxl11 (Op Mode 4) and dxl14/15 are full-register-range, and the leader xacro has NO position limits (it is torque-free). The real safety floor is the gripper current limits (follower dxl16 `Current Limit 350` + `Goal Current 350` + `Shutdown 21`, Op Mode 5; leader trigger 300 mA).
- **ros2_control YAML**: 100 Hz; JointTrajectoryController in-flight `trajectory` tolerance 2.0 rad (effectively off — the safety floor is the Dynamixel current limit), `goal` 0.10 rad arm / 0.50 rad gripper, `goal_time` 5.0 s. Bumped from upstream's tight values, which aborted the 3 s quintic boot-sync mid-flight → compose restart-storm.
- **Torque-disable on shutdown** in `entrypoint_omx.sh::disable_torque()` — `trap … SIGTERM SIGINT EXIT`, so `set -e` aborts are covered. The leader path uses the namespaced `/leader/omx_l/set_dxl_torque`.
- **Phase-3 post-sync verification** in `entrypoint_omx.sh` (phases: 1 leader, 2 follower, 3 quintic sync + verify, 4 cameras) — 0.30 rad tolerance, arm joints only, ≥50 % of commanded delta traversed, soft-fail `[WARN]` (a hard exit looped compose restarts). Exactly two hard-exit paths remain: camera-disambiguation (exit 3) and `wait_for_device()`'s 60 s serial timeout (exit 1).
- Recording-side QUALITY guards (stale camera, camera-Hz deficit at 0.9×fps) are warning-only; but a topic-availability timeout, msg-conversion error or add_frame failure hard-stops the recording timer, and the streaming frame-drop guard DISCARDS the in-flight episode and re-records it (no retry cap).
- **The leader ARM JOINTS 1-5 are torque-free/limp by design** — no gravity compensation is spawned (`Torque Enable 0`, Goal/Present Current interfaces commented out in `omx_l.ros2_control.xacro`; broadcasters only). The leader GRIPPER TRIGGER is NOT limp: `trigger_position_controller` + a 50 Hz `ros2 topic pub` of −0.7 rad simulate spring resistance under the 300 mA cap. Two comments still claim gravity compensation exists and are stale (`docker/open_manipulator/Dockerfile` leader block; `collision_monitor.py` header) — the xacro + launch files are the truth.

**ONE sanctioned exception: the teleop force/collision e-stop** — scoped to teleop/recording ONLY. Gated OFF during inference (inside the detector via `mode_is_inference`), and OFF during workflow and manual mode (`collision_monitor.py`, one combined `if on_workflow or on_manual` gate; the manual half is a sanctioned v2.11 scope change — follower-only Roboter Studio has no leader, and hand-guiding presses the arm at ~0 velocity, indistinguishable from a collision). It never modifies samples: a trip DISCARDS the in-progress episode, it does not filter or clamp.

If you need to reintroduce any OTHER software safety guard that modifies the pipeline, **stop and ask the user**.

### 3. The shipped image must reflect the repo

**physical-ai-server: COPY-WHOLESALE, no overlays.** The image's `physical_ai_server` package is a verbatim copy of `physical_ai_tools/physical_ai_server/` (staged as `pkg_src/` by `build-images.sh`, excluding `test/`, the three base Dockerfiles, `CHANGELOG.rst` and bytecode — then `rm`'d + `COPY`'d + re-`colcon`'d), so "image == repo HEAD" holds by construction: edits, new files AND deletions propagate. The Dockerfile asserts that the stripped `safety_envelope.py` and the dead `training/trainers` + `evaluation` trees never re-enter (`build-images.sh` independently re-checks the staged tree for `safety_envelope.py` only — the other two are guarded in the Dockerfile alone). Four build-time smoke gates must pass: policy imports + `CODEBASE_VERSION == 'v3.0'`, node import, `control_msgs` gpio import, functional cv_bridge rgb8 decode.

**open-manipulator: STILL the overlay model.** `apply_overlay()` in `docker/open_manipulator/Dockerfile` does sha256 pre/post verification over the **7-file** chain (both `ros2_control.xacro`s, both `*_ai.launch.py`s, both controller-manager YAMLs, `camera_usb_cam.launch.py`); the build aborts on a missing upstream target. **When adding an overlay you must add it to the chain with a unique path filter** — without that the source edit never reaches the image. Standalone scripts (`identify_arm.py`, `camera_ingest_node.py`, `calibrate_collision_currents.py`, `edu6_arm_node.py`, `feetech_bus.py`, `edu6_geometry.py`) are plain `COPY`s, not overlays.

**Both are guarded by `image-source-parity`** (`.github/scripts/image_source_parity.sh`, per-arch in `docker-publish.yml::smoke-test`): physical-ai-server asserts byte-identity (`diff -r`), open-manipulator asserts every overlay by sha256. The parity script mirrors `build-images.sh`'s staging exclusions — change one, change both. LeRobot is **not** overlaid — pip-installed from PyPI at `0.5.1` (Rule §5); `patches/fix_server_inference.py` is retained ONLY so CI `overlay-guard` can test the patch harness. The server **amd64 BASE image is pulled, never built** — `build-images.sh` resolves `robotis/physical-ai-server:amd64-0.8.2` via `docker manifest inspect`; `Dockerfile.amd64` is forward-compat scaffolding (keep its pins in lockstep anyway).

**The other TWO server bases are ours, and NO workflow builds them.** Two hand-run triggers: `BUILD_BASE_ARM64=1 PLATFORM=arm64` → `Dockerfile.arm64` (Jetson), `BUILD_BASE_OPI=1 PLATFORM=opi` → `Dockerfile.arm64cpu` (Orange Pi CPU base); every CI build merely *resolves* the tag pinned in `build-images.sh`. So **editing `Dockerfile.arm64cpu` / `.arm64` ships nothing on its own, silently** — the release goes green on the previously-published base, and Rule §5 routes people into these files to bump LeRobot pins. Two fences: `ci.yml::base-version-guard` fails any non-comment edit to a base Dockerfile whose `PAS_BASE_IMAGE` tag didn't move in the same commit; `docker/bump-upstream-digests.sh` reports all three self-built pins and exits non-zero on a tag never pushed. The rebuild is a Rule §6 manual step.

### 4. Service-role key bypasses RLS — authorization is your job

Every Supabase query in `cloud_training_api/app/` runs as **service-role** via `services/supabase_client.py::get_supabase()` (lazy singleton, fails fast on empty secrets); RLS is defense-in-depth only (anon-key/Realtime read paths) and dormant under service-role. Every endpoint touching another user's data **must** call an ownership assert. The teacher/workgroup/workflow helpers raise a German 404 — never 403 — to avoid existence leakage. The Jetson pair deliberately differs: `_assert_classroom_member` raises 403 (membership gating, not existence) and `_assert_jetson_owner` raises 404-or-**410 „Lock verloren"**; `_assert_workgroup_in_classroom` can also 400.

- `_assert_classroom_owned` / `_assert_student_owned` / `_assert_entry_owned` / `_assert_workgroup_in_classroom` — `routes/teacher.py`
- `_assert_workgroup_owned` — `routes/workgroups.py`
- `_assert_workflow_owned` (write) / `_assert_workflow_visible` (read ladder: owner OR group sibling OR classroom template) — `routes/workflows.py`
- `_assert_classroom_member` / `_assert_jetson_owner` — `routes/jetson.py`

**One missed assertion = silent IDOR.** RLS will not catch it. Writes additionally re-scope the query (`.eq("owner_user_id", …)`). Dataset registration is enforced atomically in Postgres instead: `register_dataset_safe` RPC (migration 026, `FOR UPDATE` on the caller's users row, HF-author anchor, P0034 → 403). The workflow read-visibility ladder is implemented FOUR times in `routes/workflows.py` (`_assert_workflow_visible`; inline in `list_workflows` + `get_workflow`; ad-hoc in `clone_workflow`) plus near-twin resolvers in `services/workgroups.py` — **semantics changes must touch every copy.**

The Modal worker uses the **anon key** + per-row `worker_token` (UUID). Its only DB write surface is the `update_training_progress(p_token, …)` RPC, guarded by the terminal-state `WHERE status NOT IN ('succeeded','failed','canceled','cancel_requested')` clause (migrations 010 + 032) — a late worker write is a P0001 no-op, and that P0001 is also the worker's in-band cancel signal. RPC GRANTs are asymmetric by design: `update_training_progress` is anon+authenticated (the worker), `register_dataset_safe` is service-role-ONLY. `update_training_progress` is deliberately absent from the boot schema probe (its defaulted 8-arg signature is overload-ambiguous) — drift there is invisible to `/health`.

### 5. Don't introduce drift between the LeRobot pinning sites

The LeRobot pin `0.5.1` must agree across:

- `modal_training/modal_app.py` constant `LEROBOT_VERSION`
- `physical_ai_server/Dockerfile.amd64` (`pip install "lerobot[pi,smolvla,peft]==0.5.1"`)
- `physical_ai_server/Dockerfile.arm64` (same line under the Jetson AI Lab pip index)
- `physical_ai_server/Dockerfile.arm64cpu` (Orange Pi 5 Pro CPU base, stock `ros:jazzy-ros-base`, plain PyPI; same line, but torch is PINNED EXPLICITLY — `torch==2.7.0` + `torchvision==0.22.0` — **before** lerobot, because this base inherits no torch and `lerobot 0.5.1` allows `torch<2.11`, so an unpinned resolve pulls 2.10.x and breaks the one-torch-2.7.x surface)
- the thin overlay `docker/physical_ai_server/Dockerfile`, which carries the same install and is what CI actually builds on

Bumping LeRobot is a **one-PR multi-site change**; `meta/info.json` `codebase_version: "v3.0"` and the Modal preflight `EXPECTED_CODEBASE_VERSION="v3.0"` are **derived** consts that move with the pin.

**Hard dependency caps — never widen silently:**

- `numpy==1.26.4`, force-reinstalled AFTER lerobot in the server images — ros-jazzy-cv-bridge's boost `.so` is compiled against NumPy 1.x, and numpy 2.x SEGFAULTs the rgb8 decode path (uncatchable, kills the node). A build-time functional cv_bridge decode gate proves it.
- `scipy>=1.14.0,<1.18` in all four server Dockerfiles — scipy 1.18.0 dropped numpy-1.x support (`np.long`). Never widen back to `<2.0.0` while numpy is floored at 1.26.4.

**One PyTorch surface (torch 2.7.x), three CUDA channels — by design.** Modal worker: `nvidia/cuda:12.6.1-devel` + `torch==2.7.0` cu126. Student amd64: the base ships torch 2.7.0+cu128, then the build-arg-gated `SLIM_CUDA=1` step (amd64 only, set by `build-images.sh`) swaps to **torch 2.7.0+cpu** and drops CUDA, ending at **5.56 GB** after `flatten_image`'s `docker export | import` (which also slims the `-opi` server). **Dropping CUDA is not just `/usr/local/cuda*`:** the base also lands `/opt/nvidia/nsight-compute` (1192 MB) and `/usr/lib/x86_64-linux-gnu/libnccl.so*` + `libnccl_static.a` (774 MB) OUTSIDE that prefix, both provably dead once torch is `+cpu`, so the `SLIM_CUDA=1` branch removes them too (7.53 → 5.56 GB; 2.626 → 1.592 GB compressed). **They must STAY in that branch**: opi has neither path, and Jetson arm64 keeps GPU torch 2.7.0+cu128 (SLIM_CUDA defaults 0, never flattened — NCCL is legitimate there). CPU-only students are safe: `load_policy()` returns a German „needs GPU" error, recording never loads a policy, training is cloud-only.

### 6. CI/CD deploys

Seven workflows in `.github/workflows/` are the canonical path:

- `ci.yml` — 25 validator jobs on every push/PR to `main`.
- `supabase-migrate.yml` — **W1**. `supabase db push --linked --include-all` (password extracted with `urllib.parse`, never sed) against project `fnnbysrjkfugsqzwcksd`; PROJECT-scoped concurrency so a tag release and a `main` push serialize instead of racing the DB. A `workflow_dispatch` `rollback` job applies `rollback/<name>.sql` via psql.
- `railway-deploy-cloud-api.yml` — **W2**. Read-only schema probe → `railway up` → `/health` gate asserting `body.commit == github.sha` (never a bare 200 — blue-green keeps the old pod serving 200).
- `railway-deploy-teacher-web.yml` — **W3**. Placeholder-build validate → `railway up` via `scripts/railway-deploy.sh` → `/version.json` gate asserting the buildId contains the SHA.
- `docker-publish.yml` — **W4**. Builds + dual-pushes **8 images** (3 amd64 + 2 `-jetson` arm64 + 3 `-opi` arm64) to **GHCR primary (`ghcr.io/svendanilborodun/*`) + Docker Hub fallback (`nettername/*`)**. Fires on `main` pushes (`:latest`), `workflow_call`, `workflow_dispatch`; **its standalone tag-push trigger was REMOVED** — on a tag only `release.yml` W4 builds. `build-images.sh` pushes to Docker Hub FIRST and the `retag` job creates GHCR tags FROM Hub via `imagetools create` — GHCR is the consumption primary, not the build primary.
- `release-installer.yml` — **W5**. Windows `.exe` build; `workflow_call`-only + `workflow_dispatch` (no tag race).
- `release.yml` — top-level dispatcher on `vX.Y.Z` tags. **Golden order W1→W6**: supabase → cloud-api → teacher-web → docker → installer → **W6 `publish-gui-version`** (an inline job: sets Railway `GUI_RELEASE_REPO`/`GUI_DOWNLOAD_URL`/`GUI_INSTALLER_SHA256`, then `GUI_VERSION` last, AFTER the `.exe` is attached — race-safe auto-update advertising; tag-push only).

**opi is DECOUPLED from the core release.** Its build + smoke-test legs are `continue-on-error: matrix.platform == 'opi'`; the build leg uploads an `opi-build-success` marker artifact (carrying the run's sha) LAST, and the retag job retags opi ONLY when that marker exists AND matches `github.sha` — never off an existence probe of the mutable `:latest`, or a failed opi build would promote the PRIOR release's images under new semver tags. Dual-push-integrity warns rather than fails for opi, and opi GHCR retags are best-effort, so no opi-only transient blocks the amd64/Jetson publish.

**`version-preflight` runs FIRST on tag pushes** and hard-fails the release when the tag ≠ the repo `VERSION` file. W6 advertises the TAG while the tarball/installer bake the FILE, so a mismatch puts every Pi AND every Windows GUI into an infinite forced-update loop whose skip button never appears — every update "succeeds" without advancing the anchor. W1 `needs` it; W2 additionally checks its result explicitly.

**The Pi tarball.** A W5-adjacent `pi-agent-tarball` job attaches `edubotics-pi-agent.tar.gz` (built from `robotis_ai_setup/pi_agent/`, top-level `pi_agent/`) with three baked, gated files: the repo-root `VERSION` as `pi_agent/VERSION`, a generated `pi_agent/docker/versions.env` pinning `IMAGE_TAG=<VERSION>`, and the TRACKED `docker-compose.opi.yml` twin. The tarball must contain each; both version files must equal the repo `VERSION`; the packaged compose must `cmp` equal to `robotis_ai_setup/docker/docker-compose.opi.yml`. **The post-`tar` cleanup deletes only the GENERATED `versions.env`** — `rm -rf …/pi_agent/docker` would take the tracked twin with it.

W6 also publishes `PI_AGENT_SHA256` before the `GUI_VERSION` flip — the hash of that exact tarball, emptied BOTH on hash failure AND when any of the three `-opi:<VERSION>` images is anonymously pullable on NEITHER GHCR nor Docker Hub. **An empty hash ⇒ the Pi advertises NO self-update**, so it can never pin a release whose `-opi` images never published. `pi-agent-tarball` is an ORDERING-only `needs` of W6, which gates ONLY on `installer` success — a Pi-tarball hiccup never withholds the Windows `.exe`. **The reverse direction is an owner call**: a failed installer build skips BOTH Pi-facing jobs after the `-opi` images have published (`docs/KNOWN-ISSUES.md`).

**The Modal app (`edubotics-training`) deploys MANUALLY** — the image builds in Modal's infrastructure and the CI feedback loop is too slow to debug remotely:

```bash
cd robotis_ai_setup/modal_training
modal deploy modal_app.py
modal run -m modal_app::smoke_test    # optional
```

Run it BEFORE pushing a tag if the release touches Modal.

**The three self-built Docker BASES also deploy MANUALLY** — the second sanctioned carve-out, most easily missed because it looks like ordinary source. If a release touches `Dockerfile.arm64cpu` or `Dockerfile.arm64`, rebuild + push the base and bump its tag in `build-images.sh` BEFORE the tag, or **the release silently ships on the old base**. `base-version-guard` fences the tag bump at review time but cannot check that you pushed the image — `bump-upstream-digests.sh` catches that.

For every other surface, manual `railway up`, `psql -f` and a full `build-images.sh` run are EMERGENCY-only. The `BUILD_BASE_*` invocations are a *workstation push by design*: "never push from a workstation" governs the student-facing thin images, which CI owns. CI refuses to build from a dirty tree, so `*-dirty` tags cannot reappear.

**Applying migrations:** `supabase db push` works; Claude's MCP `apply_migration` also works, but MCP re-stamps the version prefix into the ledger — **rename the on-disk file to the MCP-stamped value afterwards**, or the next `db push` sees ghost-unapplied migrations (the doubled-prefix filename on migration 026 is this scar).

## Critical architectural choices (don't undo silently)

### Windows host, WSL2, container lifecycle

- **No Docker Desktop.** Docker Engine runs in the bundled WSL2 distro `EduBotics`; the GUI calls it as `wsl -d EduBotics -- docker …` (`docker_manager.py::_docker_cmd`), never bare `docker`. USB attaches via `usbipd attach --wsl EduBotics --busid X` (5.x positional form; the 4.x `--distribution` form is rejected), always through `usbipd_resolver.find_usbipd()`'s absolute path — the Inno-launched GUI inherits explorer's pre-MSI PATH. Docker pinned `5:27.5.1-1~ubuntu.22.04~jammy` + containerd `1.7.27-1` (`apt-mark hold`, `containerd-snapshotter: false`) — 29.x's snapshotter corrupts multi-layer pulls on a custom rootfs. `start-dockerd.sh` is the distro's `[boot]` command, not systemd: it modprobes serial/UVC modules, starts udev, watchdogs dockerd, and exports its own PATH (`wsl.conf` sets `appendWindowsPath=false`). **Its modprobe list must stay in sync with `device_manager.diagnose_usb_environment`**; `device_manager.self_heal_wsl_serial` is the scan-time counterpart. Installer Step 0 `migrate_from_docker_desktop.ps1` removes a pre-existing Docker Desktop (uninstall + unregister `docker-desktop*` distros + strip its Run key; one-shot `.migrated` flag). The GUI also runs `start_keepalive()` for the session — WSL2's ~60 s `vmIdleTimeout` would otherwise kill dockerd + the manager container mid-lesson (`atexit` reaps it). usbipd-win is a pinned, SHA256-verified 5.3.0 MSI; a `RELEASE_PIN_NEEDED` sentinel in the `.iss` hard-fails `install_prerequisites.ps1` on a forgotten pin.

- **The GUI is the SOLE owner of the container lifecycle** (`_run_prerequisite_checks` / `_prereq_in_progress`, `_scan_arms` / `_do_scan` / `_scan_confirm_open` / `_scan_cameras`). The stack comes up ONLY on „Umgebung starten", enforced twice: every student-stack service in `docker-compose.yml` is `restart: "no"`, and `gui_app.py::_run_prerequisite_checks_body` calls `ensure_environment_stopped()` **immediately after the dockerd-ready gate and BEFORE the rootfs-mismatch gate**, which `return`s. **Any new early return after a distro boot must sit BELOW the teardown.** `_scan_arms` calls it first too — `identify_arm.py` opens the `/dev/serial` ports a live 100 Hz controller holds. **„Arme scannen" ENDS the previous student's session** (teardown closes the WebView2 child via `destroy_all()` first), **so it confirms first, but ONLY when a student window is open** (`has_live_window()`). A DECLINE is a total no-op — no teardown, no status text, no log line, `_scanning` untouched, button enabled.

  Two sanctioned `restart:` exceptions. **Jetson** uses `unless-stopped` — the agent owns that lifecycle; don't conflate. **Orange Pi** runs `physical_ai_manager` `unless-stopped` at boot, the manager being the setup wizard; only that tier is exempt, `open_manipulator` + `physical_ai_server` stay `restart: "no"`, and the pi-agent's `ensure_environment_stopped` stops ONLY the robot tier — never the manager, never `compose down`.

- **Compose is boot-order- and security-opinionated** (`docker/docker-compose.yml`). Health-gated startup: `physical_ai_server` waits on `open_manipulator: service_healthy`, the manager on the server — don't remove the healthchecks. Only `open_manipulator` is `privileged` + `/dev:/dev`; the server deliberately is not. **`physical_ai_server` publishes NO host port at all** — `:9090`/`:8080` went in the 2026-08-06 rosbridge move, and that removal is what makes the nginx Origin allowlist non-bypassable; with them open the proxy is theatre. What still publishes is the manager's `127.0.0.1:80:80` and `open_manipulator`'s `127.0.0.1:5557:5557` (native camera ingest). Anything published stays loopback-bound, because rosbridge is unauthenticated — anyone reaching it can drive the arm. Both robot containers get `SYS_NICE` + rtprio/memlock ulimits (the 100 Hz loop); `mem_limit` 2g/6g + `pids_limit` are what actually OOM-kill a leaky node. The `open_manipulator` healthcheck INLINE-duplicates the entrypoint's WSL2 `uname -r | grep -i microsoft` camera-source detection — change one, change both. `CAMERA_NAME_1` defaults `gripper`, `CAMERA_NAME_2` defaults EMPTY: that asymmetry is how a 1-camera Roboter-Studio kit is told from a 2-camera rig.

- **Students see the React UI through an embedded WebView2 child process.** „Web-Oberfläche öffnen" spawns `EduBotics.exe --webview` → `gui/app/webview_window.py` — a CHILD process because pywebview 6.x demands the main thread tkinter already owns (`edgechromium`; system-browser fallback on import failure or a fast ~2 s exit). The URL carries a cache-busting `_v=<IMAGE_TAG>` param (WebView2's persistent cache would serve a stale app shell after an image update), and the GUI — not React — appends `?cloud=1` in cloud-only mode. The module, which exposes `is_available()` / `runtime_missing()` / **`has_live_window()` — the ONE sanctioned read of the module's `_process`**, taken under `_lock` like `destroy_all()`; both are **PROCESS-LOCAL**. `_check_prerequisites` hits the Cloud-API `/version` FIRST: a newer release opens a non-closable modal that downloads the installer (Content-Length + SHA-256 verified, HEAD-precheck against 404'd assets); „Überspringen" appears only after a failed attempt.

- **Elevated repairs share `_run_privileged`.** With an admin token already held (UAC „Never notify") the command runs DIRECTLY, no UAC, INFINITE wait — a timeout kill reaches only powershell.exe while the wsl.exe grandchild survives detached, and killing `wsl --import` mid-copy risks a corrupt VHDX. A standard token routes through `_elevate_and_wait` (ctypes `ShellExecuteExW`, `use_last_error=True` + `SEE_MASK_FLAG_NO_UI`, German SE_ERR classification — PS `Start-Process -Verb RunAs -Wait` has unreliable wait semantics). `exit_code is None` means „never launched", distinct from a numeric child failure; launch failures and ≥2 UAC cancels open a manual-command fallback dialog whose command **MUST stay `$`-free** (an interactive PowerShell interpolates `$` inside double quotes before the child parses them). The post-reboot finalize (`_prompt_finalize_install`) runs AUTOMATICALLY with no consent dialog — `reason="rootfs_mismatch"` is the ONE path that still asks — guarded by `_finalize_in_progress`, cleared in a `finally` after ALL post-processing. `preflight_system.ps1` runs once per launch on a daemon thread: FIVE non-fatal checks (temp-path/dotted-username write probe, UAC feasibility where `isAdmin` is read, WSL2, dockerd, account-scope from the finalize marker), always `exit 0`; output is forced to UTF-8 by a `[Console]::OutputEncoding` wrapper and decoded `errors="replace"`, because PS 5.1 writes redirected stdout in the OEM codepage.

### Configuration, registries, version coupling

- **The GUI-managed `.env` (`%LOCALAPPDATA%\EduBotics\.env`) is the compose interface.** Compose resolves `${REGISTRY}`/`${IMAGE_TAG}`/camera keys ONLY from the `--env-file` the GUI passes; Windows env vars do not cross the `wsl.exe` boundary. `config_generator.MANAGED_KEYS` (9: `FOLLOWER_PORT, LEADER_PORT, ROS_DOMAIN_ID, REGISTRY, REGISTRY_FALLBACK, IMAGE_TAG, EDUBOTICS_CAMERA_NAMES, EDUBOTICS_FOLLOWER_ONLY, EDUBOTICS_ROBOT_TYPE`, plus `_MANAGED_PREFIXES` `CAMERA_DEVICE_`/`CAMERA_NAME_`) are re-emitted on every regenerate, so a hand-pinned value is SUPERSEDED; everything else is preserved verbatim by `_read_unmanaged_lines`, except an `HF_TOKEN` + `HF_TOKEN_MACHINE` pair stamped from another PC, which is DROPPED. **Keep `MANAGED_KEYS` in lockstep with the emitted lines.** Per-rig overrides go through env vars (`EDUBOTICS_IMAGE_TAG`, `EDUBOTICS_REGISTRY`), never hand-edits of managed lines; writes are atomic (temp + `os.replace` + fsync). The Pi has its own `MANAGED_KEYS` (13 vs 9); the divergences read as deliberate but **nothing asserts them** (`docs/KNOWN-ISSUES.md`).

- **IMAGE and COMPOSE are version-COUPLED, so `EDUBOTICS_IMAGE_TAG` is NOT a one-variable rollback on Windows.** `docker-compose.yml` ships with the **installer** (`{app}\docker\`, `constants.COMPOSE_FILE`) while the tag pins only the IMAGES. Two boundaries, neither visible from the pin: the **2026-08-06 rosbridge move** (`nginx.conf`'s `location = /rosbridge` and `= /video/stream` live in the manager IMAGE — pinning older gives new compose + old nginx + old SPA), and the **v2.15.0 student login gate** (`utils/authGate.js`, also in that image; pinning older restores "Start, Aufnahme, Daten, Roboter Studio usable with no login"). **Rollback is two-step: install the older `.exe` AND pin — or pin nothing.**

- **Registry resolution: env override → `docker/versions.env` → default**, shared by `REGISTRY` (`ghcr.io/svendanilborodun`), `REGISTRY_FALLBACK` (`nettername`) and `IMAGE_TAG` (`latest`) in `gui/app/constants.py`. **One-variable rollback to Hub: `EDUBOTICS_REGISTRY=nettername`** — that one IS still one variable, since the registry does not change what the image contains. The runtime fallback pulls the digest-identical Hub twin and `docker tag`s it to the GHCR name; that ref is a **prefix swap**, never `split('/')`, and the auto-pull digest pre-check uses **set membership** of the remote candidate set. `prune_superseded_tags()` is a NO-OP while `EDUBOTICS_IMAGE_TAG` is set (both GUI and pi_agent twins, `.strip()`-guarded) — an explicit pin IS the documented rollback and pruning would delete the tag the operator needs; the caller additionally gates on `any_updated and not any_failed`.

- **Both fleets pin `IMAGE_TAG` via a BAKED `versions.env`; the Pi's is baked by `release.yml`, not CI.** Windows gets `docker/versions.env` from `release-installer.yml`; the Pi gets `pi_agent/docker/versions.env` from `release.yml::pi-agent-tarball` at `/opt/edubotics/pi_agent/docker/versions.env` — the FIRST path `pi_agent/constants.py::_read_versions_env`'s upward walk probes (nearest-wins PER KEY). **TWO writers**: the tarball and `pi_agent/setup.sh` at PROVISION time. **With no `versions.env` the Pi falls back to `APP_VERSION` — its own release — NOT `latest`** (`_default_image_tag()`; only an ACTUALLY-READ VERSION counts, via `_VERSION_IS_AUTHORITATIVE`, so a blank VERSION cannot yield the unpullable ref `…-opi:`), while the GUI still falls back to `latest`. Intended: a release whose `-opi` images never published fails LOUDLY, and `pi_agent/docker_manager.py` names the missing version in German.

- **The HuggingFace token is set ONCE in the GUI (Schritt D), lives in the host `.env`, and is BOUND to the PC it was entered on.** `config_generator.write_hf_token` is the sole writer; a GUI call site using `upsert_env_var` directly stores an UNSTAMPED token, which an AST guard in `test_gui_install_lifecycle.py` refuses. The token is deliberately NOT a managed key, so it survives every regenerate AND Factory Reset; compose forwards `HF_TOKEN=${HF_TOKEN:-}` on `physical_ai_server` — **keep it in that `environment:` list**. The GUI redacts the token (and any TOKEN/SECRET/PASSWORD/KEY key) in the Protokoll; the server has a `_BearerTokenScrubber` logging filter. There is NO token UI on the STUDENT React surface; re-adding one is a regression (the Pi's `piOnly` System tab deliberately has one — `SystemPage.js` Schritt D → `POST /hf-token`).

  **`%LOCALAPPDATA%\EduBotics\` TRAVELS** (roaming profile, FSLogix, AppData redirection, golden image) and holds `HF_TOKEN`, which compose forwards. Two halves: `bind_hf_token_to_this_machine` (from `gui_app.py::__init__` BEFORE `_build_ui`, so Schritt D re-prompts) DELETES a foreign token from disk, and `_read_unmanaged_lines` never CARRIES the pair forward — including for `_rs_set_leader_mode`, which regenerates at RUNTIME on the `:8769` thread.

  `hf_token_is_foreign` is the ONE predicate both halves ask, and it refuses on PROOF only. **An ABSENT stamp is LEGACY, not foreign** — every fielded install has a token and no stamp. **This is the OPPOSITE call from the deleted `ROS_DOMAIN_ID` cache**, whose legacy handling was to re-derive; **do not harmonise them.** **One-variable opt-out `EDUBOTICS_HF_TOKEN_ANY_MACHINE=1`** — for a school baking ONE service account's token into a golden image; it gives up the protection ENTIRELY and must stay set on the clones. The Pi needs none of this: `/etc/edubotics/.env` is machine-local.

- **Per-machine `ROS_DOMAIN_ID` — derived every time on Windows, cached on the Pi.** `config_generator::_resolve_ros_domain_id` (both platforms): `EDUBOTICS_ROS_DOMAIN` env clamped to [0, 232] → (Pi only) the persisted value → `int.from_bytes(sha256(_read_machine_id() or str(uuid.getnode())).digest()[:2], "big") % 233` (`tests/test_ros_domain_twin_lockstep.py` pins the 2-byte truncation by AST STATEMENT ORDER — never string indices — and asserts BOTH intended divergences, seed source and cache, positively).
  - **The seed is a stable machine identity, not `getnode()`** (unstable on multi-NIC/VPN/dock PCs; last resort only). `gui/app/config_generator::_read_machine_id` (the Pi twin reads `/etc/machine-id`; `EDUBOTICS_MACHINE_ID` is the test seam, read at CALL time) composes `HKLM\SOFTWARE\Microsoft\Cryptography\MachineGuid` (opened `KEY_WOW64_64KEY`) **plus** the computer name from `HKLM\SYSTEM\CurrentControlSet\Control\ComputerName\ActiveComputerName`, falling back to `%COMPUTERNAME%` then `socket.gethostname()`. **All three name sources go through `_canonical_computer_name` (`upper(strip(name.split('.')[0]))`), and that is itself an invariant** — with no cache the seed alone pins a PC to one domain, so a shift in the fallback ORDER silently moves it.
  - **Windows has NO cache and must not grow one back.** **The Pi KEEPS its cache and that is correct** (`/var/lib/edubotics/.ros_domain_id` is machine-local).

### The Orange Pi agent

- **The Pi agent REPAIRS its own systemd units (`SYSTEMD_UNIT_NAMES`), udev rules (`UDEV_RULES_DIR`, `_drifted_udev_rules`/`_renew_udev_rules`) and opi compose; every mutating endpoint takes a BOUNDED lock.** `agent.py::_check_system_files_version` byte-compares the installed units against `pi_agent/systemd/` and, on drift, `_install_system_file` writes the shipped bytes atomically (temp → fsync → chmod 0644 → `os.replace`, one `.edubotics-bak`, then an fsync of the DESTINATION DIRECTORY — a rename is atomic for readers, but that is ordering, not durability) + `systemctl daemon-reload` — **never `restart`, never `enable`, never a unit not already installed**. **Repair is per-FILE via `_install_each`** — never `all(install(n) for n in drifted)`, which short-circuits.

  **`docker-compose.opi.yml` is in that repairable set** (`SHIPPED_COMPOSE_RELPATH`, `_compose_drifted`/`_renew_compose`), via a **byte-identical TWIN** at `robotis_ai_setup/pi_agent/docker/docker-compose.opi.yml`. `_shipped_compose_path()` resolves PACKAGE-relative off `__file__` — repointing it at the `robotis_ai_setup/docker/` copy leaves the suite green in a checkout and silently kills the feature in the field; `boot()` runs the repair BEFORE `docker_manager.start_manager`, so the manager tier adopts the new compose in THAT boot. **The twin's path is DERIVED, never restated**: both gates read `SHIPPED_COMPOSE_RELPATH` from `pi_agent/constants.py` via `.github/scripts/pi_shipped_compose_relpath.py`, so keep that constant a string literal or an `os.path.join()` of literals.

  **The compose repair is VALIDATE-THEN-SWAP** (`docker compose -f <tmp> config -q`). **Isolating that gate from the student's `.env` takes TWO things: omitting `--env-file` AND `env=docker_manager._scrubbed_env()`** — compose interpolates from the process environment too, and the unit is `EnvironmentFile=-/etc/edubotics/.env`. `_compose_up` also passes `--env-file`, which the gate deliberately does not: **do not "align" the two; that difference IS the fix.** **`UDEV_RULE_NAMES` is in the set too**. Renewal runs **`udevadm control --reload-rules`, NEVER `udevadm trigger`** — the analogue of „daemon-reload, never restart"; a failed reload is non-fatal.

  **The repair only ever REPLACES, never CREATES.** **Treat any new system file as undeliverable to the fielded fleet until create-vs-replace is settled** — OPEN, no owner.

  `.s6-keep` cannot join the set (0 bytes — a byte compare has nothing to find), but is still REQUIRED on disk (the compose bind-mounts it and Docker auto-creates a missing mount target as a DIRECTORY), so `setup.sh` CREATES it when there is no source `docker/` dir instead of `die`ing at step 6 of 10 under `set -euo pipefail`.

  **Every MUTATING endpoint acquires `_lifecycle_lock` with a bounded `acquire(timeout=_LIFECYCLE_LOCK_WAIT_S)` and answers a German 503 on failure — never a blocking `with`**: „Umgebung starten" holds it across a resilient image pull and nginx's `proxy_read_timeout` is 3600 s. `_LIFECYCLE_LOCK_WAIT_S` is DERIVED from `_PREVIEW_HANDOFF_TIMEOUT_S` (+1 s), since `stream_camera_preview` legitimately holds the lock across its handoff; background workers (`_run_update_job`) keep the blocking form and `start_robot_tier` pulls with `attempts=1`. `UPDATE_CHECK_TTL_S=600` is paired with `_UPDATE_CHECK_FORCE_MIN_INTERVAL_S=30` and an Origin check on `force` — `?force=1` bypassed the TTL and a no-cors GET sends no Origin, so a looping page amplified against the cloud `/version`.

### Robot control, cameras, env forwarding

- **ROS 2 `/leader/joint_trajectory` is the command rail.** The follower `arm_controller`'s JointTrajectoryController TOPIC interface (not its action server) is remapped there in `open_manipulator_bringup/launch/omx_f_follower_ai.launch.py`. Writers: teleop, the entrypoint quintic-sync/HOME, inference (`communicator.publish_action`), the Roboter Studio `_trajectory_publisher` (the SOLE workflow-side writer), and the collision monitor's recovery moves. **Anything publishing there drives the follower.**

- **Teleop collision e-stop — mixed-servo effort fractions, student-paced two-step recovery.**
  - **The force signal is MODEL-AWARE.** dxl11-13 are XL430-W250 (`Present Load` only — declaring `Present Current` on them aborts hardware init → follower dead on every rig, and `EDUBOTICS_COLLISION_ENABLED=0` does NOT help, the xacro being baked in); dxl14-15 are XL330-M288 (`Present Current`, ~1 mA/LSB). `collision_detector.effort_fraction_from_values()` normalizes both to a 0..1 fraction (Load/1000, Current/1750) and maps unsigned-published int16 back to signed FIRST (−5 arrives as 65531). The server image MUST apt-install `ros-jazzy-control-msgs` (without it the guard fail-opens silently) and MUST NOT contain `controller_manager_msgs` (Fast-CDR 2.x ABI mismatch — exit 127).
  - **Detection** (`safety/collision_detector.py`, pure/unit-tested): effort ≥ per-joint threshold AND |velocity| ≤ 0.05 rad/s, debounced 150 ms; firmware Overload bit (0x20) = immediate trip. Thresholds `EDUBOTICS_COLLISION_EFFORT_J1..J5` default 0.30/0.65/0.40/0.30/0.30; gripper (dxl16) excluded. Effort is exposed via a read-only `gpio_command_controller`. Tests: `tests/test_collision_detector.py`, `test_collision_monitor_contract.py`, `test_collision_discard_contract.py`, `physical_ai_server/test/test_collision_workflow_gate_c1_high6.py`; HW runbook `docs/COLLISION_ESTOP_WINDOWS_VALIDATION.md`.
  - **Gating**: OFF during inference (inside the detector), OFF during workflow + manual mode (`collision_monitor.py`); `COLLISION_SETTLE_WINDOW_S=0.5` re-arms on every re-torque and on mode exit. **Leader-gate**: a trip is DROPPED when `not leader_appears_active()`, keyed SOLELY on `/leader/joint_states` freshness (2 s), never on the in-process `EDUBOTICS_FOLLOWER_ONLY`. **`/leader/joint_states` delivery is SAFETY-LOAD-BEARING** (`test_press_trips_in_teleop_recording_mode` guards it).
  - **Recovery is student-paced (two-step) — the arm NEVER auto-homes**: trip → `/collision_flag=true` (leader-side broadcaster skips publishing; a 5 Hz watchdog re-asserts) → relax-in-place (delayed 0.15 s, re-sent ≤3×, commands the MEASURED pose) → in-progress episode discarded if recording → `COLLISION(7)` → modal Schritt 1 → `HOME_FOLLOWER(9)`: verified quintic glide (`COLLISION_HOMING(8)`) → `COLLISION_HOMED(9)` → Schritt 2 → `RESUME_TELEOP(8)`: STRICTLY refused until homed, leader proximity ≤0.30 rad, quintic resync, flag clears only after resync. A mid-recording collision resumes the SAME dataset; `FORCE_RESUME_TELEOP(10)` is the escape hatch and `EDUBOTICS_COLLISION_ENABLED=0` the one-variable rollback.

- **React dual build.** One codebase: `Dockerfile` (student, `REACT_APP_MODE=student`, `REACT_APP_ALLOWED_POLICIES=act`) and `Dockerfile.web` (Railway, `REACT_APP_MODE=web`, full policy list, `${PORT}`, 5 strict security headers re-declared in every nested nginx `location` **that sets any `add_header` of its own** — 3 of 4; `location /` sets none and correctly inherits the server-level five). `vercel.json` is an intentional empty kill-switch; `railway.json` intentionally has NO `buildArgs` — the buildId is stamped as a Railway service variable by `scripts/railway-deploy.sh` (restoring buildArgs re-introduces the `buildId='dev'` regression).

- **Native camera capture bridge (WSL2/Windows) — cameras bypass usbipd entirely**, because the WSL2 `vhci_hcd` bridge caps each forwarded UVC camera at ~6-10 Hz and jitters the 100 Hz Dynamixel reads. `EduBotics.exe` captures both cameras natively via OpenCV **MSMF** (`CAP_MSMF`; DSHOW rollback via `EDUBOTICS_CAMERA_BACKEND=dshow` — **enumeration and capture MUST share the backend** or index order scrambles the role pick; on MSMF set ONLY the MJPG fourcc, since width/height/fps requests force a ~12 s re-open into a slower mode) and streams JPEG over localhost TCP `127.0.0.1:5557` — **one connection per camera**, wire format `struct ">BIQ"` = `[u8 cam_id][u32 BE jpeg_len][u64 BE capture_ns][jpeg]`, cam_id 0=gripper, 1=scene, 2=phone (spelled identically in `camera_bridge.py` and `camera_ingest_node.py`). `camera_ingest_node.py` republishes as `sensor_msgs/CompressedImage` on `/gripper/image_raw/compressed` + `/scene/image_raw/compressed` (RELIABLE QoS — web_video_server drops BEST_EFFORT publishers silently). Camera roles in the `.env` MUST be `gripper`/`scene` (`generate_env_file` raises otherwise; `omx_f_config.yaml` hard-codes the topics). Cameras are NOT usbipd-attached (only the arms are). Gated by `EDUBOTICS_CAMERA_SOURCE` (auto: `native_bridge` on WSL2, `usb_cam` on Jetson/native, via `uname -r | grep -i microsoft`); **one-variable rollback** `EDUBOTICS_CAMERA_SOURCE=usb_cam`. The phone-as-3rd-camera path (HTTPS `:8444`, cert from `gui/app/scripts/new_phone_cert.ps1`) rides the same wire as cam_id 2 with a ~2 s staleness gate. Bridge delivery is event-driven and UNCAPPED — a former rate cap made the recorder re-grab duplicate frames. Unlike the 127.0.0.1-only `:8769` bridge, the phone receiver binds `0.0.0.0:8444` UNAUTHENTICATED by design (body-size gate only).

- **`usb_cam` is the Jetson / native-Linux path** (and the WSL2 rollback). Pixel format is host-gated: default `yuyv`; `entrypoint_omx.sh` flips the runtime default to `mjpeg2rgb` ONLY on WSL2 (vhci_hcd cannot sustain 2×YUYV → `VIDIOC_DQBUF: Select timeout` crash loop) unless the operator overrode it. **`raw_mjpeg` is unsupported** (usb_cam 0.8.1 falsifies the encoding — ros-drivers/usb_cam#346; green tiles).

- **Two identical-serial cameras (both `SN0001`) anchor by USB topology — three defenses.** (1) `wsl_bridge.list_video_devices()` dedups on `v4l2-ctl Bus info` and downgrades colliding by-id paths to by-path symlinks; (2) `entrypoint_omx.sh` hard-exits `[STOPP]` (exit 3) if both configured devices resolve to the same `/dev/videoN` — usb_cam path only, preventing a silent gripper↔scene swap that corrupts every dataset; (3) native-side, Windows PnP enumeration is filtered to `USB\`-rooted instance IDs.

- **`EDUBOTICS_*` env vars only reach the container if listed in a compose `environment:` list** — compose's `${VAR}` interpolation is config-time YAML substitution, invisible to the container runtime. Two CI jobs do different halves: `env-forwarding-guard` scans the entrypoint, `start-dockerd.sh`, `camera_ingest_node.py`, `edu6_arm_node.py`, `feetech_bus.py`, the `physical_ai_server` package and the overlay `.py`s for `EDUBOTICS_*` reads, but proves only that a name is forwarded **somewhere** (it unions all four composes), so it cannot see a key missing from one target or on the wrong service; `compose-env-parity` is the per-target, per-service check that can. `EDUBOTICS_FOLLOWER_ONLY` is forwarded to BOTH student containers for parity, but the server does NOT read it. **`EDUBOTICS_ROBOT_TYPE` has TWO readers in two different containers and must reach both**: the server (`__init__` → `robot_profiles.resolve`) AND `entrypoint_omx.sh`, which branches the whole arm bringup on it (`edu6_studio` → the Feetech driver instead of the OMX phases). It plus the five `EDUBOTICS_EDU6_*` knobs sit on the opi `open_manipulator` list, mirroring the student compose's order — but `compose-env-parity` compares per-service key SETS, so it fences PRESENCE, never order. Defaults: student + opi `omx_full`, Jetson `omx_follower`. The **Jetson compose forwards `EDUBOTICS_ROBOT_TYPE` (on `physical_ai_server`) + `EDUBOTICS_FOLLOWER_ONLY=1` and NONE of the five `EDUBOTICS_EDU6_*` knobs** — deliberate for a fixed single-follower OMX rig; it is outside `compose-env-parity`'s targets because it uses compose's bare pass-through form (`- ROS_DOMAIN_ID`), which that parser refuses by design.

### Robot type + the ArmProfile registry

### edu6_studio — the 6-DOF Feetech arm

A third profile: 7 × STS3215/STS3250 12 V on a Waveshare CH343P adapter (USB `1A86:55D3`, in-tree `cdc_acm` → `/dev/ttyACM*`), follower-only, **Roboter Studio ONLY** (`roboter_studio` the only true capability; `inferable` FALSE — the Inferenz tab renders, START refuses in German). Geometry from `follower_arm_modified_final1.urdf`. **Rig gates R3/R4/R5/R7/R8/R10 are open — read `docs/KNOWN-ISSUES.md` before trusting any physical claim here.** In SOFTWARE an Orange Pi can run the whole edu6 chain; **none of it is hardware-validated on a Pi.**

- **Joint 5 is ASYMMETRIC (−90°…+110°)**; the strict-vertical grasp family is `q4=0, q5=π/2−q2−q3`. The URDF number is a description — the servo-EEPROM `Min/Max_Position_Limit` written by `tools/edu6_provision.py` is the hardware floor.
- **`workflow/edu6_ik.py`** is closed-form, pure NumPy and EXACT. **World frame = URDF rotZ(π)**: `solve()` takes world xyz → URDF-native joints, `fk()` returns the world fingertip TCP at `_L_TOOL` 0.1724 m. Reach `reach_inner_m 0.09` / `reach_outer_m 0.21`.
- **Jaw/roll contract: `q6 = wrap(π − roll)`**, motion's UNCHANGED shared formula, fleet-wide 90° default. **q6 is FOLDED into [−90°, +90°]** (`_fold_jaw`, nearest-to-ZERO) — not a limit (joint6 keeps ±180° in EEPROM, jog and replay) but a free choice: the edu6 jaws are a parallel pair symmetric about this roll axis, so `q6` and `q6∓π` are the SAME grasp (the OMX's are NOT — a fold there shifts its grasp 3.3 mm). **The fold reference is fixed at 0 and must NEVER become the seed.**

- **`roll` and the roll JOINT are DIFFERENT NUMBERS on edu6 — never pass one for the other.** Both solvers expose **`roll_from_joints(joints)`** (OMX identity; edu6 `wrap(π − q6)`) and both call sites use it — `physical_ai_server.py`'s Cartesian jog and `motion.py`'s lift; the jog also PINS `arm_q[roll_idx] = arm[roll_idx]` after solving.
- **The GRIPPER channel is the end_gear servo angle in RADIANS**, 0 = closed … 1.75 = open. `object_catalog.parse_catalog` takes a per-family `gripper_close_range` — `(0.0, 1.75)` for edu6; the OMX negative-close rule is byte-identical when absent.
- **`docker/open_manipulator/edu6_arm_node.py` + `feetech_bus.py`** are plain COPYs byte-verified by `image_source_parity.sh`. **The arm mixes servo models BY DESIGN: joints 1/4/5/6/7 are STS3215 (Model 777), high-load joints 2/3 are STS3250 (Model 2825)** — register-identical, so every identity check accepts `feetech_bus.STS_ACCEPTED_MODELS` and records the ACTUAL per-servo model. **Never hardcode 777.**

- **`/joint_states` is created ONLY after the boot probe succeeds** — ping 1..7, accepted STS model, and the EEPROM provisioning FINGERPRINT (`Min/Max_Position_Limit` equal to the designed sign-aware window via the shared `feetech_bus.position_limit_window`, `Operating_Mode` 0) — so an unprovisioned/RMA-swapped/wheel-mode arm refuses to boot in German rather than boot-homing in a wrong frame at factory torque; the compose healthcheck is topic-existence-only. Consequence: **flipping `EDUBOTICS_EDU6_JOINT_SIGNS` requires re-provisioning.** The probe also refuses `Phase` bit 4 (multi-turn feedback) and a **boot `Present_Position` plausibility band**: more than `EDUBOTICS_EDU6_BOOT_POS_TOL_TICKS` (default 400 ≈ 35°, ≥4096 disables) outside its designed window — a documented no-op on joint4/joint6 (full-circle windows), and the 5 s retry loop self-heals. The 360° absolute encoder makes power-on positions valid with no homing move; the node self-homes (quintic, 3 s) to HOME `[0, 0.70, −2.40, 0, 0.70, 0]` + gripper 1.75.
- **The STS position loop is NOT wrap-aware** — a naive `goal − present` over the 0..4095 register, so a joint at tick 12 with the goal at 4090 drives the LONG way. Three guards, each with a `0` disable:
  - **Torque-ON edge refusal** — `EDUBOTICS_EDU6_EDGE_MARGIN_TICKS` (internal `EDGE_REFUSE_MARGIN_TICKS`, default 40; ≥2048 is rejected back to the default with a `[WARN]` — polarity is the INVERSE of `BOOT_POS_TOL_TICKS`). Every torque-ON TRANSITION is refused while ANY joint rests that close to the tick-0/4095 map edge, evaluated inside `_seed_goal_from_present_locked` gated on `self._torque_on and not self._bus_fault` — the SINGLE choke point, BEFORE any register write. **Never judge an already-torqued arm**; that broke jogging. The judged set is EVERY joint, never a "full-circle" subset, which misses joint2 `hi` and joint3 `lo`.
  - **Post-energise abort** — `EDUBOTICS_EDU6_TORQUE_ABORT_TICKS` (default 2048 = `TICKS_PER_REV // 2`, DEFINITIONAL not tuned; below 401 or above 4095 falls back with a `[WARN]`). Immediately AFTER writing `Torque_Enable = 1`, `_verify_after_energise_locked` re-reads `Present_Position` once and writes `Torque_Enable = 0` again (payload is the module constant `_TORQUE_OFF_PAYLOAD`), compared against the EEPROM-CLAMPED goal; `POST_ENERGISE_READ_ATTEMPTS = 2` gives one bounded retry so a dropped reply cannot de-energise a backdriving arm. Deliberately NOT gated on the OFF→ON transition, so it covers an optimistic `_torque_on` after a brown-out. An abort forces `_torque_on = False` inside the bus lock and drops the trajectory OUTSIDE it — **`_traj_lock` is never nested inside `_bus_lock`**.
  - **Commanded-tick clamp** — `EDUBOTICS_EDU6_GOAL_EDGE_MARGIN_TICKS` (default 128, ceiling **246** INCLUSIVE) in `rad_to_command_tick`, sole caller `_write_targets`. **`_seed_goal_from_present_locked` is deliberately EXEMPT**: it writes `Goal = Present` from a MEASURED tick to hold a limp arm still. The clamp provably cannot turn a non-wrapped error into a wrapped one (max |err| growth = `margin` ≤ 246 ≪ 2048).

  Residual: a joint forced across the edge while ALREADY torqued has no torque-on event to hang off, so only a continuous watchdog could catch it (assessed, NOT implemented, needs its own Rule §2 sign-off). `PHYSICAL_TORQUE_REFUSALS` + `BOOT_PHYSICAL_REMEDY_DE` are the ONE place declaring which kinds (`edge`, `wrongway`) skip the retry rail.
- **`set_torque(True)` seeds `Goal_Position = Present_Position` BEFORE writing `Torque_Enable`** (else the servo drives to its stale RAM goal at up to ~4.36 rad/s) and FAILS the torque-on on a failed read; boot torque-on retries `BOOT_TORQUE_ON_ATTEMPTS` (3). Boot-home arrival is VERIFIED (0.30 rad, arm joints only, one bounded re-send, soft German `[WARNUNG]`), and the verifier **yields the command rail**: every deliberate trajectory write goes through the single writer `_replace_trajectory`, which bumps `_traj_gen`, and the verifier bails rather than re-sending if that generation moved — two writers on one rail is a race.
- **Trajectories are REFUSED** while torque is off (re-torque also clears the buffer), under a latched bus fault, and whole on any non-finite value (min/max clamp NaN to the UPPER limit = a limit-seeking command); accepted ones execute by 50 Hz interpolating SYNC_WRITE.   Deletion is asymmetric BY DESIGN: teacher-initiated `DELETE /students/{id}` ATTEMPTS to erase the student's HF repos (skipping workgroup-shared ones); self-service `/me/delete` only cancels trainings and writes a `deletion_requested_at` that **nothing reads**. FIVE outcomes, not two: registry unreadable → **503**; account delete fails → 500 with nothing erased; `attempted > 0` all erased → 200 `hf_erasure_complete: true`; `attempted > 0` with failures → 200 `false` + `hf_failures` + `detail`; and **`attempted == 0` → 200 `hf_erasure_complete: FALSE`, `hf_failures: []`, German `detail`** saying the account is gone, no deletable dataset was registered, HuggingFace therefore never contacted. That last row is the honesty rule: **the endpoint must never claim an erasure after contacting HuggingFace zero times** — a student who never uploaded anything then gets a red toast rather than the green „Schüler gelöscht". `StudentRow.handleDelete` surfaces it on an explicit `=== false` — **keep it `=== false`**, because an older API sends a bare `{ok:true}`.

  Three fail-closed rules in `_delete_student_hf_artifacts` (returns `(failures, attempted)`, takes the caller's enumeration): the `datasets` registry is the ONLY source of the shared-repo skip list, so a failed read refuses the DATASET half entirely and names each refused repo; models are unaffected, a pooled training being skipped by its own row's `workgroup_id`; and `RepositoryNotFoundError` counts as success. **Migration 038**: `public.trainings.user_id` was the ONLY FK to `public.users` with no `ON DELETE` clause, so a student who had ever trained could not be deleted; the deliberate trade-off is CASCADE — the training history goes with the account. **A persisted erasure-retry queue remains the durable answer** for the one irreversible ordering left: a partial HF failure AFTER the account is gone has no student row to retry against, so the teacher's only remedy is the German `detail` telling them to delete by hand.

  - **The model is `workflow/arm_geometry.py`: one axis-aligned box per link in that link's OWN frame** (7 boxes, no meshes in the image), transformed by `Edu6IKSolver.link_frames()`; orientation-aware on purpose. `base_link` is a self-collision partner but EXCLUDED from the floor check. **`resolve_geometry` keys on the SOLVER's `backend`, and only `Edu6IKSolver` has `link_frames`** — that absence keeps OMX bit-identical.
  - **`workflow/home_planner.py` is the ladder**: direct → searched via → German refusal, the via SEARCHED over (j2, j3, j5). **The two legs are held to DIFFERENT bounds and that is load-bearing**: the lift leg may sit as low as the arm ALREADY is (monotone in FLOOR CLEARANCE), every later leg must clear the allowance.

Both are forwarded on the student AND opi composes.
  - **The driver refuses the boot-home glide the same way, and the refusal LEAVES THE ARM TORQUED** (`edu6_arm_node.boot_home_floor_decision` + the plain-COPY `edu6_geometry.py`, cross-checked against the server copy by `tests/test_edu6_geometry.py`, which asserts the box table and kinematic constants are EXACTLY equal). `start_boot_home` is the HIGHEST-EXPOSURE home path, and de-energising on a refusal would let a backdriving arm FALL. No via search in the driver. Unevaluable geometry FAILS OPEN.
  - **The workflow-side arrival check is warn-only at 0.30 rad**, as in the driver's boot-home verifier and the OMX Phase-3 verifier; it never re-sends (the driver owns that rail) and never raises.
  - Cartesian motion is CLEAN on edu6 (`move_to`, the approach/descend/lift corridor, `drop_at`); only `drive_to` from a HAND-GUIDED pose dips. **The OMX equivalent is UNMEASURED**.
- **Closed-form analytical IK only** (`workflow/ik_solver.py`) — NumPy FK + strict-vertical 5-DOF IK, θ0≈20.14°, elbow-up first; unreachable/out-of-limit/non-finite → `None` → German „Arbeitsbereich" error. NO numerical/PyKDL/TRAC-IK fallback. Reach annulus ≈ **0.04–0.28 m** (`_REACH_MIN/_MAX` = 0.0415/0.2825; the authoritative bound is `solve(...) is not None`). Solver + perception are built ONCE per lifetime.
- **Velocity floor** (`trajectory_builder._velocity_safe_duration`): 4.8 rad/s × 0.6 = 2.88 rad/s peak, quintic peak factor 15/8 — it only ever EXTENDS a segment. **Tempo** (run-bar 0.5/1/2 + per-move `GESCHWINDIGKEIT`, clamped `[0.5, 2.0]`, cloud rejects out-of-range) shrinks the duration BEFORE the floor re-extends it → a speed-up can never exceed the floor; a tempo-slowed segment is capped at `_MAX_STRETCHED_DURATION_S=4.5 s`.
- **Workspace floor**: `WORKSPACE_FLOOR_MARGIN_M=0.01`; any target below the (tilted-plane-aware) table → `'Zielpunkt liegt unter der Tischebene.'` Enforced in both solve paths.
- **Motion details that surprise**: the observe pose is `EDUBOTICS_OBSERVE_POSE` (joint radians, compose-forwarded, default HOME; malformed → HOME); `home` CARRIES the current gripper state; `drop_at` releases at `EDUBOTICS_DROP_HEIGHT_M` (0.05) above the table — deliberately higher than the grasp clearance, to clear container rims — and BISECTS its clearance to what is reachable. The grasp-split blocks re-solve each step WITHOUT the composite grasp's `motion_lock` atomicity (known, accepted).
- **A grasp with no room to approach from above is REFUSED, not reported as success.** `_solve_grasp_and_approach` bisects the hover to the largest reachable value; the floor is `_MIN_APPROACH_CLEARANCE_M = _APPROACH_BISECT_TOL_M` (2 mm). It raises **`GraspSkip`**, not `WorkflowError`; `grasp_object` marks the tag SKIPPED so a „Solange sichtbar" loop terminates, while a standalone „Greife" still fails loud. **`drop_at` passes `refuse_without_clearance=False`**.
- **The clamped-approach warning fires only below `_APPROACH_WARN_FRAC` (0.25) of the request**, since on edu6 ANY reduction is every grasp. Derived: `0.25 × approach_clear_m (0.060)` = `object_height_m − grasp_depth_m` on BOTH catalogs. Its reason is the arm's height over that point — NEVER „Ziel liegt am Rand des Greifbereichs".
- **„hebe an" after „Greife" is a reported no-op on edu6, and must never raise.** `_execute_pickup` already ends AT the hover, so a following `lift` gains 0 mm; it publishes nothing and says so in German. Its step 1 (`_solve_or_raise` on the CURRENT pose) is load-bearing: it refuses a lift from outside the strict-vertical family or below the table.
- **The three "rise as high as this arm can" bisects are ONE helper** (`_max_reachable_rise`): approach hover, release rim clearance, `lift`. It swallows the workspace-floor error — a no-op for the two approach callers, load-bearing for the release.

### Calibration (3 steps + optional check; wizard in `CalibrationWizard.jsx`)

- **Per-rig ChArUco intrinsics are MANDATORY — 20 frames** (`INTRINSIC_FRAMES_REQUIRED=20`), solved with `CALIB_RATIONAL_MODEL` (8-term; the ~102° wide lens overwhelms the 5-term default). Factory-default seeding is DELETED (**never re-add**). Any YAML with `source == factory_default` is skipped by both the manager and the runtime loader.
- **Scene extrinsic („single shot" to the student, a BURST in code)**: board against the 3D-printed L-jig → `EDUBOTICS_EXTRINSIC_BURST_FRAMES` (8) reads ~60 ms apart, ≥4 passing per-frame gates → MAD outlier rejection → SO(3) chordal-mean. Per frame: ChArUco `matchImagePoints` → **`cv2.SOLVEPNP_SQPNP` + `solvePnPRefineLM`** (ITERATIVE only as exception fallback; NOT `IPPE_SQUARE`) → compose with the jig-known `T_board_to_base` (yaw from `EDUBOTICS_BOARD_YAW_DEG`); reprojection/corner gates + `_check_extrinsic_orientation`, which CANNOT catch a 90°/180°/mirror error.
- **Touch-off („Tisch vermessen")**: torque-off, student taps ≥3 spread points → FK → least-squares plane (`z_table` + tilt); gates reject near-collinear/high-residual captures (`TABLE_TOUCH_MIN_MINOR_M=0.015`, residual ≤0.008, camera cross-check 0.12 m). **The per-tap verticality gate (12°) asks the SOLVER which axis the tool points along** (`ik.approach_axis_local` → OMX `+x`, edu6 `−z`, edu1 `+z`), forwarded to the manager as `get_approach_axis`; an absent/unusable provider falls back to the OMX `+x`, which is what the gate did before it existed. A hardcoded FK column is the OMX's answer and **90° wrong on both Feetech arms**, which rejected every correct vertical tap — and with no touch-off there is no `z_table`, so every grasp then refuses in German. **A ROTATING claw additionally needs the jaws CLOSED for the tap** (the TCP is the closed fingertip); that rides the additive `tool_tip_tracks_gripper` capability into an extra German step in `TableTouchStep`.
- **DUAL Z-KEY CONVENTION (don't conflate)**: `board_table_z` = camera-side table SURFACE height written by the extrinsic solve (the projection plane); `z_table` = MEASURED end-effector grasp height written ONLY by the touch-off (the descend target). **There is NO `z_table=0.0` fallback anywhere** — missing touch-off → grasp/`mark_destination` refuse in German („Tisch vermessen"). Never reintroduce it.
- **Optional ground-truth XY/yaw check („Genauigkeit prüfen")**: known-placed vs detected points → closed-form 2D similarity fit (`fit_xy_correction`, Umeyama) + circular-mean yaw bias, persisted as `xy_correction`/`yaw_bias_rad` in the extrinsic YAML and applied live. A mirror fit (`det(R)<0`) is REFUSED and persists nothing.
- `EDUBOTICS_FORCE_RECALIBRATION` (default ON) reports calibration as ABSENT until a touch-off completes in the current boot; a rig can opt out with `=0`.

### Simulation world + no-go zones

Every dot-source is `Test-Path`-guarded (Controlled Folder Access can silently truncate `{app}\scripts`). `install_prerequisites.ps1` deliberately does NOT gate on Windows edition (WSL2 works on Home; build ≥ 22000 only). The `.iss` launches the GUI via `explorer.exe` (+ `ChangesEnvironment=yes`) so it inherits the post-install PATH; `CurStepChanged(ssInstall)` runs `docker compose down` before new files land.
- **The finalize MARKER is a three-component, two-language contract, and its ENCODING is load-bearing.** `%ProgramData%\EduBotics\logs\edubotics_finalize.marker` is a NARROWER channel than the exit code, which still decides WHAT happened; the marker disambiguates exactly ONE cell — exit 0 (finalize's own `Test-DistroRegistered` passed) while the un-elevated GUI still cannot see the distro. WSL2 registers distros PER WINDOWS USER (`HKCU\...\Lxss`) and the installer is `PrivilegesRequired=admin`, so a DIFFERENT admin's `wsl --import` lands the registration in that admin's hive and no reboot helps. The contract: `finalize_install.ps1` writes all THREE shapes with `-Encoding UTF8`, carrying `user=<name>` on TWO of them (`started …` and the terminal `SUCCESS <iso> user=… distro=…`) while the `FAILED <iso>\n<problem>\n<next step>` shape has none, so a reader must tolerate its absence; `gui_app.py::_prompt_finalize_install::_marker_user` reads back as **`utf-8-sig`** and treats any U+FFFD in the parsed name as UNPARSEABLE rather than as a different account; `preflight_system.ps1` check 5 parses the same field. `%USERNAME%` may contain spaces, so the value runs to end-of-line except in the SUCCESS shape, where a reader must cut at `" distro="`. Names compare CASEFOLDED; a different account routes to the per-account German remedy, the same account or an unreadable marker to the generic one. **Both the encoding and the cut cost a wrong accusation on the SAME account, and NEITHER is catchable by the U+FFFD rule** — a mis-encoded or uncut name comes back as VALID characters that simply never casefold-match. `test_gui_install_lifecycle.py::PreflightAccountScopeTest` compares the marker PATH, the U+FFFD rule, the declared encodings and the `" distro="` delimiter; the casefold-vs-`-ine` comparison and the `user=` key are still uncompared (`docs/KNOWN-ISSUES.md`).

### Deploy-workflow hardening invariants

- Health gates verify IDENTITY, never a bare 200 (commit sha / buildId).
- **docker-publish**: native per-arch runners (amd64 `ubuntu-latest`, arm64 `ubuntu-24.04-arm`, NO QEMU; `fail-fast: false`); `jlumbroso/free-disk-space` on every leg except arm64 (amd64 + opi); `--no-cache --pull`; dirty-tree refusal; buildkit routes docker.io through `mirror.gcr.io`; smoke-test pulls the **GHCR** images and asserts arch, bundle env, amd64 **< 7 GB of UNCOMPRESSED layer bytes**, then runs `image_source_parity.sh`. That ceiling is measured with **`docker image history --human=false`, deliberately NOT `docker image inspect .Size`**: `.Size` is uncompressed layer diffs on overlay2 but **COMPRESSED** under the containerd snapshotter (the same image reads 2.626 GB instead of 7.53 GB), which makes the gate INERT rather than merely loose — a CUDA-back image compresses to ~5.6 GB and would pass. The opi ceiling stays 11 GB on `.Size` and is deliberately NOT synced: that image was never CI-measured, so tightening it without also moving it to `history` would make it silently store-dependent. Tag set: `:latest` (main), `:<sha>`, `:<short-sha>`, and on tags `:X.Y.Z` + `:X.Y` (both ALWAYS re-pointed on both registries). GHCR retags fatal, Hub best-effort.
- **Concurrency differs per workflow**: `ci.yml` cancels in-flight PR runs (never main); `docker-publish.yml` never cancels (non-atomic pushes) and runs TWO lanes — a per-tag release lane vs one shared `main` lane, keyed on `github.ref`, **NOT** `github.event_name`, which inside a reusable workflow reports the CALLER's event and would collapse both lanes. `release.yml` cancels on a newer tag; `supabase-migrate.yml` serializes on a project-scoped group. Timeouts: docker build 60 min, retag 45 min, installer 90 min.
- **Caller-permissions-superset rule**: each `release.yml` caller job must superset its callee's declared permissions, or GH `startup_failure`s the run. Change both in one PR.
- Every checkout: `persist-credentials: false` (44 of 44). All third-party actions SHA-pinned. Template injection defused via env indirection. Inno Setup pinned 6.7.0. `softprops/action-gh-release` needs the explicit `token:` under `workflow_call`.
- **Secrets consumed by CI** (10 + auto `GITHUB_TOKEN` + repo var `SUPABASE_BRANCHING_ENABLED`): `DOCKERHUB_USERNAME/TOKEN`, `RAILWAY_TOKEN`, `SUPABASE_ACCESS_TOKEN/DB_URL/PROJECT_REF/URL/SERVICE_ROLE_KEY/ANON_KEY`, `REACT_APP_CLOUD_API_URL`. `MODAL_TOKEN_ID/SECRET` are NOT used by any workflow — they exist for the operator's manual `modal deploy` only.

## When to ask the user

Act autonomously on: reading files, editing code with low blast radius, running local tests/lints, building images locally, spawning sub-agents for research.

**Ask first** for:

- `git push` (and never force-push to `main`)
- `wsl --unregister EduBotics` (destroys the VHDX → volumes `ai_workspace`, `huggingface_cache`, `edubotics_calib` gone)
- `docker compose down -v` or `docker volume rm` of `huggingface_cache` / `edubotics_calib`
- Force-push, `git reset --hard`, `git clean -fd`, `--no-verify`
- Modal `cancel` on a running training (charges credit)
- `supabase.auth.admin.delete_user` calls
- Rotating production secrets, editing CI/CD config
- Changing safety-critical paths (torque-disable, sync-verification tolerance, ownership assertions, Dynamixel current limits, the manual-mode arbiter/lock order, collision gating, the edu6 torque-on guards, `LINK_RADIUS_M + ZONE_MARGIN_M`)

- Touching `start_training_safe` / `get_remaining_credits` / `adjust_workgroup_credits` semantics (the workgroup credit pool is load-bearing; regressions are silent over-spend or refused trainings)
- Reintroducing software-side inference safety guards (Rule §2)

## Spec-before-code for multi-layer features

Any feature touching **more than one of the 10 layers** gets a one-page dated spec+plan in `docs/plans/` BEFORE the first commit, with an explicit **"Non-goals (this round)"** section carrying trigger conditions. `docs/plans/` is **gitignored and throwaway** — delete the page once the feature lands. Durable invariants graduate into THIS file; dated narratives go to `docs/CLAUDE-CHANGELOG.md`; living status goes to `docs/KNOWN-ISSUES.md`; the plan never claims to be authoritative.

## When in doubt

The single source of truth is **the code**. This file describes invariants at the time it was written. Verify against `git log` and the current file when stakes are high. If this file disagrees with the code, fix this file in the same change — the whole point is that it stays in sync.

When you find an obstacle, **find the root cause** instead of bypassing it (never `--no-verify`, never `@pytest.skip`, never short-circuit an `apply_overlay` sha256 assertion that is telling you upstream renamed something).
