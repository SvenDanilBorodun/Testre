## What this is

**EduBotics** — a vertically integrated educational stack for teaching Physical AI on **ROBOTIS OpenMANIPULATOR-X** arms to **German-speaking students**. Student lifecycle: install `.exe` → setup wizard → record demos (ROS 2 teleop) → train policy (Modal cloud GPU) → inference (local or classroom Jetson) → optional **Roboter Studio** (Blockly authoring + AprilTag-marker perception + manual arm control).

Students run Windows 11 PCs (no GPUs). Training runs on Modal (NVIDIA L4; A100 for VLA policies). The product ships as a single `.exe` that installs a bundled WSL2 Ubuntu 22.04 distro named `EduBotics` containing Docker Engine + three containers — **no Docker Desktop**. Images are pulled from **GHCR (primary) with Docker Hub fallback**. A teacher/admin web dashboard is a separate Railway deploy. Installs are online-only (the offline bundle path was removed in v2.8.2).

Single git repo, no submodules. ROBOTIS upstream (`open_manipulator/`, `physical_ai_tools/`) is absorbed as plain directories.

## Six non-negotiable rules

These exist because we paid for the lesson. Don't undo without explicit user agreement.

### 1. German UI / English code

- **German** for everything a student/teacher/admin reads: tkinter labels, React UI, `detail` fields on API errors, log strings users see, toast messages. Use literal `ä ö ü ß` (some legacy files use `Schueler`; new code uses `Schüler`).
- **English** for everything the maintainer reads: code, comments, docstrings, internal log lines, JSON keys, function names, commit messages.
- CI guards: `german-strings-lint` (transliterations in `[FEHLER]`/`[WARNUNG]`/`[STOPP]` lines + an AST pass over cloud-API `detail=`/`error_message=` AND pi_agent `message=` — the pi_agent JSON `{"ok","message"}` surface is student-facing; `# english-ok` is the escape hatch).

### 2. Hardware safety lives in xacro + entrypoint, not software overlays

Software-side inference safety envelopes (NaN/Inf guard, joint clamp, velocity cap, stale-camera halt) were removed deliberately in the 2026-05 stripdown to fix recording↔inference asymmetry. Inference runs upstream `predict()` raw. The remaining protection is hardware-enforced or warning-only:

- **Xacro Dynamixel limits** (`omx_f.ros2_control.xacro`, `omx_l.ros2_control.xacro`): restrictive position limits exist ONLY on dxl12/dxl13 — dxl11 (Op Mode 4) and dxl14/15 are full-register-range, and the leader xacro has NO position limits at all (it is torque-free). The real safety floor is the gripper current limits (follower dxl16 `Current Limit 350` + `Goal Current 350` + `Shutdown 21`, Op Mode 5; leader trigger 300 mA).
- **ros2_control YAML**: 100 Hz; JointTrajectoryController in-flight `trajectory` tolerance 2.0 rad (effectively off — the safety floor is the Dynamixel current limit, not the controller tolerance), `goal` 0.10 rad arm / 0.50 rad gripper, `goal_time` 5.0 s. These were bumped from upstream's tight values on 2026-05-18 because the upstream values aborted the 3 s quintic boot-sync mid-flight → compose restart-storm (see the inline comment in `overlays/omx_f_hardware_controller_manager.yaml`).
- **Torque-disable on shutdown** in `docker/open_manipulator/entrypoint_omx.sh::disable_torque()` — registered as `trap … SIGTERM SIGINT EXIT`, so `set -e` aborts (which exit via `exit`, not a signal) are covered too. The leader path uses the namespaced `/leader/omx_l/set_dxl_torque`.
- **Phase-3 post-sync verification** in `entrypoint_omx.sh` (the script's own phases: 1 leader, 2 follower, 3 quintic sync + verify, 4 cameras) — 0.30 rad tolerance, arm joints only, soft-fail `[WARN]` (a hard exit looped compose restarts). Requires ≥50 % of commanded delta traversed to distinguish a dropout from finishing lag. Two hard-exit paths remain: the camera-disambiguation guard (exit 3) and `wait_for_device()`'s 60 s serial-port timeout (exit 1).
- Recording-side QUALITY guards (stale camera, camera-Hz deficit — warn threshold 0.9×fps) are warning-only; but a topic-availability timeout, a msg-conversion error, or an add_frame failure (the `record()` call is exception-guarded — an uncaught raise would kill the whole node) hard-stops the recording timer, and the streaming frame-drop guard DISCARDS the in-flight episode and re-records it (no retry cap) — the session completes, that attempt doesn't.
- **The leader ARM JOINTS 1-5 are torque-free/limp by design** — no gravity compensation is spawned (`Torque Enable 0`, Goal/Present Current interfaces commented out in `omx_l.ros2_control.xacro`; broadcasters only for those joints). The leader GRIPPER TRIGGER is NOT limp: `trigger_position_controller` (`position_controllers/JointGroupPositionController`) + a 50 Hz `ros2 topic pub` of −0.7 rad simulate spring resistance under the 300 mA current cap. The `docker/open_manipulator/Dockerfile:51` "enable gravity compensation" comment is stale, and so is `collision_monitor.py:50`'s claim that the gravity-compensation controller consumes `/collision_flag` (it is never spawned) — the xacro + launch files are the truth.

**ONE sanctioned exception (user-approved): the teleop force/collision e-stop** — scoped to teleop/recording ONLY. It is gated OFF during inference (inside the detector via `mode_is_inference`), and gated OFF during workflow and manual mode (in `collision_monitor.py` — one combined `if on_workflow or on_manual` gate; the manual-mode half is the one sanctioned Rule-§2 scope change from v2.11: follower-only Roboter Studio has no leader and hand-guiding presses the arm at ~0 velocity, indistinguishable from a collision). It never modifies samples — a trip DISCARDS the in-progress episode, it does not filter or clamp. Full mechanics under "Critical architectural choices".

If you genuinely need to reintroduce any OTHER software safety guard that modifies the pipeline, **stop and ask the user**.

### 3. The shipped image must reflect the repo — physical-ai-server is COPY-wholesale; open-manipulator still overlays

**physical-ai-server: COPY-WHOLESALE, no overlays.** The image's `physical_ai_server` package is a verbatim copy of `physical_ai_tools/physical_ai_server/` (staged as `pkg_src/` by `build-images.sh` — excluding `test/`, the three base Dockerfiles (`Dockerfile.amd64`/`.arm64`/`.arm64cpu`), `CHANGELOG.rst`, bytecode — then `rm`'d + `COPY`'d + re-`colcon`'d). "Image == repo HEAD" is true by construction: edits, new files AND deletions all propagate. The old overlay model silently dropped edits (the v2.5.0 `training_manager.py` regression → node crash). The Dockerfile asserts the stripped `safety_envelope.py` AND the dead `training/trainers` + `evaluation` trees never re-enter (`build-images.sh` re-checks the staged `pkg_src/` independently before the build), and four build-time smoke gates must pass: policy imports + `CODEBASE_VERSION == 'v3.0'`, node import, `control_msgs` gpio import, and a functional cv_bridge rgb8 decode.

**open-manipulator: STILL the overlay model.** `apply_overlay()` in `docker/open_manipulator/Dockerfile` does sha256 pre/post verification over the **7-file** chain (`omx_f.ros2_control.xacro`, `omx_l.ros2_control.xacro`, `omx_f_follower_ai.launch.py`, `omx_l_leader_ai.launch.py`, both controller-manager YAMLs, `camera_usb_cam.launch.py`); build aborts on a missing upstream target. Kept (not converted) because open_manipulator contains C++ `ros2_control` packages where a full re-`colcon` is heavy/risky. When adding an open_manipulator overlay you **must** add it to the chain with a unique path filter — without that the source edit never reaches the image. Standalone scripts (`identify_arm.py`, `camera_ingest_node.py`, `calibrate_collision_currents.py`) are plain `COPY`s, not overlays.

**Both are guarded by `image-source-parity`** (`.github/scripts/image_source_parity.sh`, run per-arch in `docker-publish.yml::smoke-test`): physical-ai-server asserts byte-identity (`diff -r`); open-manipulator asserts every overlay present by sha256. The parity script mirrors `build-images.sh`'s staging exclusions — change one, change both (the exclusion list also drops `Dockerfile.arm64cpu`; the `-opi` flavor rides the same flavor-neutral gate).

LeRobot itself is **not** overlaid — pip-installed from PyPI at `0.5.1` (Rule §5). `patches/fix_server_inference.py` is retained ONLY so CI `overlay-guard` can test the patch harness — it does nothing for the current build.

The server **amd64 BASE image is pulled, never built** — `build-images.sh` resolves `robotis/physical-ai-server:amd64-0.8.2` via `docker manifest inspect`. `Dockerfile.amd64` is forward-compat scaffolding (keep its pins in lockstep anyway, Rule §5).

**The other TWO server bases are ours, and NO workflow builds them.** There are two build triggers, both hand-run: `BUILD_BASE_ARM64=1 PLATFORM=arm64` → `Dockerfile.arm64` (Jetson) and `BUILD_BASE_OPI=1 PLATFORM=opi` → `Dockerfile.arm64cpu` (Orange Pi CPU base). Grep for `BUILD_BASE_OPI` in `.github/` and you get nothing — every CI build merely *resolves* the tag pinned at `build-images.sh` (`physical-ai-server-opi-base`, `physical-ai-server-jetson-base`, `open-manipulator-jetson-base`). So **editing `Dockerfile.arm64cpu` / `.arm64` ships nothing on its own, silently**: the release goes green on the previously-published base while the edit sits in git looking landed. Rule §5 routes people straight into these files to bump LeRobot pins, which is what makes this load-bearing rather than trivia. Two fences: `ci.yml::base-version-guard` fails any non-comment edit to a base Dockerfile whose `PAS_BASE_IMAGE` tag didn't move in the same commit (comment-only edits are exempt), and `docker/bump-upstream-digests.sh` reports all three self-built pins + their upstream `FROM`s and exits non-zero on a tag that was never pushed. The rebuild itself is a Rule §6 manual step — see there.

### 4. Service-role key bypasses RLS — authorization is your job

Every Supabase query in `cloud_training_api/app/` runs as **service-role** via `app/services/supabase_client.py::get_supabase()` (lazy singleton, fails fast at startup if secrets empty). RLS policies exist for defense-in-depth (anon-key/Realtime read paths) but are dormant under service-role.

Every endpoint that touches another user's data **must** call one of the ownership asserts (the teacher/workgroup/workflow helpers raise a German 404 — never 403 — to avoid existence leakage; the Jetson pair deliberately differs: `_assert_classroom_member` raises 403 (membership gating, not resource existence) and `_assert_jetson_owner` raises 404-or-**410 „Lock verloren"** to signal a lost claim; `_assert_workgroup_in_classroom` can also 400):
- `_assert_classroom_owned` / `_assert_student_owned` / `_assert_entry_owned` / `_assert_workgroup_in_classroom` (in `routes/teacher.py`)
- `_assert_workgroup_owned` (in `routes/workgroups.py`)
- `_assert_workflow_owned` (write) / `_assert_workflow_visible` (read ladder: owner OR group sibling OR classroom template) (in `routes/workflows.py`)
- `_assert_classroom_member` / `_assert_jetson_owner` (in `routes/jetson.py`)

**One missed assertion = silent IDOR.** RLS will not catch it. Writes additionally re-scope the query (`.eq("owner_user_id", …)`) as belt-and-suspenders. Dataset registration is enforced atomically in Postgres instead: `register_dataset_safe` RPC (migration 026, `FOR UPDATE` on the caller's users row, HF-author anchor, P0034 → 403). The workflow read-visibility ladder is implemented FOUR times in `routes/workflows.py` (`_assert_workflow_visible`, inline in `list_workflows` + `get_workflow`, ad-hoc in `clone_workflow`) plus near-twin resolvers in `services/workgroups.py` — semantics changes must touch every copy.

The Modal worker uses the **anon key** + per-row `worker_token` (UUID). Its only DB write surface is the `update_training_progress(p_token, …)` RPC, guarded by the terminal-state `WHERE status NOT IN ('succeeded','failed','canceled','cancel_requested')` clause (migrations 010 + 032) — a late worker write is a P0001 no-op, and that P0001 is also the worker's in-band cancel signal (it kills the training subprocess, freeing the GPU). RPC GRANTs are asymmetric by design: `update_training_progress` is granted anon+authenticated (the worker), `register_dataset_safe` is service-role-ONLY. `update_training_progress` is deliberately absent from the boot schema probe (its defaulted 8-arg signature is overload-ambiguous) — drift there is invisible to `/health`.

### 5. Don't introduce drift between the LeRobot pinning sites

The LeRobot **version pin `0.5.1`** must agree across:
- `robotis_ai_setup/modal_training/modal_app.py` constant `LEROBOT_VERSION`
- `physical_ai_tools/physical_ai_server/Dockerfile.amd64` (`pip install "lerobot[pi,smolvla,peft]==0.5.1"` — the extra is `pi`, not `pi0`)
- `physical_ai_tools/physical_ai_server/Dockerfile.arm64` (same line under the Jetson AI Lab pip index)
- `physical_ai_tools/physical_ai_server/Dockerfile.arm64cpu` (Orange Pi 5 Pro CPU base — stock `ros:jazzy-ros-base`, plain PyPI; same `lerobot[pi,smolvla,peft]==0.5.1` line, but torch is PINNED EXPLICITLY (`torch==2.7.0` + `torchvision==0.22.0`) **before** lerobot because this base inherits no torch and `lerobot 0.5.1` allows `torch<2.11` — an unpinned resolve pulls 2.10.x and breaks the one-torch-2.7.x surface; replicates the `numpy==1.26.4` + `scipy>=1.14.0,<1.18` caps below)

(The thin overlay `docker/physical_ai_server/Dockerfile` carries the same install and is what CI actually builds on top of the pulled base — keep it in lockstep too.) Bumping LeRobot is a **one-PR multi-site change**. `meta/info.json` `codebase_version: "v3.0"` and the Modal preflight `EXPECTED_CODEBASE_VERSION="v3.0"` (`training_handler.py`) are **derived** consts that move together with the pin.

**Hard dependency caps — never widen silently:**
- `numpy==1.26.4` force-reinstalled AFTER lerobot in the server images — ros-jazzy-cv-bridge's boost `.so` is compiled against NumPy 1.x; numpy 2.x SEGFAULTs the rgb8 decode path (uncatchable, kills the node). A build-time functional cv_bridge decode gate proves it.
- `scipy>=1.14.0,<1.18` in all four server Dockerfiles (`Dockerfile.amd64`/`.arm64`/`.arm64cpu` + the thin overlay `docker/physical_ai_server/Dockerfile`) — scipy 1.18.0 dropped numpy-1.x support (`np.long`). Never widen back to `<2.0.0` while numpy is floored at 1.26.4.

**One PyTorch surface (torch 2.7.x), three CUDA channels — by design.** Modal worker: `nvidia/cuda:12.6.1-devel` + `torch==2.7.0` cu126 wheels. Student amd64 image: base ships torch 2.7.0+cu128, then the build-arg-gated `SLIM_CUDA=1` step (amd64 only, set by `build-images.sh`) swaps to **torch 2.7.0+cpu** and drops CUDA (~16 GB → ~5-6 GB after `flatten_image`'s `docker export | import` — the rm alone only writes whiteouts; the same `flatten_image` slims the Orange-Pi `-opi` server, which is CPU-torch from the start). Jetson arm64: keeps GPU torch 2.7.0+cu128 (SLIM_CUDA defaults 0, never flattened). CPU-only students are safe: `inference_manager.load_policy()` returns a German „needs GPU" error; recording never loads a policy; training is cloud-only.

### 6. CI/CD deploys

Seven workflows in `.github/workflows/` are the canonical path:

- `ci.yml` — 24 validator jobs on every push/PR to `main` (see CI guardrails).
- `supabase-migrate.yml` — W1. Migrations via `supabase db push --linked --include-all` (password extracted with `urllib.parse`, never sed) against project `fnnbysrjkfugsqzwcksd`. Its concurrency group is PROJECT-scoped (`supabase-migrate-production`) so a tag release and a direct `main` push serialize instead of racing the DB; a `workflow_dispatch` `rollback` job applies `rollback/<name>.sql` via psql in CI (manual `psql -f` is the fallback, not the only path).
- `railway-deploy-cloud-api.yml` — W2. Read-only schema probe → `railway up` → `/health` gate asserting `body.commit == github.sha` (never a bare 200 — Railway blue-green keeps the old pod serving 200).
- `railway-deploy-teacher-web.yml` — W3. Placeholder-build validate → `railway up` via `scripts/railway-deploy.sh` → `/version.json` gate asserting buildId contains the SHA.
- `docker-publish.yml` — W4. Builds + **dual-pushes 8 images** (3 amd64 + 2 `-jetson` arm64 + 3 `-opi` arm64 — Orange Pi 5 Pro CPU flavor, incl. `physical-ai-manager-opi`) to **GHCR primary (`ghcr.io/svendanilborodun/*`) + Docker Hub fallback (`nettername/*`)**. The `-opi` repos are threaded through the build+smoke matrices, both hardcoded retag/dual-push `REPOS` lists, and a separate opi size gate — but opi is DECOUPLED from the core release: its build + smoke-test matrix legs are `continue-on-error: matrix.platform == 'opi'`, the opi build leg uploads an `opi-build-success` marker artifact (containing the run's sha) as its LAST step, and the retag job retags opi ONLY when that marker exists AND matches `github.sha` — never off an existence probe of the mutable `:latest` (a failed/partial opi build must not promote the PRIOR release's opi images under new semver tags). The dual-push-integrity step warns (never fails) for opi repos in BOTH the missing-image and the mismatch branches, and opi GHCR retags are best-effort (`::warning`), so no opi-only transient can block the amd64/Jetson GHCR publish. Fires on `main` pushes (`:latest`), `workflow_call` (W4), and `workflow_dispatch`. **Its standalone tag-push trigger was REMOVED** (2026-06-11) — on a tag, only `release.yml` W4 builds. Build order inside W4: `build-images.sh` pushes to Docker Hub first (`REGISTRY=nettername` in the build job); the `retag` job then creates the GHCR tags FROM Hub via `imagetools create` — GHCR is the consumption primary, not the build primary. A `workflow_dispatch` input `cleanup_dirty_tags` runs `tools/docker-hub-cleanup.sh --execute --only-dirty` as a CI job.
- `release-installer.yml` — W5. Windows `.exe` build; `workflow_call`-only + `workflow_dispatch` (no tag race).
- `release.yml` — top-level dispatcher on `vX.Y.Z` tags. A **`version-preflight` job runs FIRST on tag pushes**: it hard-fails the whole release when the tag ≠ the repo `VERSION` file (W6 advertises the TAG while the tarball/installer bake the FILE — a mismatch would put every Pi AND every Windows GUI into an infinite forced-update loop whose skip button never appears, because every update "succeeds" without advancing the anchor). W1 `needs` it; W2 additionally checks its result explicitly (W2's `always()` tolerates a skipped W1). **Golden order W1→W6**: W1 supabase → W2 cloud-api → W3 teacher-web → W4 docker → W5 installer → **W6 `publish-gui-version`** (an inline job, not a separate file: sets Railway `GUI_RELEASE_REPO`/`GUI_DOWNLOAD_URL`/`GUI_INSTALLER_SHA256` then `GUI_VERSION` last, AFTER the `.exe` is attached — race-safe auto-update advertising; tag-push only). A W5-adjacent `pi-agent-tarball` job attaches `edubotics-pi-agent.tar.gz` (built from `robotis_ai_setup/pi_agent/`, top-level `pi_agent/`, with the repo-root `VERSION` baked in as `pi_agent/VERSION` — the anchor the agent self-update reports its version from, **plus a generated `pi_agent/docker/versions.env` pinning `IMAGE_TAG=<VERSION>`** — the Pi's equivalent of the `docker/versions.env` the Windows installer payload has always baked — **plus the TRACKED `pi_agent/docker/docker-compose.opi.yml` twin**; all three are gated: the tarball must contain each file, the two version files must equal the repo `VERSION`, and the packaged compose must `cmp` equal to `robotis_ai_setup/docker/docker-compose.opi.yml`. The post-`tar` cleanup deletes only the GENERATED `versions.env` — `rm -rf …/pi_agent/docker` would take the tracked twin with it) to the GitHub Release, and W6 also publishes `PI_AGENT_SHA256` before the `GUI_VERSION` flip — the hash of that exact tarball, emptied BOTH on a hash failure AND when any of the three `-opi:<VERSION>` images is anonymously pullable on NEITHER GHCR nor Docker Hub — the same GHCR→Hub-twin order the Pi's own pull path uses, so the availability criterion matches the apply criterion (an empty hash ⇒ the Pi advertises NO self-update, so it can never pin a release whose `-opi` images never published; a Hub-only release advertises with a `::warning` naming the GHCR gap); `pi-agent-tarball` is an ORDERING-only `needs` of W6 (so W6 hashes the exact attached asset) but W6 gates ONLY on `installer` success — a Pi-tarball hiccup never withholds the Windows `.exe` advertisement (`PI_AGENT_SHA256` degrades empty-on-failure, and an empty hash means the Pi agent advertises NO self-update — `update_checker` refuses hash-less updates, aligning the availability criterion with the apply criterion; it does NOT fall back to a Content-Length-only check like the `.exe` path). W6's `/version` verify loop round-trips the Pi fields too: `pi_agent_download_url` present and `pi_agent_sha256 == PI_SHA` when non-empty.

Nothing in CI builds them (see Rule §3): if a release touches `physical_ai_tools/physical_ai_server/Dockerfile.arm64cpu` or `Dockerfile.arm64`, rebuild + push the base and bump its tag in `build-images.sh` BEFORE the tag, or **the release silently ships on the old base**:

```bash
cd robotis_ai_setup/docker
BUILD_BASE_OPI=1   PLATFORM=opi   ./build-images.sh   # Dockerfile.arm64cpu → physical-ai-server-opi-base
BUILD_BASE_ARM64=1 PLATFORM=arm64 ./build-images.sh   # Dockerfile.arm64    → the two Jetson bases
./bump-upstream-digests.sh                            # verify every pinned base resolves
```

Both `PLATFORM=opi` and `PLATFORM=arm64` build the manager/thin layers first, so `SUPABASE_URL`, `SUPABASE_ANON_KEY` and `CLOUD_API_URL` must be exported or the script aborts before it ever reaches the base build. `ci.yml::base-version-guard` fences the tag bump at review time; it cannot check that you actually pushed the image — `bump-upstream-digests.sh` (or the release's own manifest resolve) is what catches that.

For the remaining surfaces, manual `railway up`, `psql -f`, and a full `build-images.sh` run are EMERGENCY-only. Note the narrow exception inside that rule: the `BUILD_BASE_*` invocations above are a *workstation push by design*, and the only path that exists for those three images — "never push from a workstation" governs the student-facing thin images (`open-manipulator*`, `physical-ai-server*`, `physical-ai-manager*`), which CI owns. CI refuses to build from a dirty tree, so `*-dirty` tags can never reappear.

**Applying migrations:** `supabase db push` works; Claude's MCP `apply_migration` also works, but MCP re-stamps the version prefix into the ledger — **rename the on-disk file to the MCP-stamped value afterwards** or the next `db push` sees ghost-unapplied migrations (the doubled-prefix filename on migration 026 is this scar, fossilized).

## Critical architectural choices (don't undo silently)

- **No Docker Desktop.** Docker Engine runs inside the bundled WSL2 distro `EduBotics`. GUI invokes Docker via `wsl -d EduBotics -- docker …` (`_docker_cmd()` in `gui/app/docker_manager.py`) — never bare `docker`. USB reaches the distro via `usbipd attach --wsl EduBotics --busid X` (5.x positional form; the 4.x `--distribution` form is rejected), always resolved to an **absolute path** via `usbipd_resolver.find_usbipd()` (post-install PATH race: the Inno-launched GUI inherits explorer's pre-MSI PATH). Docker pinned `5:27.5.1-1~ubuntu.22.04~jammy` + containerd `1.7.27-1` via `apt-mark hold`, `containerd-snapshotter: false` — Docker 29.x snapshotter corrupts multi-layer pulls on WSL2 custom rootfs. `start-dockerd.sh` (the distro's `[boot]` command — NOT systemd, which is unreliable on custom-imported rootfs; `wsl.conf` also sets `appendWindowsPath=false`, so the script exports its own PATH) modprobes the serial/UVC kernel modules + starts udev + watchdogs dockerd on every boot; its modprobe list must stay in sync with `device_manager.diagnose_usb_environment`, and `device_manager.self_heal_wsl_serial` is the GUI-side counterpart at scan time. Installer Step 0 (`migrate_from_docker_desktop.ps1`) actively removes a pre-existing Docker Desktop (uninstall + unregister `docker-desktop*` distros + strip its autostart Run key; one-shot `.migrated` flag). usbipd-win itself is a pinned 5.3.0 MSI, SHA256-verified at install — a `RELEASE_PIN_NEEDED` sentinel in the `.iss` hard-fails `install_prerequisites.ps1` if a release forgets to update the pin.

- **The GUI is the SOLE owner of the container lifecycle.** The stack comes up ONLY on "Umgebung starten" — never on GUI launch or distro boot. Two enforcement points: (1) every student-stack service in `docker-compose.yml` is `restart: "no"` (`unless-stopped` resurrected the stack the instant dockerd started, holding the Dynamixel serial bus before any arm scan); (2) `gui_app.py::_run_prerequisite_checks_body` calls `docker_manager.ensure_environment_stopped()` **immediately after the dockerd-ready gate and BEFORE the rootfs-mismatch gate** — that gate `return`s, and a rootfs mismatch MEANS the distro is old and was never re-imported, i.e. exactly the population whose persisted container configs still carry `restart: unless-stopped`; any new early return placed after a distro boot must sit BELOW the teardown. `_run_prerequisite_checks` is now a re-entrancy guard (`_prereq_in_progress`, `try/finally`) wrapping that body, because four call sites re-run it on worker threads and two concurrent runs meant two 15-30 min pulls racing two prunes. `_scan_arms` calls it first too — `identify_arm.py` opens the same `/dev/serial` ports a live 100 Hz controller holds, so a running stack makes BOTH arms fail to identify. The GUI also runs `start_keepalive()` for the session (WSL2's ~60 s vmIdleTimeout would otherwise kill dockerd + the manager container mid-session; `atexit` reaps it). Note: the **Jetson** compose deliberately uses `restart: unless-stopped` — the agent owns that lifecycle differently; don't conflate the two. The **Orange Pi (`-opi`) compose is a second sanctioned exception**: `physical_ai_manager` runs `restart: unless-stopped` and the pi-agent brings it up at boot, because the manager *is* the setup wizard on a Pi — a freshly booted Pi must serve the UI with the robot tier down. Only the manager tier is exempted; `open_manipulator` + `physical_ai_server` stay `restart: "no"` and come up only on „Umgebung starten", and the pi-agent's `ensure_environment_stopped` stops ONLY the robot tier (never the manager, never `compose down` — stop + `rm -f` for every tier including factory reset, so `ros_net` and the manager survive).

- **Compose is boot-order- and security-opinionated** (`docker/docker-compose.yml`). Startup is health-gated: `physical_ai_server` waits on `open_manipulator: service_healthy`, `physical_ai_manager` on the server — don't remove the healthchecks. Only `open_manipulator` is `privileged` + `/dev:/dev`; the server container deliberately is NOT (attack-surface trim). Every published port is loopback-bound (`127.0.0.1:`) because rosbridge `:9090` is unauthenticated — anyone reaching it can drive the arm. Both robot containers get `SYS_NICE` + rtprio/memlock ulimits (the 100 Hz loop); `mem_limit` 2g/6g + `pids_limit` are what actually OOM-kill a leaky node (the Perception-cache lesson). The `open_manipulator` healthcheck INLINE-duplicates the entrypoint's WSL2 `uname -r | grep -i microsoft` camera-source detection — change one, change both. `CAMERA_NAME_1` defaults `gripper` but `CAMERA_NAME_2` defaults EMPTY: that asymmetry is how a 1-camera Roboter-Studio kit is told apart from a 2-camera rig.

- **Students see the React UI through an embedded WebView2 window, and GUI startup is update-gated.** „Web-Oberfläche öffnen" spawns a CHILD process (`EduBotics.exe --webview` → `gui/app/webview_window.py`, pywebview 6.x on the `edgechromium` backend — pywebview demands the main thread tkinter already owns, hence the subprocess; system-browser fallback on import failure or a fast ~2 s exit). The URL carries a cache-busting `_v=<IMAGE_TAG>` param (WebView2's persistent cache would otherwise serve a stale app shell after an image update), and the GUI — not React — appends `?cloud=1` in cloud-only mode. Separately, `_check_prerequisites` hits the Cloud-API `/version` FIRST: a newer release opens a non-closable modal that downloads the installer (Content-Length + SHA-256 verified, HEAD-precheck against 404'd assets); „Überspringen" appears only after a failed attempt. Elevated repairs share `_run_privileged`: with an admin token already held (UAC off / „Never notify“) the command runs DIRECTLY with no UAC and an INFINITE wait (a timeout kill would only reach powershell.exe — the wsl.exe grandchild survives detached, and killing `wsl --import` mid-copy risks the corrupt-VHDX state); a standard token routes through `_elevate_and_wait` (ctypes `ShellExecuteExW` with `use_last_error=True` + `SEE_MASK_FLAG_NO_UI`, German SE_ERR classification — PS `Start-Process -Verb RunAs -Wait` has unreliable wait semantics). `exit_code is None` means „never launched“ (distinct from a numeric child failure); launch failures and ≥2 UAC cancels open a manual-command fallback dialog whose command MUST stay `$`-free (an interactive PowerShell interpolates `$` in double quotes before the child parses them). The post-reboot finalize (`_prompt_finalize_install`) runs AUTOMATICALLY — no consent dialog, re-entrancy-guarded via `_finalize_in_progress` (cleared in a `finally` after ALL post-processing). A `preflight_system.ps1` self-diagnostic runs once per launch on a daemon thread, informational only — its output is forced to UTF-8 via a `[Console]::OutputEncoding` wrapper and decoded `errors="replace"` (PS 5.1 writes redirected stdout in the OEM codepage; a cp1252 decode garbled umlauts and a stray 0x81 killed the whole capture).

- **The GUI-managed `.env` (`%LOCALAPPDATA%\EduBotics\.env`) is the compose interface.** Compose resolves `${REGISTRY}`/`${IMAGE_TAG}`/camera keys ONLY from the `--env-file` the GUI passes (Windows env vars do not cross the `wsl.exe` boundary). `config_generator.MANAGED_KEYS` (`FOLLOWER_PORT, LEADER_PORT, ROS_DOMAIN_ID, REGISTRY, REGISTRY_FALLBACK, IMAGE_TAG, EDUBOTICS_CAMERA_NAMES, EDUBOTICS_FOLLOWER_ONLY` + the `CAMERA_DEVICE_`/`CAMERA_NAME_` prefixes) are re-emitted on every regenerate — a stale hand-pinned value is SUPERSEDED; everything else is preserved verbatim via `_read_unmanaged_lines`. **Keep `MANAGED_KEYS` in lockstep with the emitted lines** — orphaning one leaks stale values (the `manifest unknown` scar). Per-rig overrides go through env vars (`EDUBOTICS_IMAGE_TAG`, `EDUBOTICS_REGISTRY`), never hand-edits of managed lines. Writes are atomic (temp file + `os.replace` + fsync).

- **Registry resolution: env override → `docker/versions.env` → default**, shared by `REGISTRY` (`ghcr.io/svendanilborodun`), `REGISTRY_FALLBACK` (`nettername`), `IMAGE_TAG` (`latest`) in `gui/app/constants.py`. The runtime fallback pulls the digest-identical Hub twin and `docker tag`s it to the GHCR name so compose's single `${REGISTRY}` ref resolves; the fallback ref is computed by **prefix swap**, never `split('/')`. The auto-pull digest pre-check uses **set membership** of the remote candidate set (manifest-list + child digests) because a buildx push makes the local RepoDigest the LIST digest. One-variable rollback to Hub: `EDUBOTICS_REGISTRY=nettername`. `prune_superseded_tags()` is a NO-OP while `EDUBOTICS_IMAGE_TAG` is set (both the GUI and pi_agent twins, `.strip()`-guarded) — an explicit per-rig pin IS the documented rollback, and pruning would delete the tag the operator needs to return to; the caller additionally gates on `any_updated and not any_failed`.

- **Both fleets pin `IMAGE_TAG` via a BAKED `versions.env`; the Pi's is baked by `release.yml`, not CI.** Windows gets `docker/versions.env` from `release-installer.yml`'s payload; the Orange Pi gets `pi_agent/docker/versions.env` from `release.yml::pi-agent-tarball` (`IMAGE_TAG=<repo VERSION>`), which lands at `/opt/edubotics/pi_agent/docker/versions.env` — the FIRST path `pi_agent/constants.py::_read_versions_env`'s upward walk probes, so no agent code knows about it. **The Pi's `versions.env` has TWO writers** — `release.yml::pi-agent-tarball` (rides the self-update tarball) AND `pi_agent/setup.sh` at PROVISION time (a Pi provisioned from a repo checkout never sees the tarball, so it previously had NO pin and silently tracked `:latest` = main HEAD). **With no `versions.env` at all the Pi now falls back to `APP_VERSION` — its own release — NOT `latest`** (`pi_agent/constants.py::_default_image_tag()`; only an ACTUALLY-READ VERSION counts, via `_VERSION_IS_AUTHORITATIVE`, so the baked literal never becomes a confidently-wrong pin and a blank VERSION can't yield the unpullable ref `…-opi:`). The GUI still falls back to `latest`. (The systemd unit's `EnvironmentFile` carries `IMAGE_TAG`, which is NOT the `EDUBOTICS_IMAGE_TAG` name `_resolve_setting` reads, so the env override never rescued it either.) **W6 additionally gates the Pi self-update advertisement on the three `-opi:<VERSION>` images being ANONYMOUSLY pullable on GHCR or, failing that, on Docker Hub** — mirroring the Pi's own GHCR→Hub-twin acquisition order (an image pullable on NEITHER ⇒ empty `pi_agent_sha256` ⇒ `update_checker` advertises NO update), so a Pi can no longer self-update onto a version whose `-opi` images were never published — the failure mode that previously killed the robot tier fleet-wide on the next „Umgebung starten". The intended consequence of the pin: a release whose `-opi` images never published now fails LOUDLY on the Pi (`:X.Y.Z` resolves nowhere) instead of quietly running main HEAD — `pi_agent/docker_manager.py` names the missing version in German on that path, because a bare docker `manifest unknown` reads like a network fault.

- **The Pi agent REPAIRS its own systemd units, udev rules AND its opi compose, and every mutating endpoint takes a BOUNDED lock.** `agent.py::_check_system_files_version` byte-compares the installed `SYSTEMD_UNIT_NAMES` against the copies inside `pi_agent/systemd/` and, on drift, installs the shipped bytes atomically (temp → fsync → chmod 0644 → `os.replace`, one `.edubotics-bak`, then an fsync of the DESTINATION DIRECTORY — the durability half; a rename is atomic for readers but that is ordering, not durability) + `systemctl daemon-reload` — never `restart`, never `enable`, never a unit that is not already installed. The System-tab `system_files_stale` banner now fires ONLY on drift the agent could NOT repair, and there is at most ONE banner line, naming exactly the unrepaired files. **"Exactly" is per FILE, and that took `_install_each`**: the legs used to be `all(install(n) for n in drifted)`, which (a) short-circuits — a failure on the FIRST of two units left the second UNATTEMPTED (MEASURED with `os.replace` → EPERM: `edubotics-pi-firstboot.service swapped=False`, no `.edubotics-bak`) — and (b) collapsed to one bool, so a unit that HAD been swapped was still named in the banner and got no success line, making the React banner's „mit der zuletzt funktionierenden Konfiguration" false for exactly that file. Every drifted file is now attempted, the success sentence names `repaired` and the banner names `failed`; a MIXED outcome stays possible (there is no transaction across several `os.replace` calls) but is reported as mixed. The reload is gated on "something actually changed", not on "everything succeeded". The `[WARNUNG]` line itself no longer restates the agent version or leads with `sudo ./setup.sh` — it says the Pi keeps running on the previous files, points at the reason logged ABOVE it (a promise the code keeps: both of `_install_system_file`'s False returns log a German reason first) and names the next-boot retry as the primary remedy, with `setup.sh` demoted to the fallback and still stating that the students' data survives. Rationale: units reach a Pi only via `setup.sh`, which needs a source checkout no classroom has, so any release touching a unit would pin a permanent amber banner on 100 % of the fleet AND leave that unit's own `ExecStartPre` swap-window self-heal undeliverable to exactly the population running the code that depends on it (it is therefore in place from the SECOND boot after the release that adds it). **`docker-compose.opi.yml` joined that repairable set** (`SHIPPED_COMPOSE_RELPATH`, `_compose_drifted`/`_renew_compose`) — it used to be unreachable, because it lived only in `robotis_ai_setup/docker/` while the release tarball packages `-C robotis_ai_setup pi_agent` and the self-update rsyncs `pi_agent/` alone, so a release that added a forwarded `EDUBOTICS_*` env / changed a healthcheck / re-pointed an image ref reached the field HALF-applied and SILENTLY (Rule §2's fail-open class). A **byte-identical TWIN** now ships at `robotis_ai_setup/pi_agent/docker/docker-compose.opi.yml`, fenced three ways: `ci.yml::pi-compose-twin-guard` (`cmp -s` against the source of truth, which stays `robotis_ai_setup/docker/docker-compose.opi.yml` — edit THAT one and copy), `ci.yml::compose-validate` (`docker compose config` on BOTH copies), and a `release.yml::pi-agent-tarball` gate asserting the packaged member exists and `cmp`s equal. **The twin's path is DERIVED, never restated**: both the CI and the release gate read `SHIPPED_COMPOSE_RELPATH` out of `pi_agent/constants.py` via `.github/scripts/pi_shipped_compose_relpath.py` (the release gate from the TARBALL's own copy, so it asserts the path the shipped agent will actually read) — the same rule that block already applied to `SYSTEMD_UNIT_NAMES`/`UDEV_RULE_NAMES`, because a gate pinned to a stale literal is green while fencing a file nothing reads. Keep the constant a string literal or an `os.path.join()` of string literals; the script parses it statically and refuses anything else. And note `_shipped_compose_path()` resolves PACKAGE-relative off `__file__` — repointing it at the `robotis_ai_setup/docker/` copy leaves the whole suite green in a checkout (both copies exist and are byte-identical) and silently kills the feature in the field, where only the package copy exists; `test_the_shipped_compose_is_resolved_INSIDE_the_agent_package` + `test_the_compose_repair_works_on_a_pi_with_NO_source_checkout` are the guards, and `TestBootRunsTheSystemFileRepair` pins that `boot()` runs the repair at all and runs it BEFORE `start_manager`. **Two consequences to keep straight.** (1) `release.yml`'s post-`tar` cleanup is `rm -f …/pi_agent/docker/versions.env`, NOT `rm -rf …/pi_agent/docker` — the directory holds a tracked file now. (2) The compose repair is **VALIDATE-THEN-SWAP** (`docker compose -f <tmp> config -q`), a gate the systemd path deliberately lacks: a bad unit is inert, but an unparseable compose stops `docker compose` doing anything, so the always-on manager — i.e. the wizard, i.e. the only repair surface — would never come up. A refused swap leaves the working file byte-intact and raises the banner. **Isolating that gate from the student's `.env` takes TWO things, not one**: omitting `--env-file` AND `env=docker_manager._scrubbed_env()`. Compose interpolates from the process environment too, and the unit is `EnvironmentFile=-/etc/edubotics/.env`, so the whole managed `.env` is already in the agent's `os.environ` — measured, a bare `EDUBOTICS_BIND_HOST='a b'` in the process env with no `.env` file anywhere makes `docker compose config -q` exit 1 and would refuse the repair permanently. Scrubbing gives the gate the same PROCESS ENVIRONMENT `_compose_up` runs under (that call has always been scrubbed) — and nothing more: `_compose_up` also passes `--env-file`, which the gate deliberately does not. Do not "align" the two by adding it; that difference IS the fix. Timing is split and the German says so: `boot()` runs the repair BEFORE `docker_manager.start_manager` (`up -d --force-recreate --no-deps physical_ai_manager`), so the manager tier adopts the new compose in THAT boot while the robot tier waits for „Umgebung starten". **`UDEV_RULE_NAMES` joined that set too** (`UDEV_RULES_DIR`, `_drifted_udev_rules`/`_renew_udev_rules`): the rules always rode the tarball (`pi_agent/udev/`) and the self-update rsync, but nothing ever COMPARED them, so the same fail-open sat one layer down — a release adding a VID/PID line (the planned CH343P line for the edu6 arm is exactly that) would put an agent that scans for an arm onto a fleet whose `/dev` node it has no permission to open. The renewal runs **`udevadm control --reload-rules`, NEVER `udevadm trigger`** — the exact analogue of „daemon-reload, never restart": a reload makes the rule set known, a trigger REPLAYS add/change events on already-enumerated devices, i.e. on the tty nodes a mid-lesson serial session is holding. A failed reload is non-fatal (the files are the durable half). `setup.sh` may and does trigger — nothing is live at provisioning time; that asymmetry is deliberate. **The repair only ever REPLACES, never CREATES — by contract, and that is a live constraint on the next release that adds a system file.** `_drifted_in` (and `_compose_drifted`) skip any name whose SHIPPED or INSTALLED side cannot be read, because absent proves nothing — so a NEWLY ADDED unit or udev rule reaches nobody: only `setup.sh` creates them and that needs a source checkout no classroom has, while the release-artifact gate happily confirms the new file is in the tarball. Adding a name to `SYSTEMD_UNIT_NAMES`/`UDEV_RULE_NAMES` is therefore delivery to the NEXT provision only; treat any new system file as undeliverable to the fielded fleet until create-vs-replace is settled, which is deferred to WP-2 (the CH343P/edu6 udev rule) by explicit user decision, 2026-07-28. `.s6-keep` stays OUT of the repairable set and cannot join it (0 bytes, empty blob `e69de29`, ONE commit in its entire history — `b0b601f`, the repo's SECOND, not its genesis; `setup.sh`'s own comment has always said so — a byte compare has nothing to find). It is still REQUIRED on disk (the compose bind-mounts it and Docker auto-creates a missing mount target as a DIRECTORY, refusing every server start), so `setup.sh` now CREATES it when there is no source `docker/` dir instead of `die`ing: that `die` sat at step 6 of 10 under `set -euo pipefail`, one statement after the compose install logged success, so a tarball-only provision aborted before `.env` seeding, the image pull and the unit install — i.e. it left the Pi with no agent at all (measured). Separately, every MUTATING pi-agent endpoint acquires `_lifecycle_lock` with a bounded `acquire(timeout=_LIFECYCLE_LOCK_WAIT_S)` and answers a German 503 on failure — **never a blocking `with`**: „Umgebung starten" holds that lock across a resilient image pull and nginx's `proxy_read_timeout` is 3600 s, so a blocking „Stoppen" froze the entire wizard for up to ~50 min behind the start it was meant to interrupt. `_LIFECYCLE_LOCK_WAIT_S` is DERIVED from `_PREVIEW_HANDOFF_TIMEOUT_S` (+1 s) since `stream_camera_preview` legitimately holds the lock across its handoff. Background workers (`_run_update_job`) keep the blocking form. Lock order stays one-directional. `start_robot_tier` pulls with `attempts=1` (it runs on the request thread); the update path keeps the patient budget. Finally, `UPDATE_CHECK_TTL_S=600` is paired with `_UPDATE_CHECK_FORCE_MIN_INTERVAL_S=30` and an Origin check on `force`, because `?force=1` bypassed the TTL entirely and a no-cors GET sends no Origin — a looping page turned the Pi into an amplifier against the cloud `/version`.

- **The Pi wizard is PROFILE-AWARE end to end, and every new key is additive so an un-updated Pi is byte-unchanged (2026-07-28).** `GET /status` gained exactly three keys — `robot_type` (the VALIDATED on-disk id), `robot_profiles` (`[{id, display_de, scan_requires_leader}]`) and `hardware_ready` — and `POST /robot-type` is the ONLY route added by this work (21 routed branches at HEAD vs 20 on `main`; nothing renamed or removed). `hardware_ready` is the profile-aware start gate (`_hardware_ready`: follower present, plus a leader only when `scan_requires_leader`); **`arms_identified.both` stays exactly as it was because it answers a DIFFERENT question** — are two arms present — and a follower-only rig is fully ready with it `false`, which is precisely why `omx_follower` and `edu6_studio` were both unstartable on a Pi. It is enforced on BOTH sides (`SystemPage.js` `canStart`, and again in `handle_environment_start` — the React gate is UX, not the fence). **Graceful degrade is the load-bearing property, and it takes both halves**: an agent predating this work sends none of the keys, so `robot_profiles` → `[]` (selector hidden, never crashed — a non-string `display_de` would throw „Objects are not valid as a React child" and white-screen the Pi's ONLY repair surface, hence rows are FILTERED not trusted), `scan_requires_leader` is read as `!== false` (only an EXPLICIT false hides the Leader tile — the same doctrine as the nav capability gating), and an absent `hardware_ready` falls back to `armsBoth`, i.e. the old both-arms gate. The selector is frozen exactly where the GUI greys its combobox: while the robot tier RUNS (the type is hardset at start and the arm container branches on it) and in cloud-only mode. **The scan card DELIBERATELY diverges from Windows and must not be re-synced**: heading, button and pill go SINGULAR on a leader-less profile („Arm scannen" / „Arm erkannt") and the Leader tile is HIDDEN rather than disabled, with the survivor renamed „Roboterarm" — because the Pi card sits beside labels the Windows card does not have, so a permanently empty „Leader —" made a Roboter-Studio kit look half-broken; the GUI stays plural everywhere (`gui_app.py:708`). **Three scan outcomes, three status codes, and the split is not the obvious one**: a WRONG-FAMILY arm yields **404**, not 409 — the by-id filter is family-scoped so the wrong-family arm never even reaches the prober, both slots come back `None`, and the generic „Kein Arm gefunden" is REPLACED by the German cross-family sentence naming the mismatch; genuinely nothing found keeps that generic 404; and **409 means right family, wrong arm within it**, where the message NAMES the arm that answered („Es wurde der Leader-Arm erkannt — dieser Robotertyp braucht den Follower-Arm.") rather than sending a student who plugged in the wrong board hunting a cable. **Camera roles are the one place the two platforms genuinely, permanently disagree.** `handle_cameras_roles` requires an EXPLICIT `gripper`/`scene` on every camera and answers a German 400 otherwise — there is NO lone-camera auto-assign, while `gui_app._on_cameras_changed` still auto-assigns a single camera the profile's `camera_roles[0]`. The Pi's default was deleted (2026-07-28) because it was unreachable: the only client, `SystemPage.js::handleSaveRoles`, filters its payload to `r === 'gripper' || r === 'scene'`, so an unassigned camera is DROPPED and never arrives role-less (the removal commit records a differential over all 405 UI-producible request bodies coming out byte-identical with the default present, absent, or even set to a DIFFERENT value — i.e. the branch could not affect any outcome the shipped UI can produce). **That React filter is therefore load-bearing** and is fenced by exactly three tests in `SystemPage.robotType.test.jsx` (the agent's own 400 is fenced separately by nine in `pi_agent/tests/test_lifecycle.py::TestCameraRolesRequireAnExplicitRole` — don't conflate the counts). **No lockstep test ties the two platforms' camera-role behaviour together in either direction** — this is a known, accepted, unguarded twin divergence: any future Pi client that is not that React page (a curl runbook, a kiosk script, a second front end) gets a 400 the wizard would never have shown, and nothing in CI notices. If anyone re-adds a Pi default, `scene` is the correct value on a follower-only rig (`edu6_studio_config.yaml` declares exactly one camera topic, `scene:/scene/image_raw/compressed`); `gripper` broke every RS kit. Finally, the two `fast_rehydrate_arms` twins (`gui/app/device_manager.py` and `pi_agent/identify_arm.py`) are signature-locked by `robotis_ai_setup/tests/test_arm_scan_twin_lockstep.py` after the Pi twin briefly ordered `arm_family` third and `require_leader` fourth — a third POSITIONAL argument then meant opposite things per platform — invisible to both platforms' own suites (each passes, both type-check, every caller today happens to use keywords), and the next one would have silently asked a Pi to scan the `True` arm family. The bodies are deliberately NOT asserted: only the call CONTRACT has to agree. That test carries an explicit zero-file floor (>100 `.py` files parsed AND ≥2 call sites found) because its caller check — "no caller passes a third argument positionally" — would otherwise be vacuously green after a directory move.

## Roboter Studio (layer 9) — consolidated reference

The Blockly programming surface for a follower-only kit: ONE OMX follower + ONE scene camera (no leader, no gripper cam). Everything below lives in `physical_ai_server/workflow/` + `components/Workshop/` unless noted.

### Mode & lifecycle
- **Follower-only via runtime container flip on `omx_full`, natively on `omx_follower` — not a separate stack.** On an `omx_full` rig the student starts a normal both-arms session; the React `LeaderToggle` → GUI localhost HTTP bridge (`gui/app/roboter_studio_control.py`, port **8769**, 127.0.0.1-bound, exact-host Origin-checked, busy-locked — its task-busy callback only knows whether another SWITCH is in flight; the GUI cannot see recording/inference state, so the React-side toggle disable is the ONLY mid-recording protection) → `docker_manager.restart_open_manipulator` regenerates the `.env` (`generate_env_file(robot_type=…, follower_only=True)` omits `LEADER_PORT`, emits managed `EDUBOTICS_FOLLOWER_ONLY=1`; BOTH the forward and the re-derived rollback call MUST carry `robot_type=self._rs_robot_type` or a failed switch silently rewrites the managed type) and recreates ONLY `open_manipulator` (`up -d --force-recreate --no-deps`, no pull, no `--wait`; `.env` rolled back on restart failure). On an `omx_follower` rig the stack is follower-only from env-start, the toggle self-hides (`caps.has_leader === false`) and the `:8769` bridge is never constructed (`_start_rs_control_server` lockout + a German belt refusal in `_rs_set_leader_mode`). Env-start regenerates from the selected profile (`omx_full` → both-arms, `omx_follower` → follower-only). The follower re-homes via a 3 s quintic to `[0, -π/2, π/2, 0, 0, 0.8]` — TWO pose families, NOT four identical sites: the ±π/2 boot/workflow HOME (`entrypoint_omx.sh::HOME`, `motion.HOME_JOINTS_RAD`) vs the deliberately more-folded ±π/4 collision/Jetson safe-home (`collision_monitor.SAFE_HOME_ARM`, `jetson_agent/agent.py::SAFE_HOME_JOINTS`). The ArmProfile mirrors both as unconsumed seam data (no-drift-tested); reconciling the divergence is an ask-first safety change.
- **The toggle's readiness gate holds the blocking overlay PAST the POST** (the POST returns when the container starts, not when the arm is back): scene-camera frames flowing again + `/joint_states` flowing again + the follower **moved-then-settled** (motion-witnessed latch; 12 s floor for the already-at-HOME case; 4 s min-settle; 90 s hard cap → manual „Trotzdem fortfahren"). The toggle hides on THREE `=== false` tests, all in one expression (`LeaderToggle.jsx`): no control bridge at all (`available !== true` — Jetson/cloud), the ROS capabilities saying this profile has no leader (`caps?.has_leader === false`), **or the control bridge itself saying so (`bridgeHasLeader === false`)**; it is disabled during RECORDING/INFERENCING/INFERENCE_LOADING. **The third clause is NOT gated on `piMode`, and reading it as "the Pi branch" is the mistake to avoid** — `piMode` selects only the bridge BASE (`rsControlBase`). Its Pi-specificity is EMERGENT: the Windows bridge's `/roboter-studio/status` returns `{follower_only, ready, busy}` and simply omits `has_leader`, so `undefined === false` is false and Windows is byte-unchanged — but if a future Windows bridge ever added the key, this clause would activate there too. It exists because the two platforms fail differently: on Windows a follower-only profile never CONSTRUCTS the `:8769` bridge, so the toggle is inert anyway; on a Pi the agent is always listening and answers every probe, leaving a real window between mount and the first `/task/status` tick where `caps` is still undefined and the toggle would render on a rig with no leader. Belt as well as braces — the agent's `handle_rs_set_mode` refuses a leader-less profile with a German 409 („Dieser Robotertyp hat keinen Leader-Arm — Roboter Studio ist hier dauerhaft aktiv."), in BOTH directions and before the busy lock, so even a rendered toggle cannot act.
- **`controller_manager_msgs` stays OUT of the server image** (ABI crash, see the collision bullet) — there is no switch_controller bridge; follower-only means the leader is simply never launched.

### Manual-mode arbiter (do not regress)
- **THE invariant: `on_manual == (_manual_persistent or _manual_transient_ops > 0)`, mutated ONLY under `_mode_lock` via `_recompute_on_manual_locked()`** (`physical_ai_server.py`; the only writers are the ctor + that helper). Jog/replay are TRANSIENT (refcounted claim/release); hand-guide/record are PERSISTENT (held until „Beenden"/cancel/cap-finish). Every mode entry (workflow/record/inference/the 4 manual services/capture) claims under `_mode_lock` around BOTH the `_assert_no_other_active` check AND the flag set.
- **Lock order is one-directional**: `_mode_lock` is held only around gate-check + flag-set and ALWAYS released before `_manual_lock`/`_dxl_torque_lock`/motion (`_manual_lock → _mode_lock` only, never the reverse → no deadlock). Never nest new locks into this.
- **A hard-exit generation (`_manual_exit_gen`, bumped by „Beenden") is snapshotted at claim and re-checked** after acquiring `_manual_lock` AND after the blocking re-torque, and folded into replay's `should_stop` — the arm can NEVER drive after the student pressed stop. A torque-ON-fail retains the session (fail-loud, never drives a possibly-limp arm). A 30 s idle watchdog (own callback group) re-torques + resets an abandoned session, re-checking activity freshness UNDER `_mode_lock` so it can't clobber a live claim; a frontend keepalive keeps an active hand-guide alive.
- **`_set_follower_torque` keeps the driver's refusal REASON.** It discarded `res.message`, so a specific German reason reached the container Protokoll (the driver logs it) but never the Roboter-Studio toast, where the student got a generic „bitte die Umgebung neu starten". ### Motion, IK, floors

- **The Grundstellung is guarded in JOINT space, because it has to be (2026-07-27).** `motion.home` published a straight joint-space line that nothing judged: with no Sperrzone drawn `safe_move` is a pass-through, and `WORKSPACE_FLOOR_MARGIN_M` lives only inside `_solve_or_raise`/`_try_solve`, i.e. it judges a CARTESIAN TARGET. HOME is not one — `solve()` emits strict-vertical poses only and HOME would need `q5 = 3.2708 rad` against joint5's `(−1.5708, 1.9199)`, so **`ik.solve(HOME_TCP)` returns `None`** and no Cartesian machinery (reach check, floor, reroute vias) can see it. Measured on the shipped collision meshes: that line drove a link **up to 167.9 mm BELOW the table** from ≈1 in 100 attainable start poses (0.3-1.9 % across seven samples). `base_link.STL` spans z ∈ [0.0000, 0.0625] m, so **z = 0 IS the table surface**, which is also why the guard needs no calibration.
  - **The model is `workflow/arm_geometry.py`: one axis-aligned box per link in that link's OWN frame** (7 boxes, 42 numbers, no meshes in the image), transformed by the new public `Edu6IKSolver.link_frames()`. Orientation-aware on purpose — the direction-blind per-link RADIUS form was measured and refuses 1500/1500 random configs and 900/900 legitimate table-level grasps. Sound in 1500/1500 (and 1200/1200 re-verified with random jaw openings and denser meshes), median conservatism 0.0 mm, **exact at HOME**. `base_link` is a self-collision partner but is EXCLUDED from the floor check — its underside IS the table. **`resolve_geometry` keys on the SOLVER's `backend`, and only `Edu6IKSolver` has `link_frames`** — that absence is the mechanism keeping every OMX profile bit-identical, and it is pinned by test.
  - **`workflow/home_planner.py` is the ladder**: direct → searched via → German refusal. Direct is kept as the answer for 588/600 measured starts because **every leg-splitting heuristic measured WORSE** (elbow-first 4/120 presses vs direct's 0/120; wrist-neutral 23/120). No FIXED via rescues the failures (best 7/34), so the via is SEARCHED over (j2, j3, j5) keeping the student's base yaw and rolls. **The two legs are held to DIFFERENT bounds and that is load-bearing**: the lift leg may sit as low as the arm ALREADY is (monotone in FLOOR CLEARANCE — unrelated to any Sperrzone test, which stays the plain `segment_blocked`), every later leg must clear the allowance — gating leg 1 on the allowance too rejects every candidate whenever the start is already below it, and a prototype in that form fired ZERO times. Verified end to end on the meshes: 588 direct / 4 rescued / 8 refused, **0 table presses**, worst +0.98 mm.
  - `EDUBOTICS_HOME_FLOOR_TOL_M` (default 0.020 m) is **NOT** `WORKSPACE_FLOOR_MARGIN_M` — that is a margin on a Cartesian fingertip target, this is an allowance for the box model's conservatism on whole-link geometry. Derived: 20 mm catches 12/12 real presses with 4 false positives in 800; 50 mm starts MISSING presses. `0` disables (one-variable rollback). `EDUBOTICS_HOME_SELFCOLL_WARN_M` is **WARN-ONLY, never gates a rung, and ships DISABLED (0.0)** — promoting it to a refusal is a Rule §2 change. ### Calibration (3 steps + optional check; wizard in `CalibrationWizard.jsx`)
- **Per-rig ChArUco intrinsics are MANDATORY — 20 frames** (`INTRINSIC_FRAMES_REQUIRED=20`), solved with `CALIB_RATIONAL_MODEL` (8-term — the ~102° wide lens overwhelms the 5-term default). Factory-default seeding is DELETED (never re-add): a guessed focal length scales every projected XY and the touch-off only fixes height. Any YAML with `source == factory_default` is skipped by both the manager and the runtime loader.
- **Scene extrinsic („single shot" to the student, a BURST in code)**: board against the 3D-printed L-jig → `EDUBOTICS_EXTRINSIC_BURST_FRAMES` (8) reads ~60 ms apart, ≥4 must pass per-frame gates → MAD outlier rejection → SO(3) chordal-mean. Per-frame solve: ChArUco `matchImagePoints` → **`cv2.SOLVEPNP_SQPNP` + `solvePnPRefineLM`** (ITERATIVE only as exception fallback; NOT `IPPE_SQUARE`) → compose with the jig-known `T_board_to_base` (yaw from `EDUBOTICS_BOARD_YAW_DEG`); hard reprojection/corner gates + an orientation sanity gate (`_check_extrinsic_orientation`: optical axis must hit the workspace region, camera must look DOWN) — which CANNOT catch a 90°/180°/mirror error; that's the ground-truth check's job.
- **Touch-off („Tisch vermessen")**: torque-off, student taps ≥3 spread points → FK → least-squares plane (`z_table` + tilt); gates reject near-collinear/high-residual captures (`TABLE_TOUCH_MIN_MINOR_M=0.015`, residual ≤0.008, camera cross-check 0.12 m).
- **DUAL Z-KEY CONVENTION (don't conflate)**: `board_table_z` = camera-side table SURFACE height written by the extrinsic solve (the projection plane); `z_table` = MEASURED end-effector grasp height written ONLY by the touch-off (the descend target). **There is NO `z_table=0.0` fallback anywhere** — missing touch-off → grasp/`mark_destination` refuse in German („Tisch vermessen"). Never reintroduce it.
- **Optional ground-truth XY/yaw check („Genauigkeit prüfen")**: known-placed vs detected points → closed-form 2D similarity fit (`fit_xy_correction`, Umeyama) + circular-mean yaw bias, persisted as `xy_correction`/`yaw_bias_rad` inside the extrinsic YAML and applied live in perception (`_apply_xy_correction`/`_apply_yaw_bias`). A mirror fit (`det(R)<0`) is REFUSED and persists nothing.
- `EDUBOTICS_FORCE_RECALIBRATION` (default ON) reports calibration as ABSENT until a touch-off completes in the current boot; a rig can opt out with `=0` in the host `.env`.

It holds `install_diagnostics.log` **plus** the elevated transcripts (`edubotics_finalize.log`/`.marker`, `edubotics_repair_usbipd.log`, `edubotics_bind_devices.log`) so support gets ONE artifact: the installer is `PrivilegesRequired=admin`, so on a managed PC the elevating admin's `%LOCALAPPDATA%` is not the student's and a per-user path splits the evidence. **The LEAF is load-bearing**: the six `.ps1` grant `Users(S-1-5-32-545):Modify, ObjectInherit, NoPropagateInherit` on it, and `NoPropagateInherit` is not `InheritOnly` — the ACE lands on the container itself, so granting it on the PARENT `%ProgramData%\EduBotics` (which is `import_edubotics_wsl.ps1`'s `-InstallRoot` parent) let a standard user pre-create `…\EduBotics\wsl` and own `ext4.vhdx`. `import_edubotics_wsl.ps1` additionally refuses a pre-existing `-InstallRoot` that is a reparse point (junction → elevated arbitrary write). The resolver falls back to `%LOCALAPPDATA%\EduBotics` then `~` on **unwritability** (a real create-probe — `os.access` is not ACL-aware on Windows), because the installer applies that ACL inside a bare `catch { }`. `%ProgramData%\EduBotics\.migrated` deliberately does NOT follow the sink into `logs\`. *Known-accepted residual*: `C:\ProgramData` ships an inherited `BUILTIN\Users:(CI)(AD)`, so a standard user can still pre-create `…\EduBotics\wsl` as a PLAIN user-owned directory; the junction/escalation case is closed, that one is not.
- Ports: web 80, web_video 8080, rosbridge 9090, camera-ingest 5557, Roboter-Studio control 8769 (127.0.0.1), phone HTTPS 8444.
- **Multi-line WSL scripts go through `wsl_bridge.run()`** (stdin bytes, CRLF-normalized) — `wsl.exe … bash -c "<script>"` mangles `$(...)` output containing `(`/tabs (the silent camera-discovery break). **`wsl --list --quiet` output is BOM-less UTF-16LE** — every consumer strips NULs before matching (PS scripts, `docker_manager.is_distro_registered`, `wsl_bridge`, and the `.iss` Pascal `IsDistroRegistered` — that Pascal fn was once the lone exception and silently skipped the image pull).
- **usbipd**: `Not shared` devices need an elevated `bind` first (AutoBind policies only cover future replugs) — `configure_usbipd.ps1`/`bind_devices.ps1` try three `policy add` syntaxes across usbipd 5.x patch drift; the GUI's "Arme/Kameras freigeben" repair calls `bind_devices.ps1`. Arms are OpenRB-150 boards: VID `2F5D`, PIDs `0103`/`2202` (FTDI is only a legacy udev fallback). `fast_rehydrate_arms(require_leader=True)` trusts saved leader/follower ports (arms have distinct stable serials — identical-serial is camera-only) and returns `(None, None)` on ANY mismatch — the GUI then only PROMPTS the student to rescan (`_try_rehydrate_arms` does not auto-trigger the full scan). On an `omx_follower` rig `_try_rehydrate_arms` reads the profile from the `.env` and passes `require_leader=False`: a missing `LEADER_PORT` is legal (returns `(None, follower)`), follower mismatch still fails; `_scan_arms` succeeds leader-less (`follower and (leader or not scan_requires_leader)`) without routing into the diagnose/repair flow; readiness gates go through `_hardware_ready(profile)` (`is_complete` vs the `follower_present` scaffold, now live).
- **Installer PS 5.1 traps** (CI-guarded): installer `.ps1` use `$ErrorActionPreference='Continue'` + `$LASTEXITCODE` (`configure_wsl.ps1` is the one sanctioned EAP=Stop file — it makes zero native calls) — under EAP=Stop a native `wsl`/`docker`/`usbipd`/`nvidia-smi` command writing stderr becomes a TERMINATING `NativeCommandError` even on success; `ci.yml::powershell-native-stderr` enforces exactly that pairing, not a blanket EAP rule. Shipped `.ps1` need a UTF-8 BOM (`ci.yml::powershell-encoding`; `.gitattributes` pins `*.ps1` to CRLF + UTF-8).
- **Rootfs upgrade gate protects student Docker volumes**: `wsl_rootfs/ROOTFS_VERSION` is baked into the rootfs as `/etc/edubotics-rootfs-version`; both `.iss::ShouldImportDistro` (German consent MsgBox) and `import_edubotics_wsl.ps1` skip the destructive `wsl --unregister` + re-import when versions match. Both sides fail **OPEN** on an unreadable stamp: `_rootfs_rebuild_required()` (GUI) and `RootfsReimportNeeded()` (`.iss`) block only on a POSITIVE mismatch (both stamps non-empty AND unequal). A fail-CLOSED `.iss` made a ≤2.6.0 upgrade show a German „images do NOT fit" modal and skip the pull while the GUI pulled them onto the old rootfs minutes later, and let ONE transient `wsl … cat` non-zero silently skip the in-installer image pull on a healthy machine; only `ShouldImportDistro` still acts on an unreadable stamp (the consented „one final re-import"). Relatedly, **`.reboot_required` is never routed on by EXISTENCE** — it means „the deferred work is not finished", which is true of every non-zero finalize exit, so both `finalize_install.ps1::Test-RebootStillPending` and `verify_system.ps1`'s `$rebootPending` discriminate on flag-mtime vs `Win32_OperatingSystem.LastBootUpTime` and prefer the FAILED direction on a read error (verify used to `exit 0` over a genuinely failed install, re-opening Audit-H23). finalize also takes CUSTODY of the flag across its `install_prerequisites.ps1` child (snapshot + conditional restore) because it cannot pass `-PreserveExistingRebootFlag` without re-arming the reboot loop, yet the child would otherwise delete a `dd-uninstall` flag it does not own. **Bump `ROOTFS_VERSION` whenever anything under `wsl_rootfs/` changes EXCEPT `*.md`** (`ci.yml::rootfs-version-guard` enforces it; docs are exempt because they never ship in the tarball, and a bump forces a DESTRUCTIVE fleet-wide re-import). Uninstall's distro wipe is consent-gated with default **Nein** (safe under `/SUPPRESSMSGBOXES`); `[InstallDelete]` wipes `{app}\gui|scripts|wsl_rootfs` on every upgrade. `import_edubotics_wsl.ps1` also hard-fails on a bad/missing rootfs-tarball SHA256 sidecar and on <20 GB free disk BEFORE `wsl --import` (a mid-copy failure leaves a corrupt VHDX that breaks retries).
- `pull_images.ps1` retries GHCR 3× before Hub and prunes superseded tags by enumeration (dangling-only `prune` misses them — the VHDX otherwise grows a full image per release). `finalize_install.ps1` is the elevated post-reboot/GUI-invoked one-button repair — idempotent and STATE-GATED: each phase trusts verified state (`Test-DistroRegistered` → `Wait-DockerReady` → `Test-ImagesPresent`), never child `$LASTEXITCODE` (a cosmetic non-zero from the import child must not skip the image pull; the ONE meaningful child code is import's 12, passed straight through), and every failure exits via `Fail-WithNextAction` (German next step + FAILED marker). Its exit code is THE contract with the GUI and the only thing the GUI routes on — `0` done / `10` reboot still required / `12` rootfs rebuild needs consent / `1` failed, mirrored as `gui_app.py::FINALIZE_EXIT_*`; `exit 0` with the distro still absent gets its own honest German branch rather than collapsing into „Einrichtung fehlgeschlagen (exit 0)". `wsl_docker_ready.ps1::Wait-DockerReady` (dot-sourced; caller MUST keep EAP=Continue) is the SOLE implementation of dockerd readiness — bounded exit-code polling with a `start-dockerd.sh` fallback, plus `-LastError [ref]`/`-ShowProgress`; used by finalize, `pull_images.ps1`, `preflight_system.ps1` AND `import_edubotics_wsl.ps1` (whose inline duplicate is gone). Every dot-source is `Test-Path`-guarded and fails with a German „Installer erneut ausführen" (Controlled Folder Access can silently truncate `{app}\scripts`). `install_prerequisites.ps1` deliberately does NOT gate on Windows edition (WSL2 works on Home; build ≥ 22000 only). The rootfs must keep `tzdata` installed — compose bind-mounts `/etc/timezone`+`/etc/localtime` read-only into every container, and Docker auto-creates a missing mount target as a DIRECTORY, refusing every container start. The `.iss` launches the GUI via `explorer.exe` (+ `ChangesEnvironment=yes`) so it inherits the post-install PATH — the installer-side half of the `usbipd_resolver` PATH-race fix; `CurStepChanged(ssInstall)` runs `docker compose down` before new files land.

## Cloud stack (cloud_training_api + modal_training + supabase + jetson_agent)

- **Rate limiter** (in-process, `--workers 1`): rules sorted longest-prefix-first; `/jetson/`, `/trainings/`, `/workflows` are **per-user keyed** (`jwt:<sha256(token)[:16]>` — hashed unverified token, so a forger can't starve a victim); everything else per-IP (leftmost X-Forwarded-For, safe behind Railway's proxy only). LRU cap 8192 keys/bucket. `BodySizeLimitMiddleware` rejects >384 KB on workflow/template writes before Pydantic materializes anything (1.5× the validator's 256 KB Blockly-JSON cap; the bare `"/workflows"` prefix match covers the trajectory POSTs too).
- **Teacher-facing sub-surfaces — IDOR-gated like everything else**: `progress_entries` (Tagesnotizen; 3 mutually-exclusive scopes enforced by DB CHECK + partial unique indexes), mid-training checkpoint listing (`HfApi.list_repo_files`, 30 s TTL cache), per-student `inference_runs` (self-write keyed to the JWT, pruned to newest 50).
- **CORS `ALLOWED_ORIGINS` is boot-validated** (no `*` with credentials, no wildcards, absolute http(s) URLs) — adding a browser-app origin is env-only.
- **Modal client rules**: cancel/status use Modal's **blocking API in `asyncio.to_thread`** (never `.aio()` on a `from_id` handle — raised under uvicorn); `get_job_status` must inspect the returned dict's `status` (the worker returns `{"status":"failed"}` with exit 0); `cancel` keeps `terminate_containers=True`. `modal>=1.4,<2` pin in requirements — review deliberately before any 2.x bump.
- **Worker (`training_handler.py`)**: dataset preflight — pinned to the SAME revision the trainer reads (`revision=EXPECTED_CODEBASE_VERSION`, i.e. the `v3.0` tag; a missing tag refuses in German) and asserting layout completeness at that revision (≥1 `data/*.parquet`, `meta/episodes/*.parquet`, per-camera `videos/<key>/*.mp4`, `total_episodes ≥ 1`) so a truncated upload fails cheaply — then spawns `lerobot_train`, progress via the scoped RPC, self-terminates on P0001 (cancel signal), checkpoint-watcher mirrors intermediate checkpoints to the private HF model repo, full stdout uploaded as `training_log.txt` on every terminal path (`trainings.log_url`, migration 028). The final model upload stamps `edubotics_model_meta.json` (dataset fps/repo/policy) next to `config.json` — the inference-side fps preflight reads it. The worker never writes `cancel_requested` — only the Cloud API does (direct UPDATE; the RPC's `p_status` check deliberately excludes it). `_pretrained_load_failed` greps worker stdout for THREE LeRobot-0.5.1-specific markers (`Could not load state dict` = pi0-family override; `Missing key(s)`/`Unexpected key(s) when loading model` = smolvla's strict=False base-class load) — fragile across upstream bumps, keep in sync with `_PRETRAINED_LOAD_FAILURE_MARKERS`.
- **Migrations**: latest is **036** (`edu6_arm_records` — vendor-bench servo calibration, service-role only, RLS enabled with no policies); 035 (`workflow_trajectories.robot_profile` — the edu6 arm-family tag, CHECK'd to `omx_f|edu6_studio`, NULL = legacy = omx_f) and 034 (`workflow_trajectories`), 033 (`workflows.sim_scene`), 030 (`users.hf_username`) are load-bearing. Rollback files ship in `supabase/rollback/`; manual data ops in `supabase/data_ops/` (post-deploy, never chain migrations). Two byte-similar workgroup-visibility resolvers exist (`services/workgroups.py` and `routes/workflows.py`) — semantics changes must touch both (and the inline ladder copies, Rule §4). `supabase/rollback/README.md` is stale (documents only through 009; 25 newer rollback files exist).
- **Jetson agent**: exclusive one-student claim, owner-pinned `:9091` rosbridge proxy, session volumes wiped on release; auto-pulls with the GUI's digest set-membership pre-check; `docker-compose.jetson.yml` is standalone (not `-f`-layered) with `EDUBOTICS_FOLLOWER_ONLY=1`. The proxy (`rosbridge_proxy.py`) locks the JWT alg to config (alg-confusion defense), pins the issuer, matches the owner `sub`, and caches ownership only 0.2 s (claim/release handoff race) — it currently has ZERO test coverage. The session-volume wipe works only because the compose declares explicit `name:`s that the agent's bare `docker volume rm` can resolve.
- Local run/test toggles: `EDUBOTICS_SKIP_SCHEMA_CHECK=1`, `DATASET_SWEEP_DISABLED=1`, `JETSON_SWEEPER_DISABLED=1`, `TRAINING_CANCEL_SWEEPER_DISABLED=1`. (`DATASET_SWEEP_DISABLED=1` gates spawning the sweep loop; the separate `DATASET_SWEEP_ENABLED=0` no-ops each tick of a running loop — both real, different layers.)
- Known accepted edge: `register_dataset_safe` "delete-all then re-anchor" (LOW, documented in migration 026). Gemma-license gating for pi0-family is documented-only, not enforced (PaliGemma tokenizer 401 at train start).

### Build images

**Default path for the THIN images: GitHub Actions.** Push to `main` with changes under the docker paths and `docker-publish.yml` builds both arches (`:latest`). Local builds of those are dev-only (never push from a workstation):

```bash
cd robotis_ai_setup/docker
SUPABASE_URL=... SUPABASE_ANON_KEY=... CLOUD_API_URL=... ./build-images.sh   # amd64
PLATFORM=arm64 ./build-images.sh                                             # Jetson repos, skips manager
PLATFORM=opi   ./build-images.sh                                             # Orange Pi repos, incl. manager
```

**The three self-built BASES are the exception: a workstation push is their ONLY path** (Rule §6). "Never push from a workstation" above governs the student-facing thin images that CI owns — it has never applied to the bases, because no workflow builds them:

```bash
BUILD_BASE_OPI=1   PLATFORM=opi   ./build-images.sh   # Dockerfile.arm64cpu → physical-ai-server-opi-base
BUILD_BASE_ARM64=1 PLATFORM=arm64 ./build-images.sh   # Dockerfile.arm64 → both Jetson bases
```

All three secrets are required even for a base-only build: every flavor builds the manager FIRST, and `${VAR:?}` aborts the script long before the base build runs.

An **image rebuild is required** whenever you touch: anything under `docker/open_manipulator/` or `docker/physical_ai_server/`, the overlay files, the entrypoint, the `physical_ai_server` package source (COPY-wholesale), or `physical_ai_interfaces` msg/srv — CI does those on a push. Touching a **base Dockerfile** additionally requires the manual base rebuild + a `PAS_BASE_IMAGE` tag bump in the same commit (`ci.yml::base-version-guard`); CI will otherwise build green against the old published base. Hot-deploys into a running container are ephemeral (revert on `--force-recreate`).

### Deploy

**Always via GitHub Actions** (Rule §6). Full release: bump the version (below), then

```bash
git tag vX.Y.Z && git push --tags     # fires release.yml → golden order W1→W6
```

Per-surface pushes to `main` fire the path-filtered workflow alone. **Before every tag: prove the installer builds** — `release-installer.yml` via workflow_dispatch with `version_tag` set to the PREVIOUS release (so the baked `versions.env` points at images that exist); it's the only `.iss` Pascal compile check in CI. For releases touching the upgrade path (installer scripts, `wsl_rootfs/`), install the artifact TWICE on a dev rig (first shows the German consent + re-imports; second logs „Import übersprungen" and preserves volumes).

**Bumping product VERSION = 4 in-tree sites in one commit**: `VERSION` (source of truth), `installer/robotis_ai_setup.iss` `AppVersion`, `gui/app/constants.py` fallback literal, and `pi_agent/constants.py` fallback literal. Both `constants.py` readers resolve the `VERSION` FILE at runtime — the literals are the last-resort fallback when no VERSION file is reachable (PyInstaller dists for the GUI; for the pi_agent the packaged `pi_agent/VERSION` that `release.yml` bakes and the self-update `rsync` refreshes). A stale pi_agent literal is the more dangerous of the two: it is what `APP_VERSION` degrades to if the packaged file ever goes missing, and `update_checker` compares it against the Cloud-API `/version` — a version that reads LOW re-offers the same update forever. `release.yml::version-preflight` hard-fails a tag whose name ≠ the VERSION file AND asserts the three fallback literals (`.iss` AppVersion, `gui/app/constants.py`, `pi_agent/constants.py`) equal it — all four sites are gated. (The literal check is a source grep, so keep each literal a plain `return "X.Y.Z"`.) W6 then auto-flips the Railway GUI-version vars after the `.exe` is attached — no manual Railway step.

Manual emergency paths (document in a PR): `supabase db push` / `psql -f rollback/NNN_*.sql`; `modal deploy modal_app.py`; `railway up --service scintillating-empathy --environment production --path-as-root . --ci` from `cloud_training_api/`; `build-images.sh` from a clean Linux host.

- **env-forwarding-guard** — every `EDUBOTICS_*` read by entrypoint/start-dockerd/ingest-node/overlay `.py` must appear in a compose `environment:` list **somewhere**. Read that literally: "forwarded" is a UNION over all four shipped composes reduced with `comm`, so the guard is structurally blind to a key present on ONE target only, and to a key on the WRONG SERVICE of the right file. Both shipped at once — `EDUBOTICS_ROBOT_TYPE` sat on the opi compose under `physical_ai_server` only, so an Orange Pi's arm container ran the OMX Dynamixel bringup against a Feetech bus, and the five `EDUBOTICS_EDU6_*` rollback knobs reached a Pi not at all, with this job green throughout (measured both ways: it stays green with all six deleted from the opi compose)
- **compose-env-parity** — the per-TARGET, per-SERVICE half the union guard cannot provide: `.github/scripts/compose_env_parity.py` (stdlib-only) compares `docker-compose.yml` against `docker-compose.opi.yml` service by service and fails naming both the missing key and the service. Gates KEY PRESENCE only; value diffs are `::notice` (the opi compose legitimately pins `EDUBOTICS_CAMERA_SOURCE=usb_cam` where the student compose interpolates — a `PINNED-LITERAL` notice flags that sub-class, since a knob the Pi `.env` cannot reach is how a documented rollback goes missing). An `INTENTIONAL` allowlist carries a written reason per divergence (today exactly one: opi-only `EDUBOTICS_ROS_NET_GATEWAY` on `physical_ai_manager`) and a STALE entry is a hard error. The parser reads ONE shape — a block sequence of `- KEY=value` under `environment:`, at or below that key's indent (a flush-indent sequence is valid YAML compose injects, and silently dropping it made a genuinely-missing Pi key come back green; adversarial review 2026-07-28) — and REFUSES every other way a compose could carry env rather than comparing an incomplete picture: an inline/flow/aliased `environment:`, a second `environment:` in one service, `env_file:`, `extends:`, a `<<:` merge, a non-`- KEY=value` entry, a duplicate key, a file with no services. An alias that cannot carry env is left alone — the opi compose really uses `logging: *opi_logging`. ### Deploy workflows + hardening invariants

- Health gates verify IDENTITY, never bare 200 (commit sha / buildId).
- **docker-publish**: native per-arch runners (amd64 `ubuntu-latest`, arm64 `ubuntu-24.04-arm`, NO QEMU; `fail-fast: false`); `jlumbroso/free-disk-space` amd64-only (the ~15.5 GB build needs it; arm64 fits); `--no-cache --pull`; dirty-tree refusal; buildkit routes docker.io through `mirror.gcr.io`; smoke-test pulls the **GHCR** images, asserts arch, bundle env, amd64 `.Size < 11 GB`, and runs `image_source_parity.sh`. Tag set: `:latest` (main), `:<sha>`, `:<short-sha>`, and on tags `:X.Y.Z` + `:X.Y` (both ALWAYS re-pointed on both registries — reconciles a failed-then-retried release). GHCR retags fatal, Hub best-effort (a Hub 429 warns, never fails the release).
- **Concurrency semantics differ per workflow**: `ci.yml` cancels in-flight PR runs (never main); `docker-publish.yml` never cancels (non-atomic pushes) and runs TWO lanes — a per-tag release lane vs one shared `main` lane, keyed on `github.ref` (**NOT** `github.event_name`, which inside a reusable workflow reports the CALLER's event and would silently collapse both lanes); a single static group let a third queued `main` push evict a release's PENDING W4 mid-release, skipping W5/W6 after W1 migrations and W2/W3 deploys had already landed; `release.yml` cancels on a newer tag; `supabase-migrate.yml` serializes on a project-scoped group. Job timeouts encode real budgets: docker build 60 min, retag 45 min, installer 90 min.
- **Caller-permissions-superset rule**: `release.yml` grants per-job permissions and each caller job must superset its callee's declared permissions or GH `startup_failure`s the run (documented at the grant sites). Change both in one PR.
- Every checkout: `persist-credentials: false`. All third-party actions SHA-pinned. Template injection defused via env indirection (never `${{ }}` inline in run/script for attacker-influenced values). Inno Setup pinned 6.7.0 (`--allow-downgrade --force`). `softprops/action-gh-release` needs the explicit `token:` under `workflow_call`.
- **Secrets consumed by CI** (10 + auto `GITHUB_TOKEN` + repo var `SUPABASE_BRANCHING_ENABLED`): `DOCKERHUB_USERNAME/TOKEN`, `RAILWAY_TOKEN`, `SUPABASE_ACCESS_TOKEN/DB_URL/PROJECT_REF/URL/SERVICE_ROLE_KEY/ANON_KEY`, `REACT_APP_CLOUD_API_URL`. `MODAL_TOKEN_ID/SECRET` are NOT used by any workflow — they exist for the operator's manual `modal deploy` only. (`zizmor.yml`'s "12 documented secrets" = these 10 + the 2 unused Modal tokens.)

## When in doubt
