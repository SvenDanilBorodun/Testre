### Unreleased, 2026-07-25 — edu6 pre-bench audit + R6 signs cleared on the real arm

Two threads. **On the bench (read-only throughout — ping and read only, no write, no torque, no EEPROM touched): R6 cleared.** All seven direction signs are the baked default (+1), so `EDUBOTICS_EDU6_JOINT_SIGNS` stays unset and the existing provisioning stands — no re-jig, no re-provision. The strongest instrument was **limit-impossibility**, which needs no accurate pose and no judgement call: a flipped sign means the true angle is the negative of the reading, and where that lands outside the joint's own URDF window it is physically impossible (J2 +78.3°, J3 −152.2°, J5 +118.9°, gripper +0.4° — all impossible negated). J1 and J4 were settled by absolute direction tests after two early "CCW sighting along the link" readings gave *wrong* answers: that phrasing silently inverts if the operator stands at the other end, so bench instructions now use only descriptions that cannot invert („the fingertip moves LEFT/RIGHT", „looking down at the table"). J6's sign is deferred and free to flip (symmetric window ⇒ no re-provision) and reveals itself at the first tag-aligned grasp, merging with the owed `GRASP_ROLL` jaw check. Q1 answered YES — J6 swept −178.1°→+179.7° and J4 accumulated 227°, so the ±180° map-edge residual is REACHABLE, not theoretical. Incidental: J5 reached +119.2°, past its +110° software limit (the software limit binds, not the mechanism), and the 400-tick boot band was validated by hardware — at rest J3 sits 60 ticks (5.3°) OUTSIDE its designed window, which under the original 114-tick band was 4.7° from refusing „Umgebung starten" on a completely healthy arm.

**In the code: a 9-defect pre-bench audit**, found by re-deriving the uncommitted sessions 2-4 work from scratch instead of reading its claims; two were live edu6-only software defects that had never run on hardware and were invisible to a green suite. (1) The **Cartesian jog mirrored the wrist**: `roll` and the roll JOINT are the same number on the OMX (`theta5 = roll`) but not on edu6 (`q6 = fold(wrap(π − roll))`), so both "move the tool, keep the current wrist" call sites got `−q6` back and spun the wrist up to 178° on every X/Y/Z step, rotating a held object with it — fixed by giving both solvers `roll_from_joints()` (OMX: identity) and pinning the roll joint after the solve. (2) The **seed-relative J6 fold was reverted**: measured through the real solver it reaches exactly ±180° within two grasps (the seed is the previous grasp's own answer, so the rule feeds its output back in) while the worst swing stays 178.9° either way — only the mean moved 60°→49°, not worth trading a bounded joint for; the fold reference is fixed at 0 and `solve()`'s "seed does not change the solution" contract holds again. Plus: `set_torque(True)` now seeds `Goal_Position = Present_Position` before energising (the servo otherwise drove to its stale RAM goal at up to 4.36 rad/s the instant torque returned) and fails the torque-on on a failed read; boot torque-on retries 3×; the boot-home verifier yields the command rail via a generation counter so a jog/workflow taking over is never fought; the boot plausibility band was re-sized 114→400 ticks and made env-tunable (a wrap lands ≥795 ticks outside every detectable window, so tolerance costs no detection power while a limp arm resting past a stop no longer refuses a healthy boot); the read loop was split so a raise in `_publish_joint_state` can no longer kill the thread while the write loop keeps commanding; and `Present_Load` is published as `JointState.effort` (free — the 6-byte sync_read already spans it), which is what gives R4 and R6 numbers instead of guesses. Also settled by bench data: **the firmware computes `Present_Position = (Actual − Homing_Offset) mod 4096` — it WRAPS**, so the magnet seam never reaches our software and the only discontinuity our code sees is our own tick↔angle map edge at exactly ±180° from each joint's zero. That killed both the six-horn mechanical re-clock and the J2/J3/J4/J6 limit trim (full ±180° windows KEPT), and it means the J6 fold survives on new evidence — bounded wrist swing and never parking on the map edge — not the disproven "the reading flickers 4095↔0 and the servo slams the motor" rationale that was written into the code comment.

### Unreleased, 2026-07-24 — bench R1/R2 + mixed-model discovery (STS3215 + STS3250)

First hardware power-on. R1: the CH343P enumerates on Windows as `USB-Enhanced-SERIAL CH343 (COM5)`, VID:PID `1A86:55D3`, "Not shared" (Windows owns the port for bench provisioning), descriptor carries "CH343" → `_EDU6_BYID_MARKERS` covers it. Fix: `feetech_bus.STS_ACCEPTED_MODELS = {777, 2825}` + `STS_MODEL_NAMES` as the single source shared by all three identity checks (provision, `probe_bus`, `identify_feetech`); the provisioning record now stores each servo's ACTUAL model + name (traceability), never hardcodes 777. Tests 81 direct / 626 discover (mixed-model accepted, foreign model refused, per-servo record). Open bench decision carried to R4/R6: the tool's `PROTECTION_CURRENT=150` (≈975 mA) is likely below the STS3250 holding current — measure `Present_Current` at R6 before committing the final overcurrent floor (the sustained-overload safety at addr 34/35/36 is factory-set and independent).

## Recent changes — cloud-training cancel + live-progress fixes (2026-06-09)

**The four locked decisions (2026-06-07):**
