# leLab vs EduBotics — Deep Comparative Study (2026-06-06)

**Method.** 37 Opus 4.8 agents (4.0M tokens, 889 tool calls): 11 dimension agents read both codebases file-by-file with git archaeology; every high/medium-impact lesson was then re-verified by an adversarial agent that re-read the cited code in BOTH repos and tested the proposal against the six non-negotiable rules. Result: 53 lessons → 26 verified → **8 confirmed / 15 partially-correct (direction holds, details corrected) / 3 refuted**.

**Subject.** [huggingface/leLab](https://github.com/huggingface/leLab) — HF's official LeRobot web GUI. FastAPI + React/Vite/TS/shadcn served from ONE pip-installed process on `:8000`; wraps LeRobot's Python API directly for SO-101 (Feetech) leader/follower arms. ~6.2K LOC Python + ~13.5K LOC TS. 374 commits, zero tags, version hardcoded `0.1.0`, born at the June-2025 LeRobot Worldwide Hackathon, effectively single-author (Nicolas Rabault 358/374), AI-review commits co-authored by Claude Opus 4.7. Local clone studied: `/tmp/lelab-study/leLab`.

## 1. The one-paragraph verdict

leLab and EduBotics are near-twins in genesis (single author, 2026-05 commit burst, LeRobot wrapper, Claude-assisted review sweeps) and **opposites in philosophy**: leLab is a thin, trusting, English, developer-facing wrapper that rides HF's primitives (HF Jobs for cloud GPU = ~509 LOC; your account, your bill) and refuses product weight (no auth, no tags, no safety, hardcoded robot). EduBotics is a vertically integrated product that trusts nothing (credits under `FOR UPDATE` row locks, two-phase cancel, German-at-source errors, collision e-stop, image==repo CI gates). **Neither architecture transfers wholesale — the audiences dictate them** — but the comparison surfaced one live data-destroying bug in EduBotics, ~10 cheap adoptions, and several doc-vs-code drifts. The deepest result: across 11 dimensions the agents repeatedly found *convergent evolution* (same subprocess+stdout-scrape training pattern, same 1s→30s WS backoff, same anti-vacuous-pass guards, same footer-less-parquet hazard) — independent confirmation that both teams keep hitting the same walls LeRobot leaves to its integrators.

## 3. P0 — Bugs in EduBotics surfaced by the comparison (fix regardless of leLab)

1. **`data_editor.py` is layout-incompatible with what we record (CONFIRMED, high/high).** delete_episode / delete_episodes_batch / merge_datasets (data_editor.py:962-1066 etc.) are hardcoded to the v2.1 per-episode layout (`data/chunk-000/episode_NNNNNN.parquet`, per-episode mp4, `meta/episodes.jsonl`); the v2.5.0 recorder writes v3.0 concatenated shards (`videos/<key>/chunk-NNN/file-NNN.mp4`, `meta/episodes/*.parquet`). The feature is **live and student-reachable** (Daten tab → DeleteSection/MergeSection): deleting an episode from any freshly recorded dataset throws FileNotFoundError immediately — and this is the most data-destructive path in the product. Fix: rewrite against v3.0 (resolve episode→(chunk,file,row-range) via `meta/episodes/*.parquet`, or load→filter→re-create via upstream utilities), keep a v2.1 path for legacy datasets, gate the UI on `codebase_version`, add a record-tiny-v3.0-then-delete regression test, finalize()+re-verify after every edit.
2. **The "Factory Reset" button does not exist.** CLAUDE.md instructs students/operators to use it (v2.5.0 upgrade notes, "When to ask the user") but grep across all .py/.js/.ps1 finds no implementation. Either build it (GUI button → volume wipe with German consent) or fix CLAUDE.md + release notes to give the `wsl -d EduBotics -- docker volume rm` path.
3. **Uninstall wipes all volumes with no warning.** Upgrades got the ROOTFS_VERSION gate + consent dialog (v2.6.1), but uninstall still unconditionally `wsl --unregister EduBotics` (robotis_ai_setup.iss:194-198) — datasets/HF cache/calibration gone silently. Add the same German consent + "upload your datasets first" warning to the uninstaller.
4. **Doc-vs-code drift: capture backend.** CLAUDE.md + win_camera.py docstring say DirectShow (`CAP_DSHOW`); the code defaults to MSMF (win_camera.py:62-65, post-2026-05-24 benchmark). Fix the docs (CLAUDE.md "When in doubt" rule applies to itself).
5. **Dead code: ZMQ remote-inference pair.** `server_inference.py` + `client_inference.py` (TorchSerializer over ZMQ REP/REQ) — `ServerInference` is never instantiated anywhere, and it constructs InferenceManager with kwargs that don't match. Delete or document why retained (Rule §3 asserts what ships == repo; dead code in the COPY-wholesale package ships to every student).
6. **Enum NAMES already diverge across the wire mirror.** SendCommand.srv says `MOVE_TO_NEXT = 4`, taskCommand.js says `NEXT: 4` — only the int saves us today. See P1-3 for the CI guard.

(Also noted: the "AWS key in git history" a verifier flagged is **benign** — GitHub's S3 signing key ID inside an *expired 2024 presigned URL* in the old vendored LeRobot README, removed in 8d1962d. It just needs a gitleaks allowlist entry.)

## 4. P1 — Confirmed adoptions from leLab (verified, rule-clean)

1. **Pre-flight the checkpoint's camera contract + language-conditioning (high/medium).** leLab reads `pretrained_model/config.json` (jobs.py:943-973), extracts `observation.images.*` + `requires_task` (`_LANGUAGE_CONDITIONED_POLICY_TYPES = {smolvla, pi0, pi0_fast, pi05}`, jobs.py:531) and forces camera binding pre-run. EduBotics parses the SAME keys (`_read_expected_image_keys`, inference_manager.py:122-131) but only uses them **mid-run** → German RuntimeError tears down inference. Adopt: extend `validate_policy`'s return (avoid a new .srv — interfaces-validate friction), surface "dieses Modell erwartet Kameras X, Y" pre-flight in InferencePanel, hide the Aufgabenanweisung field unless language-conditioned. Order UX download→introspect→run.
2. **Live camera preview at role assignment (high/medium).** leLab shows a live thumbnail per camera binding (CameraConfiguration.tsx:285-318, getUserMedia). Our tkinter role dialog is two name-only combo boxes ("Kamera 0/1", gui_app.py:1442-1481) — with identical-serial Innomakers a student picks blind, and a gripper↔scene swap **silently corrupts every recorded dataset**. Adopt in the GUI with the existing win_camera capture. Verifier corrections: PIL/ImageTk is NOT currently bundled (use Tk PhotoImage/PPM or add Pillow to gui/requirements.txt + build.spec); backend is MSMF not DSHOW; open-once-and-poll, never concurrent with the running bridge (pre-start scan phase only).
3. **`enum-parity` CI job (high/low).** Parse `uintN NAME = N` from SendCommand.srv + TaskStatus.msg and assert the same INTS exist in taskCommand.js/taskPhases.js (key on value — names legitimately diverge, see P0-6), plus assert the getattr-fallback literals (collision_monitor.py:113-114, physical_ai_server.py:992,1001, test_collision_monitor_contract.py:376) equal the .msg constants. Same Python-heredoc idiom as interfaces-validate/tutorials-validate. Closes the getattr scar's missing guardrail.
4. **gitleaks secret-scanning CI job (high/low).** We have ZERO secret scanning across 7 workflows carrying 12 GHA secrets + service-role keys. Add SHA-pinned `gitleaks-action` as job #15 with a `.gitleaks.toml` allowlist (CI placeholder keys at ci.yml:67-70/240/476/513-516, the expired GitHub-presigned URL above, Supabase project refs). leLab runs it in pre-commit + CI (quality.yml:49-52).
5. **Frontend lint gate (high/medium, reframed).** Headline "zero linting" was wrong — CRA runs eslint warnings non-blocking on build. The real gap: **no GATING lint job**, and CLAUDE.md documents exactly the bug class react-hooks/exhaustive-deps catches (stale rosbridge closure, Benutzer-ID wipe). Add `react-lint` ci.yml job (`npx eslint src/` with CRA's bundled config), advisory-first for one release, then enforce.
6. **Transient spec→plan scaffold (high/low).** leLab committed dated spec+plan docs BEFORE each multi-module feature (4637685 precedes the whole HF-Jobs tree; the robot-config spec wrote down its non-goals WITH trigger conditions) then deleted them all (88859e7). Adopt: `docs/plans/` (gitignored), one-pager required for any feature touching >1 of the 10 layers, mandatory "Non-goals (this round)" with trigger conditions. CLAUDE.md stays invariants-only. Targets our 0.23 feat:fix ratio.
7. **Show-the-remedy escalation in CollisionModal (medium/low).** leLab pattern-matches the discontinuity error and auto-scrolls a demo video into view + dedicated remedy alert (Calibration.tsx:39,353-363,805-823). Adopt: when the safe-home glide exhausts GLIDE_MAX_SENDS, escalate the modal with a bundled (NOT hot-linked — offline classrooms) diagram/clip of "remove the obstacle". Pure German React.
8. **Precise HF-auth message on upload failure (medium/low).** leLab detects 401/"authentication" substrings and returns an actionable message + docs link (record.py:527-537). Ours shows generic `[WARNUNG]`. Adopt at the REAL hot spot (verifier): `upload_huggingface_repo()` whoami-catch (data_manager.py:1186-1192) + hf_api_worker.py:386-390 — German: "HF-Token ungültig oder abgelaufen → EduBotics-App Schritt D", never "hf auth login".
9. **Teacher-only full training log (medium/medium).** Worker keeps only a 2KB truncated blob on failure (training_handler.py:601,663-672); leLab tees full stdout to durable log.jsonl + re-parses metrics from it. Adopt: upload the full `output_lines` deque to the private HF model repo (worker already holds the token + create_repo path) or Supabase Storage; nullable `trainings.log_url`; surface ONLY in teacher dashboard behind the existing ownership asserts (Rule §4). ## 6. Refuted — do NOT implement (and why, so they don't come back)

1. **"Add a mode-arbiter lock — flags race across 6 executor threads."** FALSE: all four start callbacks are 3-tuple registrations on the node default **MutuallyExclusiveCallbackGroup** — rclpy guarantees they never co-schedule even on a 6-thread executor. The flag-check+set is already serialized. (leLab DID have this race — ea4b7f2 fixed it — because bare HTTP threads have no such group.)
2. **"Decouple mode-liveness from the data stream (their a08ab03)."** Premise false twice: the 5 s `DEFAULT_TOPIC_TIMEOUT` is a **startup warmup grace** keyed to a fixed per-episode start time (never refreshed → cannot fire mid-episode), and the camera cache is last-known-wins (a transient gap doesn't null it). Mid-recording stale-camera is already warn-don't-halt. The inference-side "keep going on dead camera" half would brush Rule §2.
3. **"Adopt a periodic batched AI-review sweep ritual."** We already do this bigger than leLab (616c8aa: 60+ findings across all layers, one commit, Claude-co-authored; 307cffa; the 11-agent v2.6.1 audit). Their two sweep commits were a one-time cleanup, not a ritual; the "one mega-commit" prescription is worse than our current practice.

Pedagogical value: visualize joint limits, collision freeze, home pose; works with no arm powered. Bundle meshes in the SPA (offline), subscribe /joint_states via existing rosbridge.
- **Phone as 3rd camera (medium/high).** leLab built WebRTC phone-camera and **abandoned it** ("not working", 0ac38c1 → removed; docs still dangle). Our camera_ingest_node IS the simple working version of what they attempted — any JPEG source can feed a 3rd cam_id over TCP. Gaps: ImageGrid hard-caps 3 cells (fine), static camera_topic_list YAML, phone→PC transport (LAN HTTPS for getUserMedia, or a tiny app POSTing JPEG). Bypasses the WSL2 USB ceiling entirely for an extra view.
- **Teacher try-before-install demo (medium/high).** Their HF Space "demo" is a backend-less billboard with a non-dismissible install modal — the *funnel pattern* transfers, not the implementation. We already dual-build the SPA with a configurable rosbridge URL; a Railway demo mode with canned/simulated topics is the missing piece.
- **Developer inner-loop (medium/medium).** `lelab --dev` = Vite HMR + uvicorn --reload; our loop is image-rebuild + reinstall. Containerization is non-negotiable (Rule §3 governs SHIPPED images), but a documented dev-only bind-mount compose override (mount physical_ai_server source into the container + react-scripts start against the live rosbridge) would cut iteration 10×. ## 8. Where EduBotics is ahead (the reverse lessons — leLab would have to learn from us)

- **Dataset integrity:** explicit upload-gating `finalize()` + layered verifiers. leLab has the **exact footer-less-parquet bug we paid for**: `record_with_web_events` never finalizes; `push_to_hub` uploads the folder before any `__del__` runs → a <10-episode dataset ships unreadable. (Their pinned lerobot's own docstring calls `__del__` "only a safety net".)
- **Safety:** model-aware collision e-stop, SIGTERM torque-disable, anti-vacuous-pass Phase-4, Rule §2 trust-boundary discipline. leLab: zero runtime safety, no torque handling on shutdown — official ≠ safety-hardened.
- **Curation intent:** their EditDataset is a stub; ours exists (and after P0-1 will actually work on what we record).
- **Multi-tenancy/cost-safety:** row-locked credits, derived (not mutable) credit counting, two-phase cancel with confirmed-teardown-before-refund, scoped worker tokens, preflight-before-GPU-burn, server-side caps. They have *nothing* here — and will re-earn these scars if they ever serve >1 user.
- **Camera robustness:** single-owner capture (no preview/recorder contention — they reverted 5 commits fighting it), identical-serial defense, per-stream QoS with documented rationale, capture-time stamping for sync.
- **Release engineering:** semver + IMAGE_TAG pinning + W1→W6 atomicity + deploy gates asserting commit equality + upgrade-safe rootfs gating vs their 0.1.0-forever, zero tags, commit-back race (visible as 3 consecutive bot commits).
- **Ops UX:** 279 German toast sites, build-config white-screen guards, self-updating client, heartbeat tri-state, Windows→WSL→Docker diagnostic chains, GDPR private-by-default uploads.
- **Multi-robot:** they specced-and-deferred; our config-YAML core already ships 4 robot configs — the strategic asset for DK1/XLeRobot.

## 9. Philosophical takeaways

1. **Birth archetype is destiny.** Hackathon-genesis bought leLab simplicity it still cashes (one process, one wheel, `--dev` HMR); product-genesis bought us trust machinery they can't retrofit cheaply. Copy *patterns* across the boundary, never *architecture*.
2. **Ride the dependency's native primitives where the trust model allows.** HF Jobs (~509 LOC) vs our owned Modal stack (thousands) is the starkest frame: every place we CAN lean on HF/LeRobot/ROS primitives without violating the school trust model, we should subtract owned surface. (And the inverse: where the trust model forbids it, our "overhead" IS the product.)
3. **Generic + bespoke CI are complementary, not rivals.** Their stack catches whole classes (secrets, action security, types) with zero authorship; ours catches what no generic tool can know (German strings, env forwarding, image parity). Converge: adopt their 3–4 cheapest generics; they'd need our bespoke layer to ship a product.
4. **Both teams keep independently rediscovering the same LeRobot integration walls** (subprocess+stdout-scrape, finalize hazards, vacuous-pass guards, WS backoff constants). Watch their repo: their fix-history is free advance warning of our next wall — and vice versa.
5. **Write down deferrals with trigger conditions.** Their robot-config spec's "we'll add a `model` field when a second model actually ships" is the discipline our Known-Issues register approximates but doesn't formalize. The transient spec→plan scaffold (P1-6) imports it.
